## 一、业务流程全景图分析

### 1.1 流程图结构解读

基于提供的业务流程图，系统包含 **7 条核心业务流程泳道**，从上至下分别为：

```
泳道 1: 采购管理 ──────── 请购→审批→订单→审批→收货→质检→入库
泳道 2: 销售管理 ──────── 询价→报价→订单→审批→备货→出库→发货
泳道 3: 生产管理 ──────── 计划→工单→审批→领料→生产→报工→完工入库
泳道 4: 仓储管理 ──────── 入库→上架→存储→拣货→出库→盘点
泳道 5: 质量管理 ──────── 来料检→过程检→出厂检→缺陷处理
泳道 6: 设备管理 ──────── 台账→点检→保养→维修→OEE
泳道 7: 财务管理 ──────── 应收→应付→成本核算→报表
```

流程图中每个泳道包含：
- **圆形节点**：业务操作步骤
- **菱形节点**：审批/判断决策点
- **矩形节点**：状态变更/数据写入
- **箭头连线**：流程方向和条件分支
- **分支路径**：审批通过/驳回/撤销

## 二、效率瓶颈识别

### 2.1 采购流程瓶颈

| 瓶颈编号 | 瓶颈描述 | 严重程度 | 代码位置 |
|----------|---------|----------|---------|
| **PB-01** | 采购订单 submit() 缺少前置状态校验 | 高 | PuPurchaseOrderServiceImpl.submit() 第194行 |
| **PB-02** | 供应商校验 validateVendor() 仅做基础检查，缺少价格/交期智能比对 | 中 | PuPurchaseOrderServiceImpl.validateVendor() |
| **PB-03** | 请购来源单一，仅支持手动创建，缺少自动补货建议 | 中 | PuPurchaseRequisitionServiceImpl |
| **PB-04** | 收货与IQC检验之间无自动联动，需人工触发 | 高 | PuPurchaseReceivingServiceImpl |
| **PB-05** | 供应商评估算法未实现，评估数据无法沉淀 | 中 | PuVendorEvaluationServiceImpl (空实现) |

**瓶颈影响分析**：
- PB-01 可能导致非草稿状态的订单被重复提交到审批流
- PB-04 导致采购收货后需要人工等待IQC结果才能入库，增加了 **2-4小时** 的等待时间
- PB-05 导致采购决策缺乏数据支撑，供应商优选依赖经验而非数据

### 2.2 生产流程瓶颈

| 瓶颈编号 | 瓶颈描述 | 严重程度 | 代码位置 |
|----------|---------|----------|---------|
| **PB-06** | BOM递归展开缺少深度限制，循环引用导致栈溢出 | 高 | PrdWorkOrderServiceImpl (BOM分解) |
| **PB-07** | 生产完工后缺少自动倒冲领料，库存与工单状态脱节 | 高 | PrdWorkOrderServiceImpl.complete() |
| **PB-08** | 工单→MES流转卡之间缺少自动联动接口 | 中 | PrdWorkOrderServiceImpl |
| **PB-09** | 缺少产能日历，排产无法考虑设备/人员可用性 | 中 | 无(待开发R-022) |
| **PB-10** | 返工订单未支持，返工场景无法管理 | 中 | 无(待开发R-020) |

**瓶颈影响分析**：
- PB-06 是一个**生产环境炸弹**，一旦BOM数据出现循环引用，将直接导致系统崩溃
- PB-07 导致完工后库存数据不准确，需要人工补录领料单，平均每个工单额外耗费 **30分钟**

### 2.3 仓储流程瓶颈

| 瓶颈编号 | 瓶颈描述 | 严重程度 | 代码位置 |
|----------|---------|----------|---------|
| **PB-11** | 出库操作无流水记录，审计链条断裂 | 高 | WmSalesIssueServiceImpl.completeSalesIssue() 第119-185行 |
| **PB-12** | 4个库存过账方法缺少@Transactional注解 | 高 | WmStockOperationServiceImpl 第51-70行 |
| **PB-13** | 全局无并发控制(无锁/无乐观锁/无分布式锁) | 高 | 所有库存操作 |
| **PB-14** | 条码生成器使用JVM内存AtomicLong，多实例部署时重复 | 高 | BarcodeGenerator第16行 |
| **PB-15** | 策略execute(Object... args)类型不安全 | 中 | StockOperationStrategy |
| **PB-16** | 仅2/7个策略有幂等检查(hasPosted) | 中 | TransferStrategy/CountAdjustStrategy等 |
| **PB-17** | 盘点快照与实际过账之间存在时间差，可能导致调整方向错误 | 中 | WmStockTakingPlanServiceImpl.generateLines() |
| **PB-18** | 入库/出库存在两条不一致的执行路径 | 高 | completeSalesIssue vs stockOperationService.postSalesIssue() |

**瓶颈影响分析**：
- PB-11 + PB-18 组合风险最高：出库操作可能通过两条不同路径执行，一条记流水一条不记，数据不一致
- PB-13 在高并发场景下可能导致**库存超卖**（扣减后变成负数）或**双重入库**

### 5.2 Phase A: 紧急修复 (1-2周)

#### 优化项 A1: 库存并发安全加固

**目标**: 消除库存超卖和双重操作风险

**实施步骤**:

| 步骤 | 具体操作 | 工作量 |
|------|---------|--------|
| A1-1 | `wm_material_stock` 表增加 `version INT DEFAULT 0` 字段 | 0.5d |
| A1-2 | `WmMaterialStock` 实体增加 `@Version` 注解 | 0.5d |
| A1-3 | 所有库存更新操作增加 WHERE version = ? 条件 | 1d |
| A1-4 | 库存不足时抛出 `ServiceException` 而非静默失败 | 0.5d |
| A1-5 | 编写并发测试验证乐观锁生效 | 1d |

**预期效果**:
- 并发更新时后更新的请求自动失败(版本不匹配)
- 消除库存超卖风险
- 库存操作成功率从 ~99% 提升至 100%

**KPI指标**:
| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| 并发库存操作冲突率 | ~1%(估算) | 0% |
| 库存数据不一致事件 | 偶发 | 0 |

**目标**: 消除部分成功无法回滚的风险

#### 优化项 A3: 统一出库执行路径

| A3-4 | 回归测试全部出库场景 | 1d |

**预期效果**:
- 出库操作100%有审计流水
- 出库逻辑只有一条执行路径，维护成本降低50%

**预期效果**:
- 撤回后业务单据状态自动回退到初始态
- 前端显示状态与实际流程状态一致

**目标**: 消除9个模块的审批流代码重复

| 步骤 | 具体操作 | 工作量 |

| B1-2 | 将通用的 submit/getProcInsId/getBusinessDataById 逻辑上移 | 2d |
| B1-3 | 将 afterFlowHandle 的状态映射逻辑配置化(状态映射表) | 2d |
| B1-4 | 9个ServiceImpl改为继承抽象基类 | 2d |
| B1-5 | 验证所有审批流功能正常 | 1d |

**预期效果**:
- 审批流集成代码减少 **60%**(约900行)
- 新模块接入审批流只需实现状态映射配置
- 审批流逻辑统一维护，减少bug

**抽象基类设计**:

```java
public abstract class AbstractFlowableCallbackService<T> implements WfCallBackServiceI {
    
    protected abstract Class<T> getBusinessClass();
    protected abstract Map<String, String> getStatusMapping();
    // ActStatus → 业务状态 的映射关系
    // 例如: {"pass" → "APPROVED", "reject" → "REJECTED", ...}
    
    @Override
    public void afterFlowHandle(WfMyBusiness business) {
        String actStatus = business.getActStatus();
        String bizStatus = getStatusMapping().get(actStatus);
        if (bizStatus != null) {
            updateBusinessStatus(business.getDataId(), bizStatus);
        }
    }
    
    @Override
    public Object getBusinessDataById(String dataId) {
        return getBusinessById(Long.parseLong(dataId));
    }
}
```
