## 1. 目标与范围

本次工作目标是使用本机 3306 的现有业务库，生成可追溯、符合实际业务关系和编号规则的正式业务数据，真实跑通以下四条主链路，并在过程中修复可复现的后端漏洞和 PC 前端显示问题：

1. ERP：基础资料、销售订单、采购、收货入库、生产计划、工单、领料、完工、发货和库存追溯。
2. MES：ERP 工单发布、消息下发、工序派工、流转卡、数据采集、报工、SN/批次追溯、质量检验、返工和安灯。
3. IoT：产品/设备注册、MQTT 接入、属性解析、数据入库、最新值、告警和 SSE 实时推送，并验证与 MES 工位/设备的关联。
4. AI/Flow：ERP/MES/IoT 事实快照、缺料和 APS 推演、风险评分、证据、摘要、人工审批、ERP 草稿动作、幂等、STALE 和结果追踪。

AI 还需对现有 40 类交付风险案例进行真实 HTTP 回归。案例业务 ID 映射到本机真实生成的工单和自然业务编号，不沿用明显的 `DEMO-`、`TEST-` 或 `MOCK-` 业务名称。

CV、Station、IM、电子签章不作为本轮主链路；只有在上述链路存在依赖或实际故障涉及这些模块时，才补充验证。

## 2. 数据治理与编号策略

### 2.1 数据来源与租户

写入前先只读盘点：

- 实际系统、ERP、MES、IoT 数据库名称和连接状态；
- 有效租户、用户、部门、仓库、车间、工位、客户、供应商、物料、单位、BOM、工艺路线和设备；
- 当前自动编码规则、序列号/批次号规则和各模块所需状态初值。

优先复用已有有效基础资料。缺失的基础资料通过实际业务接口创建，禁止直接伪造外键关系或跨租户借用记录。目标租户以盘点结果为准，不预设 `000000`。

### 2.2 编号策略

- 业务单据编码统一使用现有 `SysAutoCode` / `AutoCodeUtil` 规则；
- 产品序列号、批次号和条码使用 `bd_serial_number_rule`；
- 工单、采购申请、采购订单、收货单、入库单、MES 流转卡、设备和 IoT 产品的编号由实际服务生成；
- 不手工拼接业务编号，不硬编码雪花 ID、单据 ID 或外键 ID；
- 不修改流水号规则的当前值，除非正常业务接口本身产生递增；
- 业务名称和编码不出现 `DEMO-`、`TEST-`、`MOCK-`、“测试”“演示”“临时”等明显测试标识。

### 2.3 可追溯与回滚

本次不新增数据库表、不导入主初始化 SQL、不清空或重置既有业务表。写入前保存目标表数量和关键摘要；每次写入后立即记录表名、主键、业务编号、租户、创建时间、依赖关系和回滚顺序到本地内部清单。内部清单不记录密码、Token、连接串或完整敏感配置。

回滚脚本只根据本次内部清单按依赖逆序生成，默认不自动执行。禁止 `TRUNCATE`、全库清空、无条件按名称删除和直接修改业务状态字段。测试产生的业务状态和审计记录默认保留，清理需另行明确授权。

### 2.4 时间与事实

以 2026-09-28 为执行基准，通过业务日期偏移形成订单承诺日、采购到货日、生产计划日、产能日历和 IoT 采集时间。日期必须符合订单、采购、生产、质量、库存和设备事件的时序关系。

AI 事实全部从 ERP/MES/IoT 业务记录重读并计算。预期风险、根因、方案和动作只用于验收比对，不作为业务输入写入 AI 表。

## 3. 执行链路与场景

### 3.1 基线检查

不写入数据，完成 Git、数据库、Redis、RabbitMQ、MQTT、Flow/任务调度、后端和前端依赖检查；读取租户、账号、权限、编号规则和基础资料；保存现有目标表数量、最大业务编号和关键业务摘要；生成本次执行批次清单。基础设施不可用时记录阻塞，不用 SQL 伪造通过。

### 3.2 ERP

**ERP-01 正常订单交付：** 基础资料 → BOM/工艺路线 → 销售订单 → 生产计划 → 工单 → 采购申请/采购订单 → 到货/收货入库 → 生产领料 → 完工入库 → 销售发货。

断言编号、状态机、订单/计划/工单/需求/采购关联、数量、库存、批次、SN 和追溯完整且无孤立明细。

**ERP-02 采购延期与缺料：** 通过真实采购业务产生到货日晚于需求日的事实，校验需求、采购、到货和缺口关系，并由 ERP 缺料服务重算缺料日期、缺口和供应商证据。

**ERP-03 库存与仓储异常：** 覆盖收货入库、生产领料、退料或库存调整、批次/SN 追踪、发货扣减和库存流水；不直接修改库存余额。

### 3.3 MES

**MES-01 工单执行闭环：** ERP 工单发布 → RabbitMQ 下发 → MES 接收 → 派工 → 流转卡/工序任务 → 数据采集 → 报工 → SN/批次绑定 → 完工回写 ERP。验证消息幂等、报工数量约束、回写对象和重复消费。

**MES-02 质量异常与返工：** IQC/IPQC/OQC → 缺陷/NCR → 返工工单 → 重新报工 → 复检。验证检验标准、缺陷数量、原始报工不可篡改、返工追溯和放行状态。

**MES-03 安灯事件：** 触发设备/工序异常，验证安灯告警、通知、处理人、关闭记录、工单/工序/设备关联和重复上报幂等。

### 3.4 IoT

**IoT-01 设备采集：** 产品 → 设备 → MQTT 认证/连接 → 属性发布 → Topic 解析 → 类型转换 → 数据记录 → 最新值缓存。验证产品、设备、属性、租户、采集时间、无效主题和越权设备。

**IoT-02 告警推送：** 发布超限温度、振动或停机状态，验证规则、告警事件、通知、恢复、SSE 消息、重复数据和乱序数据处理。

**IoT-03 MES 关联：** 关联真实工位/设备，在工单执行期产生采集数据，验证 AI 可读取设备健康、停机和异常证据；设备失效或解绑时验证权限和提示。

### 3.5 AI/Flow

**AI-01 综合风险：** 使用 ERP 订单/采购/库存/工单、MES 计划/报工/质量/安灯和 IoT 状态/告警形成 `DeliveryContextSnapshot`，执行缺料推演、APS What-if、风险评分、证据和摘要，最终进入 `WAITING_APPROVAL`。风险数值由确定性服务计算，模型不得伪造事实、证据或动作。

**AI-02 审批与幂等：** 覆盖催货、采购申请草稿、排产草稿、驳回原因、重复审批、重复执行、数据变化导致 `STALE`、部分执行失败、重试和审计。验证 actionId、decisionRunId、幂等键、执行结果和错误原因。

**AI-03 40 案例：** 保留正常、缺料、供应商延期、产能瓶颈、紧急插单、组合风险和证据缺失分类；每例先通过 ERP 只读核对真实工单 ID/编号，再启动 Decision，等待合法终态，对比风险、置信度、根因、方案、动作和精确失败码。CONTROL 审批/执行场景单独统计。

## 5. 缺陷处理

每个缺陷先保存请求、响应、日志、数据库状态、消息和页面证据，在最小范围稳定复现并定位数据流根因；随后增加失败回归测试，确认测试因缺陷失败，实施最小修复，确认测试通过，再重跑受影响链路和相关回归。不得通过放宽断言、修改黄金期望、跳过场景或直接改状态字段消除失败。

后端问题补 Java 回归测试；前端问题补纯函数、组件或页面行为测试。与本任务无关的重构不纳入分支。
