
## 4. 编码重置方案

### 4.1 ★★★ 有 5 套计数器，只清 `sys_auto_code_result` 是不完整的

| # | 机制 | 计数器位置 | 管什么 | 怎么重置 |
|---|---|---|---|---|
| **A** | 自动编码引擎 | `ry-vue.sys_auto_code_result.last_serial_no` | 30+ 张表的单据号/主数据码 | `DELETE FROM … WHERE tenant_id='000000';` |
| **B** | Redis 按日序列 | Redis `erp:batch:seq:*`、`erp:sn:seq:*` | **`wm_batch.batch_code`、`wm_sn.sn_code`** | 见下方陷阱 |
| **C** | DB 列计数器 | `ry-erp.wm_barcode_config.current_sequence` | `wm_barcode.barcode_code` | `UPDATE … SET current_sequence=0;` |
| **D** | 产品级序列号规则 | `ry-erp.bd_serial_number_rule.current_seq`+`attr1` | SN/批次/条码（仅手工 API） | `UPDATE … SET current_seq=0, attr1=NULL;` |
| **E** | Redis 设备维修单号 | Redis `mes:eq:repair:no:*` | `eq_repair.repair_no` | `DEL mes:eq:repair:no:*` |

> **⚠️ 机制 B 陷阱**：批次号/序列号的 Redis 序号**种子来自 `SELECT MAX(batch_code)/MAX(sn_code)`**。
> **只删 Redis key 不删数据会从旧最大值继续；只删数据不删 key 48h 内也无效 —— 两边都必须清。**

**机制 C/D 对应 `wm_barcode_config` / `bd_serial_number_rule` 是「保留表 + 重置计数器」，不能 DELETE 整表**（删了编码生成停摆或号段割裂）。

**另有 3 类"无计数器"生成器，删除业务数据后自动归零**：`COUNT(*)+1` 型（`qc_*.*_no`、`pro_sn.sn_code`、`sch_shift.shift_code`）、时间戳/雪花型（`pro_flow_card.card_no`、`gl_voucher.voucher_no`）、无生成器型（`bd_process.process_code`、`bd_unit_of_measure.uom_code`、`bd_material_category.category_code`）。

### 4.3 重置顺序（★ 必须先删数据）

**三条硬证据**：
1. 编码日期段取**生成时的系统日期**（`LocalDateTime.now()`），不是单据日期 —— 数据还在就必然重发同一字符串。
2. 引擎**从不查重**，唯一保护是业务表唯一索引 —— 而 **11 个编码字段根本没有唯一索引**（§7.13），重置后是**静默重复**而非报错。

## 5. 全新生产基础资料重建方案（v2 · 十大类扩展）

### 5.1 设计原则

| 原则 | 说明 |
|---|---|
| **离散型制造** | 多工序、装配型 BOM、层层可追溯。不使用流程行业的配方/联副产品模型 |
| **十大类覆盖** | 按你给定的十大类构建目录，每类 2~5 个产品族 |
| **三层物料结构** | 每个产品族 = 原材料 → 半成品 → 产成品，BOM 逐层向上 |
| **工艺可落地** | 每个产成品配 `bd_routing` + `bd_routing_step`，工序引用 `bd_process` |
| **商城可售** | 每个产成品必须具备：售价、成本价、销售单位、可生成商品图（见 §6） |
| **不复用旧数据** | 仅复用"电动牙刷"这类**成熟工艺模式**（完整 BOM + 多工序 + 固件 + 测试）作为模板，不沿用任何旧记录 |
| **编码引擎生成** | 所有编码走引擎，禁止人工录入（§7.17 的教训） |

### 6.3 商品图生产约束

- **通道**：商汤 `sensenova-u1.5-lite` + `size=1:1` + `quality=2k`
- **⚠️ 水印**：两个模型都会在右下角打固定"日日新 sensenova"水印，**必须用 `script/tools/strip_watermark_batch.py` 去除**（实测有效）
- **⚠️ RPS 限制**：并发提交会 `rps exhausted`（实测 4 并发 → 3 张失败），**必须串行**
- **上传**：`POST /api/admin/upload/image?model=product&pid=0`（multipart 字段名 `multipart`），落 MinIO bucket `shop`
- **数量**：37 个产成品 ×（1 主图 + 3 轮播）≈ **148 张**，串行限速约需数小时

> **建议**：先做十大类各 1~2 个旗舰产品（约 15 个）跑通上架闭环，再批量补齐。

### 6.4 同步架构（沿用已决策方案）

```
ERP (ry-erp)                            nexus-shop (crmeb)
   bd_material / bd_bom / bd_routing
              │
              │  ① 单向主数据同步（低频）
              │     中间表 erp_shop_product_sync
              └──── SnailJob 定时任务 ──────────► ② 建品 + 补 attr_result + 上架
              │
              │  ③ 商品图
              └──── MinIO (bucket: shop) ───────► ④ URL 回填
```

- **主数据同步走中间表 + SnailJob**（已决策）
- **库存不实时同步**：商城库存作为独立可售库存池
- **绝不合并部署**（`com.nexus.common.mq.constant.QueueConstants` FQCN 冲突）

### 6.5 上架链路（源码实测）

```
① POST /api/admin/login {account,pwd}              → token（旧后台桥接，绕开 @ApiEncrypt）
② GET  /api/admin/express/shipping/templates/list  → tempId（现有 id=1 全国包邮）
③ POST /api/admin/upload/image?model=product&pid=0 → 图片 url
④ POST /api/admin/store/product/save               → 写 6 张表；★ 强制 isShow=false 且不返回 ID
⑤ GET  /api/admin/store/product/list?type=2&keywords=<名称> → 反查商品 id
⑥ GET  /api/admin/store/product/putOnShell/{id}    → 真正上架
⑦ 补写 eb_store_product_attr_result                → 否则多规格商品 C 端详情报错
```

**四个必踩的坑**（详见《产成品接入商城售卖方案》）：
1. `attr[]` **必须带 `optionList`**（现有后台页面漏传，提交必失败）
2. `/save` **强制 `isShow=false`**，需二次调 `putOnShell`
3. `/save` **不返回商品 ID**，需按名称反查
4. `tempId`/`cateId` **只做非空校验，不校验存在性** —— 脏数据不报错但下单会炸
