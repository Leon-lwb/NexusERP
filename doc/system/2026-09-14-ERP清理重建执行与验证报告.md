## 九、物料分类「两处菜单数据不一致」的根因与修复（2026-09-14 追加）

### 9.1 现象

「物料管理」菜单左侧的分类树 与「物料分类」菜单的分类列表，查出的分类**不是同一批**：前者已是重建后的新分类，后者仍是重建前的旧分类（个人护理电器 / 整机 / 零部件 / 聚乙烯 / 原木 …）。

### 9.2 根因（两个独立缺陷叠加）

#### 缺陷 1：整表缓存陈旧（主因）

`BdMaterialCategoryServiceImpl.selectList()` 上挂着 **ERP 模块里唯一的「列表级」缓存**：

```java
@Cacheable(cacheNames = CacheNames.BD_CATEGORY_TREE, key = "'list_all'",
    condition = "#bo.categoryCode == null and #bo.categoryName == null and #bo.status == null")
```

两个菜单调的是**同一个** `/erp/bd/category/list`，但传参不同，于是走了两条数据路径：

| 调用方 | 前端传参 | 是否命中缓存 | 实际数据来源 |
|---|---|---|---|
| 物料分类菜单 | `useCategoryTree(proxy, { queryParams: {} })` → 无参 | ✅ 命中 `list_all` | Redis（TTL **30 天**） |
| 物料管理菜单 | `useCategoryTree(proxy)` → 默认 `{status: 1}` | ❌ 条件不满足，绕过缓存 | MySQL 直查 |

只要分类被「应用之外」的方式改过——本次全量重建正是用 SQL 直接跑的——两条路径就会长期分叉。实测 Redis 里是 **53 条旧分类**，库里是 **116 条新分类**。

`@CacheEvict(allEntries = true)` 仅挂在应用自身的增删改方法上，**SQL 级变更无法触发失效**，这是该缓存策略的固有盲区。

#### 缺陷 2：`categoryName` 从未回填（次因）

`BdMaterialServiceImpl` 只调用了 `fillBaseUomName()`，全模块不存在 `fillCategoryName`。`BdMaterialVo.categoryName` 字段声明了（还带 `@ExcelProperty("分类名称")`）却**恒为空**，导致物料侧看不到分类名，也无法与分类树对账。

### 9.3 修复

| 文件 | 改动 |
|---|---|
| `ruoyi-erp/.../bd/service/impl/BdMaterialCategoryServiceImpl.java` | 去掉 `@Cacheable` 与 5 处 `@CacheEvict`，分类树一律直查（该表仅 116 行）。ERP 模块内其余 `@Cacheable` 均按 ID/类型精确缓存，不再存在「带筛选直查、不带筛选读缓存」的双数据源 |
| `ruoyi-erp/.../bd/service/impl/BdMaterialServiceImpl.java` | 新增 `fillRefNames()` / `fillCategoryName()`，在**分页、列表、详情、按分类批量查** 4 个出口统一回填分类名（新增 `BdMaterialCategoryMapper` 注入） |
| Redis | 删除遗留键 `000000:bd_category_tree` 及 Redisson 附属键 |
| 应用 | `mvn -o -pl ruoyi-modules/ruoyi-erp -am compile` 增量编译 → 重启（PID 6232） |

### 9.5 顺带发现（本次未改动）

`MybatisPlusConfig.java:78` 设了 `paginationInnerInterceptor.setOverflow(true)`（注释写"分页合理化"）。
实测：请求第 7 页（`pageSize=50`，共 6 页）**不返回空页，而是回绕返回第 1 页数据**。

这是 RuoYi-Vue-Plus 上游的既定设计，前端 `pagination` 组件自身会钳制页码，正常点击翻页无影响；但**脚本/API 对接时若按"空页即结束"遍历会重复取数**（本次验证脚本就多累计了 50 条）。
此处保留上游行为；若确需改为"超界返回空页"，需评估对所有分页接口的连带影响。

## 十、同类问题扩散排查：字典缓存陈旧导致 5 个 AI 字典返回乱码（2026-09-14 追加）

### 10.1 触发原因

§9 定位到"SQL 级改库 → 缓存不失效"这一根因后，对 ERP 用到的 Redis DB0 做了全面排查。结果发现**同一个根因在字典上又中了一次**。

### 10.2 现象与证据

`ai_model_api_protocol`、`ai_model_capability`、`ai_model_currency`、`ai_model_type`、`ai_provider_type` 这 5 个字典类型，**接口返回的是乱码，而数据库里是正确的 UTF-8**：

| 位置 | `ai_model_currency` 第 1 项 |
|---|---|
| MySQL（`HEX()` 确认为 `E4BABAE6B091E5B881`） | `人民币` ✅ |
| Redis `000000:sys_dict` 缓存值 | `浜烘皯甯` ❌ |
| 重启后接口返回 | `浜烘皯甯` ❌ |

`浜烘皯甯` 正是 `人民币` 被"UTF-8 字节按 GBK 解读"后的典型双重编码形态。

**决定性实验**：单独 `HDEL 000000:sys_dict ai_model_currency` 再取一次接口 —— 立即恢复为 `人民币`。说明乱码来自**缓存里的旧值**，与数据库、代码、连接字符集均无关。

这 5 个类型恰好是本次重建中被修正过标签的字典，其余 222 个类型因为值没变过，"陈旧"与"正确"恰好相等，所以只有这 5 个露馅。

### 10.3 修复

```bash
# 清除字典缓存（DB0），应用会按需从库重建
redis-cli -n 0 DEL 000000:sys_dict
```

同批清理的业务缓存（均为只读穿透缓存，删掉零风险，**未触碰任何登录令牌 / 限流键 / IoT stream**）：

| 键 | 说明 |
|---|---|
| `000000:sys_dict` | 字典数据（本次乱码来源） |
| `000000:sys_config` | 参数配置 |
| `000000:sys_dept` / `000000:sys_dept_and_child` / `000000:sys_role_custom` | 部门与数据权限 |
| `000000:sys_user_name` / `000000:sys_nickname` | 用户昵称缓存 |
| `000000:sys_oss` / `global:sys_oss_config` / `global:sys_oss:default_config` | OSS 配置 |
| `global:sys_client` / `global:sys_tenant` | 客户端与租户 |

### 10.4 验证结果

|---|---|

| 字典类型名乱码 | **0** |

## 十一、物料成本/重量/体积补齐 + 分类修正 + 成本卷积打通（2026-09-14 追加）

### 11.1 起因

重建后的 270 条物料里，**成本、重量、体积几乎全空**：132 条原材料与 101 条半成品的
`standard_cost / reference_price / weight / volume` 全是 0，37 条产成品也缺重量体积。
`BdBomServiceImpl.materialCost()` 取叶子物料标准成本，叶子全是 0，**BOM 成本卷积结果恒为 0**。

### 11.2 根因：三处「一刀切」

排查过程中发现，光补单价并不能得到可用成本，背后还有三处「一套值套所有件」的生成缺陷：

| # | 缺陷 | 证据 |
|---|---|---|
| 1 | **原材料单价/重量/体积从未赋值** | `add_material(..., 0.0, 0.0)` 就地传 0，共 132 条 |
| 2 | **`bd_bom.routing_id` 全为 NULL** | 137 张 BOM **0 张**关联工艺路线 → `costRollup` 取不到工序，工序成本恒为 0 |
| 3 | **标准工时是工序级默认值，被逐件套用** | 每步成本 `工时 × (人工50×2人 + 机器100×1台) = 工时×200`，导致一个售价 45 元的螺栓组套算出 **¥770 工序成本** |

外加两处数据错误：

- **分类误挂**：`raw_leaf()` 的兜底分支 `return "CH_LUBE"` 把匹配不上的物料统统塞进「润滑剂」，
  实测 **45 条**（伺服电机 400W、谐波减速器 CSF-20、单晶硅电池片、镀膜钢化玻璃、热敏打印头、
  玻璃镜头、国标充电枪线…）。半成品侧还有 24 条误挂（如 HT250 铸造件挂在注塑件下）。
- **半成品 BOM 与分类脱钩**：半成品 BOM 的「模板行」由分类决定，分类一改模板就错。典型：
  `齿轮箱体 精加工`（HT250 铸造件）的 BOM 是「合金钢棒料 40Cr + 切削液」。
- **MES MBOM 挂错 BOM**：生成器里 `fg_bom_id = bom_id` 在生成完各半成品 BOM 之后才取值，
  拿到的是**最后一个半成品的 BOM**。实测 `mes_mbom` **37/37 全部指向半成品**，0 条指向产成品。

### 11.3 修复

| 类别 | 内容 |
|---|---|
| 新增分类 | **29 个节点**：新二级「外购件与机电」+ 轴承 / 直线传动件 / 链条与带 / 电机 / 减速装置 / 油封 / 机械密封 / 橡胶密封件 / 光学镜头 / 玻璃件 / 光伏电池片 / 光伏辅材 / 模具导向件 / 模具冷却件 / 过滤耗材 / 纺织软装 / 其他辅材 / 外购结构件 / 外购五金件，以及 模块与器件 / 线束线缆 / 磁性材料 / 表面处理药剂 / 电子化学品 / 塑料合金 / TPU / 橡胶成型件 / 软件与固件 |
| 分类修正 | 原材料 **66 条**、半成品 **24 条**（分类树 116 → **151**，`润滑剂` 从 45 条收敛到 **4 条**） |
| BOM 模板换行 | 24 张半成品 BOM 删 53 行、增 47 行，模板与分类对齐（`SM_CAST`→铸铁/生铁、`SM_RUBBER`→硅胶/硫化剂…） |
| 原材料成本 | 132 条按 `raw_table.py`（采购数据表）回填 `standard_cost`、`reference_price`（= 成本×1.08）、重量、体积 |
| **目标成本标定** | 按产品行业类别给定占比（材料 42~72%、工序 10~23%），缩放 BOM 用量与标准工时。**缩小方向全行等比缩；放大方向只放大模板占位行**——产品专属料（机床床身 1250kg 铸铁、机架 42kg 型钢）已按件定过量，放大它们会得到物理上荒唐的值。缩放系数区间 [0.02, 30]，命中 **32/37** |
| 半成品/产成品卷积 | `standard_cost` = Σ(叶子料 累计用量 × 标准成本) + Σ(工序 工时 × 费率)；`weight`/`volume` 同步卷积 |
| BOM↔工艺路线 | 37 张产成品 BOM 关联到对应 `bd_routing`，工序成本可算 |
| MES MBOM 修正 | `mes_mbom.bom_id` 按 `routing_id → bd_routing.material_id → bd_bom.parent_material_id` 重挂，**37/37 指向产成品** |

### 11.5 顺带修复的 DDL 缺陷

`bd_material.volume` 原为 `decimal(12,4)`（注释 m³），**最小只能表达 0.0001 m³ = 100 cm³**，
螺栓、轴承、芯片这类小件的体积在字段上无法表达、必然落 0（实测 46 条为 0）。
放宽为 `decimal(18,9)`（最小 1 mm³，最大 9.99 亿 m³），Java 侧为 `BigDecimal`，无代码影响。
已更新主脚本 `script/sql/ry-erp.sql` 并登记《数据库增量变更记录.md》。
