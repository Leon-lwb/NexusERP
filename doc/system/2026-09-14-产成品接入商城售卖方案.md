# 产成品接入商城售卖方案

> 编制日期：2026-09-14
> 目标：把 Nexus-ERP 的产成品作为商品接入 nexus-shop（CRMEB）商城售卖
> 范围：① 物料/BOM 不合格数据清理 ② 需新建的产成品 ③ 商城上架方案 ④ 商汤生图方案
> 本文所有"实测"结论均来自本机真实查询（MySQL `root/root`）与只读源码分析，未执行任何写操作

---

## 0. 结论先行

| # | 事项 | 结论 |
|---|---|---|
| 1 | 物料/BOM 清理 | ERP 有 **52 个物料 / 15 个 BOM**。**5 个物料可物理删除（零引用）**，4 个 BOM 是已软删的脏数据可物理删除（**但需先解 MES 引用**），另有 **23/52 物料计量单位错误、"克"被用作减速机/电机的单位** 等系统性问题 |
| 2 | 需新建产成品 | 现有 9 个"成品"中**只有 4 个是真产品**，其余是测试料/错挂/重复。建议分两步：**先做商城侧多规格变体（轻量、立刻见效）**，再按产品族补 ERP 产成品 |
| 3 | 商城上架 | 接口链路已完全摸清：`POST /api/admin/store/product/save` → `GET putOnShell/{id}`。**存在 4 个必踩的坑**，其中"后台页面当前提交必定失败"是已确认缺陷 |
| 4 | 商汤生图 | **通道可用**（已实测出图）。但**两个模型都会打"日日新 sensenova"水印**，且 `u1-fast` 会忽略尺寸参数并自行添加标注文字。**水印已实测可修复**（OpenCV 修复，非破坏性） |

**最大风险**：`site_url` 配置是垃圾值 `https://111111`；商城与 ERP **都默认占用 8080 端口**（当前 ERP 在跑，商城起不来）。

**MES 跨库引用（硬阻断点）：**

```
ry-mes.mes_mbom.mbom_id=2  →  bom_id = 1  →  该 BOM del_flag=1（已删）
```
即 MES 里有一条 ACTIVE 的制造 BOM 指向一个**已被删除**的 ERP BOM。删除 bom_id=1 前必须先修 MES。

## 3. 需求②：需新建的产成品

### 3.1 问题诊断

现有 9 个"成品"里真正能卖的只有 **4 个**（自行车、电动牙刷 TB-100、简易金属工具架、减速机JZQ-350），而其中：
- 电动牙刷 TB-100 **连库存行都没有**（工单 `SCGD202608230001` 计划 300 台、完成 0）
- 只有 RACK-001 有 15 套库存，**且 `frozen_flag=1` 全部冻结**

所以"产品种类不够"是**真实且严重**的。

### 3.2 两条解法（建议先做 A，再做 B）

#### 方案 A：商城侧多规格变体（轻量，零 ERP 改动，立刻见效）★推荐先做

ERP 的 `bd_material` 是**单层物料主数据**，没有"颜色/尺寸"这类销售属性概念；而商城 `eb_store_product` 原生支持 `spec_type=1` 多规格。**用商城的多规格能力把 4 个真产品裂变成十几个 SKU**，是投入产出比最高的做法：

| ERP 产成品 | 建议商城规格 | 变体数 |
|---|---|---|
| 电动牙刷 TB-100 | 颜色：白色 / 粉色 / 蓝色 | 3 |
| 简易金属工具架 RACK-001 | 层数：三层 / 四层 / 五层 | 3 |
| 自行车 IF20251110001 | 车架尺寸：S(1.2m) / M(1.5m) / L(1.8m) | 3 |
| 减速机 JZQ-350 | 无（工业品单规格） | 1 |

→ **4 个商品裂变为 10 个售卖 SKU**，无需新建任何 ERP 产成品、无需新 BOM、无需新工艺路线。

#### 方案 B：ERP 侧新建产成品（重型，需 BOM + 工艺 + 工装）

按现有半成品/单元能力推演，**建议的新建清单**（产品族已成型，可直接补）：

| 产品族 | 已有基础 | 建议新建产成品 | 依据 |
|---|---|---|---|
| **个人护理电器** | TB-100 电动牙刷、主控板 PCBA-TB100（5 子件 BOM）、6 道工序（组装/烧录/功能测试/防水/质检/包装）、TB 专属工位 GZZ0018~21、独立仓 WH006 | ① 电动牙刷 TB-200（儿童款）<br>② 电动牙刷 TB-100 Pro（蓝牙升级款）<br>③ 冲牙器 FC-100 | 数据最新最完整，工位/仓库/固件体系已就绪，**最容易复制** |
| **智能网关** | 智能网关PCBA GW-1000（有 BOM、有刷写工艺 RT-FLASH-GW、10 件库存） | ④ **智能网关整机 GW-1000**（当前只有 PCBA，缺整机成品） | 有半成品无成品，链路断在最后一步 |
| **金属工具架** | RACK-001、侧板组件 RACK-SIDE、连接件包 RACK-FIT、RT-RACK-001 工艺 | ⑤ RACK-002 五层工具架<br>⑥ RACK-003 带轮工具车 | 钣金/焊接/装配工艺已跑通，有 16 条销售记录 |
| **自行车** | 车架/车轮/车把/辐条/轮圈/轮胎/把管/把套全套半成品 + BOM | ⑦ 自行车 电动助力款 | 零部件体系最完整，但数据较旧（2025-11） |

> ⚠️ **建议新建数量与型号需业务决策**。上表的依据是 ERP 里"已具备但未闭环"的能力，不代表市场选择。

### 3.3 新建产成品的标准工序

每新增一个 ERP 产成品，需同步补齐（否则不满足上架条件）：

1. `bd_material` 主数据（**类型=3、分类正确、单位正确、`reference_price` 非零**）
2. `bd_bom` + `bd_bom_detail`（父项成品、子项半成品/原材料，`is_current=1`、`status=1`、无自引用、无重复子件）
3. `bd_routing` + `bd_routing_step`（工艺路线与工序）
4. `ry-mes.mes_mbom`（关联上述 BOM + 工艺路线，`mbom_status='ACTIVE'`）
5. `so_price_list_line`（价目表行 —— 该表当前为空，需先建 `so_price_list` 头）

## 4. 需求③：商城上架方案

### 4.1 上架技术链路（源码实测）

```
① 认证   POST /api/admin/login  {account, pwd}      → token（走旧后台桥接，绕开 @ApiEncrypt）
         后续请求带 Authori-zation: <token>
② 前置   GET  /api/admin/express/shipping/templates/list  → tempId（现有 id=1「全国包邮」）
         GET  /api/admin/category/list/tree?type=1&status=-1 → cateId（需先建"产成品"分类）
③ 上图   POST /api/admin/upload/image?model=product&pid=0
         multipart 字段名 = multipart（不是 file！）→ 返回 url
④ 建品   POST /api/admin/store/product/save  (JSON)  → 一个事务写 6 张表
⑤ 反查   GET  /api/admin/store/product/list?type=2&keywords=<名称>  → 取回商品 id
⑥ 上架   GET  /api/admin/store/product/putOnShell/{id}
```

**建品事务写入的 6 张表**：
`eb_store_product`(1) → `eb_store_product_attr`(N) → `eb_store_product_attr_option`(Σ规格值) → `eb_store_product_attr_value`(N) → `eb_store_product_description`(1) → 可选 `eb_store_product_coupon`

### 4.2 四个必踩的坑（全部已定位到源码行）

| # | 坑 | 后果 | 规避 |
|---|---|---|---|
| **1** | `attr[]` 必须带 `optionList`，但**现有后台页面 `creatStore.vue` 恰好不传** | 后端抛 `规格属性值不能为空`。**当前后台"提交"按钮实际是坏的** | 我们的脚本必须显式构造 `optionList` |
| **2** | `save()` 内部**强制 `isShow=false`**，与请求参数无关 | 调完 `/save` 商品仍是"未上架" | 必须再调 `putOnShell/{id}` |
| **3** | `/save` 返回 `CommonResult<String>`，**不返回商品 ID** | 无法直接拿到 id 去上架 | 用 `/list?type=2&keywords=<名称>` 反查 |
| **4** | `tempId` / `cateId` **只做 Bean Validation，不校验存在性** | 脏数据不报错，但下单算运费时炸 | 脚本侧自己做存在性校验 |

**附加注意**：
- `content` 传 `null` 会 NPE（`request.getContent().length()`）→ 必须传 `""`
- `price` / `stock` **不是入参**，由 `attrValue` 派生：`price`=最小 SKU 价，`stock`=ΣSKU 库存
- `isPostage` DTO 里没有该字段 → 落 DB 默认 `0`（不包邮）
- 接口**无幂等**（无 sku/条码唯一约束）→ 重推会重复建品，脚本必须先按 `storeName` 查重
- 多规格商品建完后 `eb_store_product_attr_result` 仍为空 → C 端详情会抛 `未找到对应属性值`，**必须额外补写该表**

### 4.3 集成架构选型（4 条路线，已实测可行性）

| 方式 | 可行性 | 关键阻塞 |
|---|---|---|
| ① 数据同库直写 | ✅ 可行但**不推荐** | 商城扣库存走 `version` 乐观锁（`id+type+version`），ERP 外部直写会**绕过乐观锁造成丢失更新**；且 `eb_store_product.stock` 是 `SUM(attr_value.stock)` 的冗余，须双写 |
| ② 共享 MQ 异步同步 | ✅ 可行（需改造） | `/erp` 与 `/shop` vhost 物理隔离，跨 vhost 无法直接投递，需 shovel/federation 或第二个 ConnectionFactory |
| ③ REST-API 调用 | ✅ 可行 | 8080 端口冲突；无 SSO（JWT 密钥不同）；`api-decrypt` 默认开启 |
| ④ 中间表 + 定时任务 | ✅ **最可行、耦合最低** | SnailJob 端口/namespace 撞车；需新增数据源；分钟级延迟 |

### 4.4 推荐架构

```
ERP (ry-erp)                        nexus-shop (crmeb)
    │                                      │
    │  ① 单向主数据同步（低频、可容忍延迟）
    │     中间表 erp_shop_product_sync      │
    └──── SnailJob 定时任务 ───────────────►│ 消费：建品 + 补 attr_result + 上架
                                           │
    │  ② 商品图片
    └──── MinIO (bucket: shop) ───────────►│ 图片 URL 写回
```

- **主数据同步走 ④**（商品/分类/价格，低频，天然容忍延迟）
- **图片走 MinIO 直传**（同一 MinIO 服务，商城已有 `image` 通道）
- **库存不做实时同步**：商城库存作为**独立可售库存池**维护（ERP 库存现状也支撑不了实时：4 个真产品中 3 个零库存）。这是本方案的重要简化决策。
- **绝不合并部署**（`QueueConstants` FQCN 冲突）

## 5. 需求④：商汤生图方案

### 5.1 已验证的能力

| 项 | `sensenova-u1.5-lite` | `sensenova-u1-fast` |
|---|---|---|
| 出图 | ✅ 成功 | ✅ 成功 |
| `size` 参数 | 接受宽高比（`1:1`）→ 实测输出 **1024×1024** | 接受**像素**（`2048x2048` 报错，须用 `1664x2496`/`2048x2048`/`2752x1536` 等枚举） |
| 实际输出尺寸 | 与请求一致 | **忽略请求**：要 2048×2048，实得 **2752×1536** |
| 附带文字 | 无 | **自动添加尺寸标注**（"600mm/800mm"） |
| 水印 | ❌ **有**："日日新 sensenova"（右下角） | ❌ **有** |
| 并发限制 | ❌ **有 RPS 限制**：4 个请求并发发出 → 3 个返回 `rps exhausted` 失败 | 同左 |

> **⚠️ 实测踩坑：`rps exhausted`。** 一次性并发提交 4 个生图任务，只有 1 个成功，其余 3 个报 `rps exhausted`。
> **因此批处理流水线必须串行/限速，不能并发 fan-out。** 串行重试后 4 张全部成功。

### 5.2 水印问题与解决方案（已实测）

**问题**：两个模型都在**固定位置**叠加半透明水印。实测 1024×1024 输出中水印包围盒为
`x: 0.797→0.971, y: 0.908→0.971`（归一化），即右下角约 17%×6% 区域。

**解决方案（已验证可行）**：用 OpenCV 对该矩形做 inpaint 修复。产品图多为纯色背景，修复效果干净。

```
原图（含水印） → cv2.inpaint(mask=水印矩形+6px 安全边距, INPAINT_TELEA) → 干净图
```

实测结果：水印完全消除，背景无缝，**无可见修复痕迹**。修复脚本见 `script/tools/strip_watermark_batch.py`。

**备选方案对比**：

| 方案 | 评价 |
|---|---|
| OpenCV inpaint 修复 ★推荐 | 已实测有效；纯本地、零成本、可批处理 |
| 裁剪后重新填充 | 会改变构图，产品可能被裁到 |
| 换付费渠道/模型 | 需用户提供无 Free 水印的 API 密钥 |
| `edit_image` 图生图去水印 | 未验证，且图生图可能再次打水印 |
| 接受水印上架 | ❌ 商品图带第三方 AI 水印不可接受 |
