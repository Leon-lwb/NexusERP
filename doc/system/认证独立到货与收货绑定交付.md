- Certified Draft 在原事务/物料锁内验证同租户已批准通知、原 PO 行/供应商/物料/单位、已收+未完成承诺+本次数量。头保存原 notice ID/编号、行保存 notice_line_id，永久 command 同时保存成对引用；非空引用追加 hash 独立命名域。null 引用不追加任何摘要字节，原 10 参数 Request 构造器保留。
- Posting 保留全部条款、IQC 原出生证据、库存/数量/成本门禁，同原 ERP 事务核头/行/永久 command 引用并累计 `received_qty`；未满 `PARTIAL_RECEIVED`、全部满 `FINISHED`，条件更新不超过声明量。已过账重放提前返回，不能重复累计。旧无通知 Line 文本/指纹格式保留。

## C1/I1 限定修复（独立审查后）

- C1：回调只把实例/定义/事件状态当待核线索；新增内部只读 `WmCertifiedArrivalWorkflowPort` 和 ERP 包内 `WmCertifiedArrivalWorkflowReader`。读取 master 的真实业务关联、引擎历史/活动实例、必要源变量和实际待办数，不信被错配任务污染的关联 `pass`。启动时 `noticeCode` 是此契约的 businessCode，并在 ERP 持锁后与原通知编号再次比较；`businessKey` 必须不可变地等于该通知 ID。
- 只有本租户、本通知、本定义实际结束，无运行实例/剩余待办、历史最终状态为 completed 且无删除原因才是 APPROVED；仍运行仅为 APPROVING，终止/撤回不视为批准，缺历史/源变量或身份冲突拒绝。其他合法任务的 pass 不得批准尚未完成的目标通知，重复 synchronize 也不得按受污染的关联状态升级。
- I1：首次 doing 的 ERP 写入失败，后续自身合法流程完成时，回调或 synchronize 可将 DRAFT 幂等收敛到 APPROVED；真实流程未完成、编号不符或来源缺失，不能借此批准任意草稿。重复同步不建普通收货、不改数量。
- 读取器仅 `@DS("master")` + REQUIRES_NEW/RR/readOnly；master 快照读取结束并清理资源后，才进入原 ERP 独占执行器。master 回调仍延迟至 afterCommit 并隔离旧资源上下文；没有用 master 事务中的 DS 切换冒充 ERP 事务。
- 本轮不改公共流程/任务发布器、原权限/候选人/签章门禁或 API/DTO，不新增迁移；legacy hash、数量无损、原库存/来源/额度及 ERP 事务守卫不变。

## 精确接口与 DTO

以下是草案，不是实际提交。所有 ID、版本、Q、计划/实到日及流程须主线程从新真实业务获取；不得复用已完成原收货/单据补历史。雪花 ID 保持字符串传递，不经 JS Number 转换。

1. `POST /erp/wm/arrivalnotice/certified`，权限 `wm:arrivalnotice:add`：

```js
// 变量必须用真实新订单来源替换，quantity 不凭空增加。
({ requestKey: NOTICE_KEY, orderId: O, expectedOrderVersion: V,
   purchaseLineId: P, quantity: Q, noticeName: '独立到货通知',
   arrivalDate: PLANNED_DATE, remark: '真实来源说明' })
```

`Request` 字段：requestKey（1–128 ASCII 字符）、orderId/purchaseLineId（正 ID）、expectedOrderVersion（>0）、quantity（精确正数）、noticeName（1–255）、arrivalDate（yyyy-MM-dd，计划日可未来）、remark（可空≤500）。不接受客户端供应商/单位/租户/人员/批准标志作为来源。返回 noticeId=N、noticeLineId=NL、noticeCode、status=DRAFT、replayed。

2. `POST /erp/wm/arrivalnotice/certified/{N}/submit?selectFlowId=F`，权限 `wm:arrivalnotice:submit`；草稿/驳回→APPROVING→APPROVED。
3. 流程实例可沿 `GET /erp/wm/arrivalnotice/{N}/proc`（原 query 权限）查询；正常办理：`GET /workflow/process/todoList`，按需 `POST /workflow/task/claim`，`POST /workflow/task/complete`。DTO 为真实 taskId、procInsId、dataId=N、comment、variables（实际节点表单/签章），以及节点所需的实际下一办理人字段。不得假设流程/人员/密码或空 variables 可用。
4. master 已提交而 ERP 回调失败时：`POST /erp/wm/arrivalnotice/certified/{N}/synchronize`，同 submit 权限；只从自身真实关联和引擎状态重同步：核 tenant、回调服务、定义/实例、不可变 businessKey、源 dataId/noticeId 与原 noticeCode，不接收批准 DTO；仅有完整自身正常完成证明时允许丢失 doing 的 DRAFT 恢复为 APPROVED。不是跨库回滚/历史认证补写。
5. `POST /erp/wm/receive/certified/draft`，权限 `wm:receive:add`：

```js
({ requestKey: RECEIVE_KEY, orderId: O, expectedOrderVersion: CURRENT_V,
   purchaseLineId: P, quantity: ACTUAL_Q,
   warehouseId: W, areaId: A, locationId: L,
   actualArrivalDate: ACTUAL_DATE, remark: NOTE,
   noticeId: N, noticeLineId: NL })
```

原 10 字段语义不变，新增 noticeId/noticeLineId 可空但必须同时为空或成对正 ID；不能用旧 requestKey 换通知。实际到货日仍不得未来，原仓储/单位/订单余额门禁保持。返回原 receiveId=H、lineId、状态 DRAFT_CREATED。
6. 原真实批次/分配、收货审批保持：`POST /erp/wm/batch/createBatch` / `POST /erp/wm/detail`，`POST /erp/wm/receive/{H}/submit?selectFlowId=F`，通过后进入 APPROVED。批次来源、效期、全部明细数量守恒及权限不能省略；没有准备实际 payload 或运行验收。
7. 原 IQC/Birth/evidence 路径不修改，必须实际完成原单位合格证据；然后 `POST /erp/wm/receive/certified/shelf/{H}`（wm:receive:shelf，SHELVED）、`POST /erp/wm/receive/certified/execute/{H}`（wm:receive:execute，FINISHED）。只有 execute 的首次实际事务才累计通知；审批/上架/重放均不累计。

## nullable 迁移与 MySQL 5.7 重放

- `script/sql/ry-erp.sql` 仅空库安装。存量库**不能重导**含 DROP 的主脚本。
- 独立增量：`script/sql/update/certified-arrival-receipt-link.sql`，只选已核 ERP 库；原通知头/行、收货头/行及 wm_certified_receive_command 须为 b4 适用基线/InnoDB，已有 received_qty 必须在位。先备份/维护窗口，核 CREATE/ALTER/CREATE ROUTINE 权限。
- 新空命令表；只追加收货行 notice_line_id、收货 command notice_id/notice_line_id 为有符号 nullable BIGINT、默认 NULL，附查询索引。原头已有 notice_id/notice_code 不重建；不做历史 DML、hash 重算、单位/数量转型或认证补写。
- information_schema 条件追加，无 8.0 专用的重复列句法；已有引用类型/可空/默认值或索引不匹配即 SIGNAL。DDL 隐式提交，中途失败可重放已成功追加，不代表整组原子。新命令表如已存在，须人工核对完整定义；IF NOT EXISTS 不是签发或全 schema 匹配证明。
- 新安装/增量共同保留现有通知 DOUBLE(12,2)。此入口对 DOUBLE **仅接受范围内无损整数**；非整数/超原生精度明确拒绝，绝不默默取整/CAST 成伪精确。合格 DECIMAL 结构按 precision/scale 检查。小数量物料若需支持，须另行无损迁移审查，本次不自动改历史列。
- 先 DDL、再全节点部署新版本，之后才开启新入口；旧节点不可过账新绑定收货，否则缺通知累计且新重放指纹不匹配。

## 交付限制与审查项

- 本轮仅封住认证通知投影对错配事件的信任，不宣称已修复所有通用任务 dataId 父绑定；公共流程发布器未改。引擎历史须保留实例 tenant/businessKey、必要源变量及实际最终状态，缺失时关闭式拒绝，不能 SQL 补批准或删除/重建已批准实例恢复。

- **认证采购退货未覆盖**：普通 `PuPurchaseReturnServiceImpl` 的 requireLegacyReturn* 保持，不能把本次到货接线当成退货支持；没有扩写退货。
- 不改 plus-ui/MES/IPQC/Station；只给接口与 DTO，人工流程模板/候选人/签章、实际 UI、真机或生产验收未验证。
- 新入口是单行通知，只对真实已批准认证 PO 行建立声明；主线程负责新真实 MRP/需求/采购 quota 和正常原物料、实际调用，不允许复用原链补历史。
- 未执行 MySQL 5.7 迁移、真实 master→ERP 回调/故障恢复、服务或数据库并发；以上限制需主线程部署前审查。收到 master 已提交但 ERP 未同步的错误，应核实际流程后 synchronize，不能假称跨库回滚。
- source/条款/库存/额度门禁未放宽，数量不足/结构不匹配失败关闭；暂无独立第二 Agent 审查，本交付经过本地聚焦自审，主线程统一复核整合。
