# Nexus-ERP 临时服务器迁移方案与执行计划

> 版本：v1.0
> 状态：已获用户批准并执行；2026-10-12 新机部署、Windows 本地 3306 数据恢复及域名切换已完成，收尾进度见文末执行记录
> 创建日期：2026-10-12
> 调查环境：两台 Linux 服务器、当前 ERP 工作区及相邻 Vision 工作区
> 审批边界：用户明确要求先审查方案，再执行关停与部署

> **For agentic workers:** 获批后使用 `executing-plans` 按批准的范围逐项执行，保留复核证据；步骤使用复选框跟踪。本方案不授权访问第三台服务器、修改第三方数据库或自动提交/推送。

## 本轮已确定的部署方向

以下方向来自 2026-10-12 的用户补充要求，写入方案但尚未获得执行批准：

- **MinIO 留在旧服务器。** 新服务器不部署 MinIO、不搬运对象数据；旧服务器保留 `nexus-minio` 运行，新 ERP 通过 `http://159.75.14.226:9005` 访问。旧服务器其余 Nexus 容器在切换完成后停止。
- **MinIO 延迟可以接受，但附件功能仍需带权限验收。** 新服务器到旧 MinIO 的 10 次健康检查全部返回 200，连接耗时中位数约 2.4 ms，请求总耗时中位数约 5.2 ms，最大约 8.9 ms。现有 `sys_oss` URL 直接匿名请求返回 403，说明这组 URL 不能作为匿名下载基准；上线前必须通过应用的授权上传、下载或签名 URL 流程抽样验证真实附件。
- **Vision 使用最新工作区版本。** 保留 `nexus-vision-service` 当前工作区修改，构建 CPU 镜像，`GPU_IDX=-1`、`UVICORN_WORKERS=1`、`OMP_NUM_THREADS=2`，并将 OpenBLAS / MKL 线程限制为 1；不使用当前 Dockerfile 中的 NVIDIA 设备预约和 GPU 运行库。
- **Milvus 不部署。** 运行覆盖将向量存储设置为 `inmemory`，避免应用尝试连接不存在的 19530 端口；知识向量只存在进程内，服务重启后会丢失。本次不把知识库 / RAG 持久化作为上线验收项。
- **扩展服务使用域名。** Monitor Admin 的客户端 URL 使用 `http://nexuserp.website/admin`，SnailJob 客户端的 server host 使用 `nexuserp.website`、端口仍为 17888。旧 IP 保留在配置注释和回滚记录中；SnailJob 的 17888 是独立 RPC 端口，域名不能替代端口放行，也不能只依赖 Nginx 的 80/443。
- **ERP 增加内存。** 新机取消 MinIO 预算后，将相同的 384 MiB 加给 ERP 主服务，ERP 容器上限从 1,536 MiB 调整为 1,920 MiB；新机总容器预算仍控制在 6,080 MiB。


**Goal:** 将 Nexus-ERP 与扩展服务迁移到临时服务器，保留旧服务器 MinIO 作为共享对象存储，核实资源余量，并在验收后关停旧服务器除 MinIO 外的 Nexus Docker 容器。

**Architecture:** 新机运行 ERP、数据库、Redis、RabbitMQ、Nginx、最新 Vision CPU 单 worker、Monitor Admin 与 SnailJob Server；MinIO 保留在旧服务器，通过旧 IP 提供对象存储。Milvus 本次不部署，ERP 以无 Milvus 模式运行并明确 RAG 向量不持久化；容器使用明确的内存上限。

**Tech Stack:** Docker Engine / Compose、Java 17、Vue 前端 / Nginx、MySQL 5.7.44、Redis 7.2.8、RabbitMQ、MinIO、SnailJob 1.9.0、Spring Boot Admin 3.5.6、Python 3.10 CPU Vision。

## 2. 内存结论与本轮资源预算

**结论：新机是 4 核、约 7.44 GiB 可用物理内存，按本轮方向可以承载 8 个新机容器；MinIO 留在旧机，Milvus 不部署。必须使用资源上限、最新 Vision CPU 单 worker，并通过完整预热和低并发验证。**

本轮不把旧 MinIO 的内存计入新机；旧机只保留 MinIO 数据与服务。新机预算把原 MinIO 的 384 MiB 加到 ERP 主服务，其他服务预算保持不变。

| 服务 | 容器内存上限 | JVM 堆 / 资源策略 |
|---|---:|---|
| ERP 主服务 | 1,920 MiB | 最大堆先设 1,024 MiB；给非堆、线程、直接内存留空间 |
| Vision 最新版 | 1,536 MiB | CPU；1 worker；GPU_IDX=-1；OMP=2；OpenBLAS / MKL=1；视频并发=1 |
| MySQL | 768 MiB | 缓冲池初始 256 MiB；连接上限与连接池总预算核对后设定 |
| Redis | 128 MiB | maxmemory 初始 64 MiB；保持 noeviction；预留 AOF / fork 开销 |
| RabbitMQ | 384 MiB | 设置绝对内存告警水位 256 MiB，预留额外开销 |
| SnailJob Server | 768 MiB | 最大堆初始 384 MiB；连接池 minimum-idle=2、maximum=8 |
| Monitor Admin | 512 MiB | 最大堆初始 256 MiB |
| Nginx | 64 MiB | 前端、API 与 SSE 代理 |
| **新机容器上限合计** | **6,080 MiB，约 5.94 GiB** | MinIO 不在新机运行 |
| **操作系统与缓存剩余预算** | **约 1,538 MiB，1.50 GiB** | 其中含当前约 655 MiB 系统占用 |

- 部署完成后读取 `HostConfig.Memory` 确认硬上限；同时验证进程/JVM限制。
- ERP 增加的 384 MiB 只用于主服务，不把所有增加空间一次性分配给堆；根据预热后的 RSS、非堆和线程使用量再决定是否微调。
- Vision 构建必须使用 CPU torch / onnxruntime，移除 NVIDIA 设备预约与 CUDA 运行库；源码工作区的未提交修改需明确纳入发布清单。
- 最新版 Vision 会预加载 YOLO、OCR、人脸和活体模型。必须完整预热后测量，旧镜像约 404 MiB 的快照不能替代新版内存测试。
- 如果 Vision 超过 1.5 GiB 或整机无法保持放行余量，暂停 DNS 放行，改为增加新机内存或拆分服务；不通过继续增加 Swap 伪造可用容量。
- MinIO 旧机当前约 142 MiB 的容器内存不占用新机预算；旧机停掉其他容器后应单独监控 MinIO、宿主机可用内存和 9005 端口。

## 3. 目标布局与配置

拟在新机使用以下路径，均在审批后创建：

| 路径 | 用途 |
|---|---|
| /nexus/deploy/compose.yml | 合并后的临时服务器编排，固定镜像版本或 ID |
| /nexus/deploy/.env | 仅部署账号/root 可读的运行参数与已有密钥引用 |
| /nexus/deploy/config/ | 生产配置覆盖、受保护的 secret 配置来源 |
| /nexus/releases/ | ERP / 扩展服务 / Vision 所选发布产物与清单 |
| /nexus/backups/2026-10-12/ | 受保护的备份和校验清单；不进入 Nginx 静态目录 |
| /docker/mysql/data | 新机数据库持久化 |
| /docker/redis/data | AOF / RDB 持久化；另行保留旧匿名卷 |
| /docker/rabbitmq/data | 消息队列持久化 |
| 旧服务器 `/docker/minio/data` | 业务附件对象；新机不创建此目录 |
| /docker/nginx/ | 前端、代理、证书、日志 |
| /docker/vision/models | 所选版本的必要推理模型与场景配置 |
| /docker/server、/docker/monitor、/docker/snailjob | 日志与服务所需运行目录 |

新机基础服务和扩展服务使用同一 Docker 网络，各服务优先通过内部名称访问。对外入口为 Nginx 80 / 443；保留实际使用的 MQTT 1883 / WebSocket 8083 设备通道。5001、数据库、Redis、MQ 管理、9090、8800、28080 等优先内部访问；SnailJob 的 17888 需要作为独立 RPC 端口放行。MinIO 不加入新机网络，ERP 通过旧服务器 `159.75.14.226:9005` 访问。

配置调整范围：

1. 保留指定 prod / secret 配置的真实值与前后端 API 加密一致性，用部署覆盖将四个业务数据库、Redis、RabbitMQ、Vision 改为新网络内的服务；MinIO endpoint 保持为旧服务器 `159.75.14.226:9005`。
2. Monitor Admin 客户端 URL 使用 `http://nexuserp.website/admin`；旧的 `117.72.190.225:9090` 仅写入注释和回滚记录。域名切换前若需预启动新机，使用临时 hosts 解析或内部地址做验证，DNS 生效后再以域名作为正式配置。
3. SnailJob 客户端 `server.host` 使用 `nexuserp.website`、端口仍为 17888；旧的 `117.72.190.225:17888` 仅写入注释和回滚记录。17888 是独立 RPC 端口，必须在新机安全组 / 防火墙上放行；Nginx 的 80/443 代理不能替代它。
4. SnailJob Server 的数据库必须使用最终确认的数据源，不能沿用 `81.68.78.136` 默认值；本次只把客户端连接地址改为域名，不假定第三台服务器数据库已迁移。
5. 维持 `prod` namespace、group、token 与版本匹配；切换时核对客户端注册地址和执行端口，避免旧新服务同时消费或执行任务。
6. Nginx 保留 `/prod-api/`、SSE 的长连接与关闭缓冲行为，`/admin/`、`/snail-job/` 改到新机内部实例。
7. 新 HTTPS 证书纳入上线准备；签发方式取决于 DNSPod 操作权限。证书和私钥留在服务器受保护目录。
8. 附件继续使用旧 MinIO endpoint，不做对象数据搬迁，不修改当前 18 条旧 IP URL；先验证应用授权上传、下载或签名 URL。若未来要释放旧机，再另立 MinIO 迁移计划。
9. 在 prod 覆盖中将 `nexus.ai.vector-store.type` 设置为 `inmemory`，不启动或连接 Milvus；必须把知识向量重启丢失和 RAG 未持久化写入运行说明。
10. 不把完整训练数据集搬到 49 GB 系统盘；只迁移最新 Vision 实际推理权重、场景配置及业务必要持久化文件。

## 4. 数据与版本保护

### 4.1 数据库

- 迁移全部 5 个数据库及实际使用的账号权限；同版本 MySQL 5.7.44，镜像基线保持一致。
- 业务停止写入后，用 `mysqldump` 的事务一致性备份并保留 routines / events / triggers；账号权限另行受保护迁移，输出不显示口令。
- SQL 备份仅保存到受保护目录，校验 SHA-256，并在新实例恢复后核验库名、表数、关键表计数和账号连接权限。
- **不导入含 DROP TABLE 的 ry-*.sql 主初始化脚本，不把现网数据库重建成演示数据。**
- 若选择本地新版，先按所选代码和现网 information_schema 生成结构差异；确认每条增量、备份和回滚路径后再执行。目前缺少 ai_config 已证实，不能假定现网与新代码基线一致。
- 本次没有执行备份、导入、初始化 SQL 或任何数据库写操作。

### 4.2 其余持久化

- MinIO：不向新机同步对象数据；旧服务器保留 `nexus-minio`，设置可恢复的重启策略并限制 9005 来源。新服务器上线前后从 ERP 应用流程做授权附件抽样，确认跨机访问；旧机 MinIO 备份与保留周期单独记录。
- Redis：停写并优雅停机后保存 /redis/data 的 AOF / RDB，另保留已识别的匿名卷；不执行 FLUSH、清空租户会话或初始化任务数据。
- RabbitMQ：切换前复查消息数，保留持久化数据和节点身份，版本保持一致；若最终有未消费消息，先明确排空或一致性迁移方式。
- Vision：保留 MySQL 中的人脸底库、所选镜像模型，以及任何运行时新增的持久化文件；不因当前没有 volume 就认为容器内没有需保留的数据。
- 前端：与所选后端版本一致；历史业务对象与配置备份不放入前端公开目录。

### 4.3 选用本地新版时增加的验证

- ERP / 两扩展服务重新构建所选代码，记录版本与 SHA-256。
- 后端测试显式 `-DskipTests=false -Dprofiles.active=`，确认相关模块 Surefire 非零测试数；生产打包与测试过滤分开，运行时明确激活 prod。
- 前端执行类型检查、相关现有单测和生产构建。
- Vision 只发布明确选用的代码状态；保留原工作区修改，运行该版本已有的健康、鉴权、检测场景与人脸等相关测试。
- 本次不部署 Milvus；验证 ERP 不连接 19530，记录 `inmemory` 向量存储的重启丢失限制，知识库持久化不作为本次验收项。
