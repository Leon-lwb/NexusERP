# Nexus 客户端生态规划 — 桌面工位端 / 手持终端 / 边缘网关

> 日期：2026-08-19
> 定位：承接 [MES 硬件生产流程差异分析](../mes/hardware-production-flow-analysis.md) 的 P0 结论（产线烧录上位机、工位扫码 UI），规划需要新建的项目、技术选型与实施路线。
> 范围：**nexus-station**（工位智能终端·桌面端，P0）、**nexus-pda**（手持终端，P0-P1）、**nexus-edge-gateway**（边缘采集网关，P2）、以及 **nexus-erp 仓库内的配套服务端增强**。

## 一、现状盘点

### 1.1 已有系统

| 系统 | 技术栈 | 角色 |
|---|---|---|
| nexus-erp | Java / Spring Boot (RuoYi-Vue-Plus) | 后端：ERP + MES + IoT + AI |
| plus-ui | Vue 3 + TS + Element Plus | Web 管理端（办公/管理人员） |
| Nexus_App | uni-app + Vue 3 | 移动端（管理/办公场景，App / 小程序 / H5） |
| nexus-vision-service | Python / FastAPI | 视觉服务（人脸 / OCR / YOLO，HTTP API） |

### 1.2 服务端已就绪、但至今没有真实客户端的能力

MES `flash` 包已实现完整的"中心大脑"（见 `doc/mes/plans/2026-08-17-mes-flash-operation-guide.md`）：

- 刷写类型 SPI（`FlashTypeProvider` 5 种：固件文件 / 配置文件 / MAC 池 / SN 池 / 外部 REST）
- 资源池 CAS 原子分配、SN 全生命周期、完工门禁（`checkFlashStepGate`，FORCE 模式）
- **免登录设备通道已预留**（`FlashReportController`，请求头 `X-API-KEY`，租户 000000，宽松模式）：
  - `GET /mes/flash/report/station/pending?snCode=` — 工位扫 SN 拉待刷清单
  - `POST /mes/flash/report/flash/auto` — 批量刷写结果上报
  - `POST /mes/flash/report/test/auto` — 综测结果上报
- 目前唯一调用方是测试脚本 `doc/mes/scripts/flash-smoke-test.js`（模拟上位机），**没有任何真实客户端**

### 1.3 缺口（按层次）

| 层次 | 缺口 | 承载项目 |
|---|---|---|
| 物理执行层 | 烧录上位机（串口/USB/烧录器 CLI 驱动、固件下载、结果回传）——分析文档认定的**最大断点** | nexus-station |
| 人机交互层 | 工位扫码 UI、仓储/产线手持作业端 | nexus-pda + nexus-station |
| 现场设备接入层 | PLC / Modbus / SMT 设备数据采集 | nexus-edge-gateway（P2） |
| 服务端配套 | 工位机台账/密钥/升级管理、标签打印体系、设备通道接口补齐 | nexus-erp 内增强 |

## 三、新项目一：nexus-station 工位智能终端（P0）

### 3.1 定位与功能范围

安装在烧录 / FCT / 装配等工位工控机上的桌面应用，是产线工人的作业界面。**不是** Web 管理端的桌面壳——plus-ui 继续承担全部管理职能（不为管理功能做桌面端包装）。

功能模块按里程碑：

| 里程碑 | 模块 | 说明 |
|---|---|---|
| M1 | **刷写作业**（核心） | 扫 SN → 拉取待刷清单（station/pending）→ 预取内容（固件下载 / SN·MAC 预分配）→ 执行烧录 → 上报（flash/auto）→ 完工门禁闭环 |
| M1 | 标签打印 | SN 标签 / 流转卡标签（网络或 USB 打印机，TSPL/ZPL） |
| M2 | 综测上报 | 对接综测仪（串口/网口收数 → test/auto） |
| M2 | 关键件绑定 | 合盖前扫码绑定 PCBA/屏幕/电池 ↔ 成品 SN（分析文档 P1「合盖前强制校验」的执行端） |
| M3 | SOP 查看 / 返修换板 / 外协模式 | SOP 工位查看；解绑+重绑+留痕；外协厂受限账号+指定工单 |

### 3.2 技术选型

**推荐：Electron + Vue 3 + TypeScript + Element Plus + electron-vite**

| 维度 | Electron | Tauri 2 | C# WPF (.NET 8) | Flutter Desktop |
|---|---|---|---|---|
| 团队技能复用 | ★★★ Vue/TS 直接复用 | UI 复用，硬件层需 Rust | ★ 需引入 C# | ★★ 需 Dart |
| 串口/HID/USB 生态 | `serialport`/`node-hid`/`usb`，行业事实标准，纯 JS | serialplugin + Rust crates，可用但要写 Rust | .NET 内置 SerialPort，工业生态最厚 | 生态弱 |
| 调用厂商 CLI（J-Link/CubeProg/esptool） | `child_process` 极简 | Rust Command | Process | 间接 |
| 老工控机（Win7） | 仅 v22 及以下支持 | 不支持（依赖 WebView2） | 需 .NET Framework 4.8 | 部分 |
| 体积 / 内存 | ~200MB / 高 | ~15MB / 低 | ~80MB / 中 | ~60MB / 中 |
| 自动更新 | electron-updater 成熟 | 官方 updater 成熟 | Velopack | 弱 |

推荐 Electron 的决定性理由：

1. **硬件库生态最成熟且纯 JS**：`serialport`（串口）、`node-hid`/`usb`、`net`（TCP RAW 9100 网络打印）、`child_process`（包装 J-Link Commander / STM32CubeProgrammer CLI / esptool 等厂商工具）——全部 npm 即装，无需第二语言。
2. **与 plus-ui 同栈**：UI 组件、请求封装、类型定义可直接复制，同一批 Vue 开发者可交付。
3. **自带 Chromium**：不依赖工控机系统浏览器组件状态（Tauri 依赖 WebView2，Win7 老工控机没有）。
4. **自动更新成熟**：electron-updater generic provider + 现有 MinIO 静态托管，即可搭好全厂升级通道。

备选切换条件：

- 全部工位机确认 Win10+ 且强烈在意体积/内存 → Tauri 2（接受硬件层写少量 Rust）
- 团队后续引入 C#/工控背景人力 → WPF 也成立，当前团队配置下不推荐

**硬性前置**：Phase 0 盘点工位机 OS 版本与烧录器型号（Win7 则 Electron 锁定 v22 LTS）。

### 3.3 应用架构

```
┌─────────────────────────────────────────────────────┐
│ 渲染进程（Vue 3）                                     │
│   工位作业 UI：刷写 / 综测 / 绑定 / 打印 / SOP          │
├──────────────────── IPC（typed）────────────────────┤
│ 主进程（Node）                                        │
│  ┌──────────────┐ ┌────────────────┐ ┌───────────┐  │
│  │ MES Client    │ │ Hardware Hub   │ │ Print     │  │
│  │ X-API-KEY     │ │ FlasherDriver  │ │ TSPL/ZPL  │  │
│  │ 拉单/预取/上报 │ │ SPI 注册表      │ │ TCP/USB   │  │
│  └──────────────┘ └────────────────┘ └───────────┘  │
│  任务队列（失败重试）· 日志环缓冲 + 一键导出 · 看门狗    │
└─────────────────────────────────────────────────────┘
```

烧录驱动 SPI——与后端 `FlashTypeProvider` 对称的客户端抽象，新增设备型号 = 新增一个 Driver 注册，UI 与上报逻辑零改动：

```ts
interface FlasherDriver {
  id: string                        // 'serial-generic' | 'cli-jlink' | 'cli-stm32cubeprog' | 'cli-esptool' | 'hid-custom'
  detect(): Promise<PortInfo[]>     // 枚举串口 / USB 设备
  flash(task: FlashTask, onProgress: (p: Progress) => void): Promise<void>
                                     // 阶段: 下载 → 擦除 → 写入 → 校验 → 复位
  verify(task: FlashTask): Promise<VerifyResult>
}
```

- `serial-generic`：通用串口协议驱动（AT/自定义帧协议，配置化：波特率/帧格式/ACK 超时）
- `cli-*`：包装厂商 CLI 工具，解析其 stdout 转进度条

### 3.4 与 MES 的对接协议

现有接口直接可用：`station/pending`、`flash/auto`、`test/auto`。AUTO 上报落 `mes_flash_record`，完工门禁（`checkFlashStepGate` 查询绑定项 × SN 最新记录）对 MANUAL/AUTO 记录同等生效，**闭环无需后端改动**。

**需在 nexus-erp 新增的免登录接口**（AUTO 通道当前只有"拉单 + 回传"两端，缺中间的内容获取步骤）：

| 接口 | 用途 | 说明 |
|---|---|---|
| `POST /mes/flash/report/station/prepare` | 内容预取/预分配 | SN + flashType → 返回 payload（池类内容在**物理写入前**必须先拿到服务端分配的 SN/MAC 值）+ 固件下载地址 + checksum。须幂等：同 SN 同类型重复调用返回同一分配结果。现有 `pool/allocate` 为登录态接口，设备通道无免登录版 |
| `GET /mes/flash/report/station/firmware/{id}/download` | 固件下载 | 服务端校验 RELEASED + 物料 + 租户后从 MinIO 流式返回。当前 `FirmwareController` 无下载端点，上位机无法免登录取固件 |
| `POST /mes/flash/report/station/register` / `heartbeat` | 工位机注册与心跳 | 配套 `mes_station_device` 台账与远程升级（见 §5.1） |

> 备选设计：上报时携带实际写入的池值由服务端绑定池项。不推荐——写入前无法校验，prepare 模式更稳。

MQTT 上报（分析文档曾提及）**暂不做**：HTTP 通道已满足，避开上位机侧 broker 断连重放复杂度；MQTT 留给 edge-gateway 场景。

### 3.5 可靠性与运维

- **自动更新**：electron-updater（generic provider），产物存 MinIO，版本清单由后端下发（可按设备灰度）
- **服务化**：开机自启 + kiosk 全屏；后台任务不依赖 UI 存活
- **日志**：本地环缓冲 + 压缩包一键导出（产线排障刚需）；心跳携带版本/磁盘/IP
- **测试**：com0com 虚拟串口对 + 协议模拟器做 Driver 回归；`flash-smoke-test.js` 扩展为集成冒烟

### 3.6 里程碑

- **M1（4-6 周）**：拉单 → 烧录（serial-generic + 1 个 cli 驱动）→ 上报 → 门禁闭环 + 固件下载 + SN 标签打印；1 条产线试点
- **M2（+3-4 周）**：综测上报、关键件绑定、设备台账/自动更新铺开、第二类烧录器驱动
- **M3**：SOP、返修换板、外协模式

## 四、新项目二：nexus-pda 手持终端（P0-P1）

### 4.1 定位与场景

**作业端**（仓库员/产线工人/质检员），扫码优先的全屏流程式 UI：

- **仓储**：收货上架、备料发料、移库、盘点（对接 wm 现有单据流）
- **生产**：工序报工扫码、流转卡查询、SN 绑定/解绑、上料校验
- **质量**：IQC/IPQC/OQC 任务执行、不良拍照（可调 vision-service 的物料 OCR / 标签解析 API）

### 4.2 技术选型

**推荐：uni-app + Vue 3 独立新仓库**（与 Nexus_App 同栈同规范，独立 App）

| 维度 | uni-app 新项目（推荐） | 在 Nexus_App 内加模式 | Kotlin 原生 | Flutter |
|---|---|---|---|---|
| PDA 扫码枪接入 | 插件市场有主流厂商插件 / plus.android 注册广播 | 同左 | 厂商 SDK 体验最佳 | 插件一般 |
| UI 范式 | 扫码优先全屏流程，独立设计 | 受现有 tab 框架束缚，需大改 | 自由 | 自由 |
| 发布节奏 | 独立（跟 PDA 试点走） | 与办公端耦合 | — | — |
| 团队技能 | ★★★ 现有 uni-app 经验直接复用 | ★★★ | ★ | ★★ |
| 离线/性能 | plus.sqlite + 队列，够用 | 同左 | Room/WorkManager 最强 | 中 |

关键设计：

1. **扫码接入三级方案**（按优先级）：
   - 键盘楔模式（扫码枪模拟键盘，输入框焦点接收）——零适配，兜底
   - **广播模式（推荐）**：主流 PDA（Urovo、iData、Honeywell、Zebra DataWedge）均可配置广播输出；uni-app 通过 `plus.android` 注册 BroadcastReceiver 接收，或直接用插件市场对应厂商插件
   - **采购锁定 1-2 个 PDA 型号**，统一广播 action，避免适配矩阵失控
2. **离线优先**：本地 SQLite 任务表 + 操作队列 + 弱网自动重试（仓库环境网络差是常态）
3. **便携打印**：BLE 连便携标签打印机（TSPL over BLE），备料标签/库位标签即时打印
4. **拍照识别**：调 vision-service（已有物料 OCR / 标签解析接口），收货对单

### 4.3 与 Nexus_App 的代码复用

抽公共包（uni_modules 或私有 npm）`nexus-client-core`：request 封装（clientid/加密登录/401 处理）、auth store、api 层按域复用。**不共享 pages**——两端 UX 范式不同，共享页面会互相拖累。

### 4.4 里程碑

- **M1（Phase 1，与 station 并行）**：仓储四流程（收货/发料/移库/盘点）扫码 + 离线队列；1 个仓库试点
- **M2（Phase 2）**：MES 场景（报工/质检/SN 绑定）+ BLE 打印 + vision-service 拍照识别

## 五、nexus-erp 内的配套增强（不新建仓库）

### 5.1 设备接入管理（Phase 0-1，station 的运维地基）

- 新表 `mes_station_device`：device_code、名称、绑定工位/产线、OS、app_version、last_heartbeat_ip、api_key（设备级）、状态
- plus-ui 新页「工位设备」：台账、心跳监控、版本分布、远程升级下发、密钥吊销
- **设备级 API Key 取代全局 `mes.api-key`**（现状：一把钥匙全厂共用，泄露即全线失守）；兼容期两者并存，新接口优先校验设备 Key

### 5.2 标签打印体系（Phase 1-2）

| 环节 | 方案 |
|---|---|
| 模板管理 | plus-ui「标签模板」页。v1 字段映射式（选打印机语言 TSPL/ZPL + 字段绑定的内置布局）；v2 视需要嵌 hiprint 开源设计器 |
| 渲染 | 服务端 Java 拼 TSPL/ZPL 指令串（纯字符串，无重依赖），模板 JSON 入库 |
| 打印通道 | 网络打印机（后端/工位机 TCP 9100 直发）、USB（station）、BLE（pda） |
| 触发点 | **SN 批量生成后自动打印**——挂现有 `SnCreatedEvent`（`pro/event`）发打印任务；流转卡下达打印流转卡标签 |

### 5.3 P1 门禁类后端（Phase 2，引用分析文档）

入库/出货自动校验 FCT/整机测试记录；合盖前强制绑定校验；返修换板一键流程。纯后端 + Web 逻辑，与 station/pda 执行端配套形成"先测后入、先绑后盖"的强制闭环。

## 六、新项目三：nexus-edge-gateway 边缘采集网关（P2）

定位：现场设备（PLC、Modbus 仪表、SMT 设备、AOI）数据采集上行，接入现有 IoT 管道。

**推荐：Node.js 20 LTS 单服务**（与 station 同技术域，`modbus-serial` / `node-opcua` / `mqtt.js` 均成熟），部署在工控盒或工位机（Windows 服务 / systemd / Docker）。

- 上行协议：MQTT → nexus-erp 内置 Vert.x Broker，设备身份走 `IotMqttAuthenticator`（在 iot_product/iot_device 注册网关设备），数据自动流入现有 `IotStreamConsumer` → `DcDataRecord` / MES 管道——**后端零新增**
- 备选：Go（单二进制交叉编译 ARM，量大后再说）；Node-RED（非标设备协议快速接、流程配置化，但运维粒度粗）；商用网关（有人/繁易等直接 MQTT 上报，零开发但受制于型号）

## 七、工程化与代码组织

- **仓库**：`nexus-station`、`nexus-pda` 独立仓库（与 Nexus_App / nexus-vision-service 的组织方式一致）；edge-gateway 到 P2 再建
- **共享**：`nexus-client-core`（station 与 pda 的请求/加密/工具）私有 npm 托管；v1 允许复制起步，跑通后再抽包
- **CI**：station 出 NSIS 安装包 + electron-updater 产物归档 MinIO；pda 出 apk；均内网分发，无需应用商店
- **版本**：三端版本号独立，`mes_station_device.app_version` 台账可见，支持按设备灰度
- **环境配置**：沿用 config.js 模式（dev → localhost:8080，prod → nexuserp.website/prod-api）；注意 API 加密开关前后端必须一致（AGENTS.md 已记录的 gotcha）

## 八、安全设计

1. 设备级密钥 + 心跳 IP 监控（防一把钥匙全厂失守 + 异常接入点告警）；支持远程吊销重发
2. 固件链路：下载端点校验 RELEASED/物料/租户 + MD5（服务端已有校验逻辑可复用），工位机下载后本地二次校验
3. 网络分区：产线 VLAN，工位机仅出站访问 MES/MinIO；MQTT 沿用 IoT 模块认证鉴权
4. 审计：AUTO 上报已有 `@Log`；新增 register/prepare 同样落日志

## 十、风险与对策

| 风险 | 对策 |
|---|---|
| 烧录器/设备协议碎片化（**最大技术风险**） | FlasherDriver SPI 隔离；先做通用串口 + 厂商 CLI 两类驱动；Phase 0 就采购样机验证，不做纸上驱动 |
| 工控机 OS 陈旧（Win7） | Phase 0 盘点决定 Electron 版本策略；确有 Win7 则锁定 v22 |
| PDA 厂商适配失控 | 采购锁定 1-2 型号，统一广播 action |
| station/pda 与 Nexus_App 边界漂移 | 定位写进各自 README：station=工位作业，pda=移动作业，App=管理办公，plus-ui=Web 管理 |
| 设备密钥泄露 | 设备级 Key + 心跳 IP 告警 + 吊销机制 |
| 团队并行度 | station 与 pda 均为 Vue 系，同一批人分阶段交付；后端改动集中一人 |
