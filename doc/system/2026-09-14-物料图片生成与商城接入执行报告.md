## 5. 本会话发现并处理的缺陷

### 5.1 ✅ 已修 · 商城 OSS 默认通道被写坏（数据静默丢失）

| 项 | 内容 |
|---|---|
| 现象 | `POST /api/admin/upload/image` 返回 200 和一个 url，`eb_system_attachment` / `sys_oss` 也写了行，但**图片根本不存在**（MinIO 404） |
| 根因 | `sys_oss_config.status` 语义是 **0=启用/默认、1=停用**（`SysOssConfigServiceImpl.init()` 取 status='0' 的那行写 Redis `global:sys_oss:default_config`）。5 条配置里**唯一 status='0' 的是失效的腾讯云 `qcloud`**（`nexus-shop-1301182743.cos.ap-chengdu.myqcloud.com`），而正确的 `minio`（bucket `shop`）是 '1' |
| 后果 | 所有 `uploadType=6` 上传都发往无效 COS 端点 → **S3 403 签名错误**；`UploadServiceImpl` 把异常吞成一行 `logger.error`，主流程照常写库 → **数据库认为成功、文件实际丢失** |
| 修复 | `fix_oss_default.py`：`minio` → status '0'，其余 → '1'；并把 Redis `global:sys_oss:default_config` 写成 **JSON 串 `"minio"`（含引号，7 字节）**。仓库自带的 `docs/oss-migrate/oss_config_minio.json` 也印证 minio/status=0 才是预期状态 |
| 佐证 | `minio_selftest.py` 用**纯 stdlib 实现 SigV4**直连 MinIO：`PUT → 200`、匿名 `GET → 200`，证明凭据/端点/bucket 都是好的，问题在商城侧 |

> `UploadServiceImpl` 这个「吞异常 + 照常写库」的模式是本次能发现问题的关键，也是它危险的地方：
> **上传失败在业务上是不可见的**。建议后续给上传失败加显式返回。

### 5.2 ⚠️ 已定位未修 · 商城 MinIO 上传路径本身有缺陷

| 项 | 内容 |
|---|---|
| 现象 | OSS 通道修好后，上传仍失败：`上传文件失败，请检查配置信息:[subscription has been cancelled.]` |
| 真因 | 打开 AWS SDK DEBUG 后看到实际是 **HTTP 403**：`The request signature we calculated does not match the signature you provided`。canonical request 里 `x-amz-content-sha256: UNSIGNED-PAYLOAD` —— SDK 在**明文 HTTP** 下用异步流式请求体时按 UNSIGNED-PAYLOAD 签名（日志自己也警告 "Payload signing was disabled for an HTTP request with a payload... Use HTTPS for unsigned payloads"），而 MinIO 在非 TLS 下不接受 |
| 代码位置 | `UploadServiceImpl` case 6 调 `OssClient.upload(InputStream,...)`；而 `OssClient` **已经有一个 file 版** `upload(Path filePath, ...)`（用 `transferManager.uploadFile`，第 140 行），case 6 却没用它 |
| 影响 | 商城后台「上传图片」在当前 HTTP MinIO 配置下不可用 |
| 本次规避 | 改走 `minio_put.py`——用 SigV4 直传 MinIO，object key 与商城自身约定完全一致（`nexusimage/public/product/yyyy/MM/dd/<32hex><14rand>.png`） |
| 建议修法 | case 6 改用 `OssClient.upload(file.toPath(), systemAttachment.getSattDir(), null, multipartFile.getContentType())`；或让 `OssClient.upload(InputStream,...)` 内部用 `RequestBody.fromBytes(...)` 替代 `BlockingInputStreamAsyncRequestBody`。**未改源码**（属可独立提交的框架层改动，且需要 MinIO 侧联调确认） |

### 5.3 ✅ 已修 · `eb_store_product.store_info` 每次浏览商品详情被清空（全站，已改源码）

| 项 | 内容 |
|---|---|
| 现象 | 商品简介永远是空的；`GET /api/front/product/detail/{id}` 调用一次，DB 里的 `store_info` 就被写成 `''` |
| 影响面 | **全站商品**，含 7 个存量电商品（实测它们 `store_info` 全为 `''`）——不是本次导入引入的 |
| 根因 | ① `StoreProduct.java:44` 声明 `private String storeInfo = "";`（**Java 字段初始化为空串，非 null**）；② `ProductServiceImpl`（浏览量+1）用 `new StoreProduct()` + `updateById`，MyBatis-Plus 默认 `NOT_NULL` 更新策略把非 null 的空串一并写回 → 每次浏览都清空 |
| 修复 | `ProductServiceImpl` 改为 `LambdaUpdateWrapper` **只 set `browse` 一列**；重建商城 jar + 重启 |
| 回归 | `fix_and_verify_store_info.py`：写入真值 → 连看 3 次 C 端详情 → 值保持 `'M12×60 8.8级 含螺母平垫'`，且 `browse` 仍正常自增 |

> 附带结论：`store_info` 在 C 端**本来就不返回** —— `StoreProductServiceImpl.getH5Detail()`（第 1354 行起）
> 用 `lqw.select(...)` 显式列清单，**不含 `store_info`**。所以这个 bug 只影响后台/数据完整性，不影响 C 端展示。

### 5.4 ℹ️ 既有缺口 · `optionList` 的 JSON 键名是 `value` 不是 `optionName`

方案文档坑 #1 只说「`attr[]` 必须带 `optionList`」，但没说键名。实际：

```java
// ProductAttrOptionAddRequest
@JsonProperty("value")            // ← 序列化键名 = value
@NotBlank(message = "属性名不能为空")
private String optionName;
```

传 `{"optionName":"默认"}` 会被 `@NotBlank` 拒为 **「属性名不能为空」**，必须传 `{"value":"默认"}`。

### 5.5 方案文档中原有「坑」的复核结果

| 文档所述 | 复核 |
|---|---|
| `save()` 强制 `isShow=false`，必须再 `putOnShell` | ✅ 属实（`StoreProductServiceImpl:322`） |
| `save()` 不返回商品 id，需反查 | ✅ 属实（`CommonResult<String>`） |
| `content=null` 会 NPE | ✅ 属实（`:408` `request.getContent().length()`），传 `""` |
| `attr[]` 必须带 `optionList` | ✅ 属实（`:313` 抛「规格属性值不能为空」），但键名坑见 §5.4 |
| `tempId` / `cateId` 只做 Bean Validation | ✅ 属实，脚本侧自行校验存在性 |
| `eb_store_product_attr_result` 从不写入 → 多规格 C 端报「未找到对应属性值」 | ✅ 属实但**只对 `specType=true` 成立**；本批用单规格规避 |

**踩过的两个 Python 坑（后续写脚本必看）**：
1. **`cv2.imwrite` 在 Windows 上遇到中文路径会静默失败**（返回 False 不报错），
   导致 37 张只落了 22 张。必须 `cv2.imencode` + `Path.write_bytes()`。
2. **长连接读库会看到旧快照**：分类是商城应用用另一条连接写的，脚本若在同一个
   REPEATABLE READ 事务里反复 SELECT，会一直看不到新行并误判「创建失败」。
   读连接要 `autocommit=True`。
