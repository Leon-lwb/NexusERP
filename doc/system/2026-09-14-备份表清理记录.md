## 3. 执行内容

### 3.1 删表

| 脚本 | 作用 |
|---|---|
| `script/tools/shop/recon_backup_tables.py` | 枚举 `bak_` 前缀备份表 + 体积 + 回滚源是否还在 |
| `script/tools/shop/scan_backup_patterns.py` | 9 种命名约定全库重扫（找出后缀式漏网的 3 张） |
| `script/tools/shop/drop_backup_tables.py [--dry-run]` | 删 202 张（`LIKE 'bak\_%'`，并断言选中的名字都以 `bak_` 开头） |
| `script/tools/shop/drop_suffix_backup_tables.py` | 删 `ry-vue` 那 3 张（**显式白名单**，避免模式放宽导致误删） |
| `script/tools/shop/verify_backup_cleanup.py` | 复核：全库 `bak_` 为 0 + 表数 + 3D 演示数据 |

`drop_backup_tables.py` 内置的安全约束：只匹配 `bak\_%`（下划线转义，不会误伤 `bakery...`），
且**若选中集合里出现任何不以 `bak_` 开头的名字就直接拒绝执行**。

### 3.2 剔除初始化脚本里被带进去的备份表块

排查中发现更严重的一件事：**主初始化脚本本身就是被备份数据污染的**。

| 文件 | 清理前 | 其中备份表块 | 备份行占比 |
|---|---|---|---|
| `script/sql/ry-erp.sql` | 2.39 MB / 15713 行 | 131 | **52.7%** |
| `script/sql/ry-mes.sql` | 0.71 MB / 5897 行 | 68 | **48.3%** |
| `script/sql/ry-iot.sql` | 0.07 MB / 441 行 | 3 | **67.6%** |
| `script/sql/ry-vue.sql` | 39.28 MB / 96544 行 | 1（`ai_provider_bak_20260820`） | 0.0% |

也就是说：**只清库不清脚本的话，下一次全新导入会把 203 张备份表原样重建。**

`strip_backup_blocks.py` 按 Navicat 的块结构（`-- Table structure for X` … 到下一个表头）
逐块剔除，并以**字节**为单位拼接（保留内容逐字节不变）。清理后：

| 文件 | 清理后 | 表数 | 与库比对 |
|---|---|---|---|
| `ry-erp.sql` | 1.01 MB / 7433 行 | 127 | live 127，missing 0 / extra 0 |
| `ry-mes.sql` | 0.32 MB / 3050 行 | 68 | live 68，missing 0 / extra 0 |
| `ry-iot.sql` | 0.01 MB / 143 行 | 3 | live 3，missing 0 / extra 0 |
| `ry-vue.sql` | 39.28 MB / 96508 行 | 191 | live 191，missing 0 / extra 0 |

## 5. 结论与提醒

- **清理前的数据现在不可恢复**：逻辑备份文件早已丢失，205 张备份表也已删除。
- 如果以后还要做这类「重建」，**先把逻辑备份存到库外**（换盘 / 对象存储 / 别只留 `.gitignore` 的本地目录）。
- 初始化脚本请保持「干净库」状态；不要把带备份的整库 dump 直接覆盖 `script/sql/*.sql`
  （本次就是这么被污染的）。需要重新生成时，先剔除 `bak_*` 再入库。
