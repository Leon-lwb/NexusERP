## 第一批：机制性防线（建议立即）

### F1. `check-permission-seeds.ps1` 扩为「三向」校验 `[已复核]`
**现状**：脚本只做「代码里的权限码 ⊆ 种子里的权限码」**单向差集**，`[豁免]` 是按前缀整体豁免。
**漏掉的**（本轮全部实证）：
- **端点根本没写注解**：`PrdCapacityCalendarController` 6 个 CRUD 端点无 `@SaCheckPermission`，脚本**完全看不见**；
- **前端权限码**：`fa:asset:*`（7 处）、`pu:vendorEvaluation:batchCalculate`（1 处）在种子中不存在，脚本只扫后端；
- **种子未被任何角色持有**：menu 6030/6040/6075/4127/4128/4196/6154/6158/6191 在 `sys_role_menu` 中 0 行 → 全新环境非超管仍 403，脚本只证 `code ⊆ seed`；
- **种子码无端点执行**（死码）：`wm:materialReturn:remove/export`、`wm:materialHandover:remove`、`fin:cost:list`、`cv:face:review`、`pu:vendorEvaluation:calculateAll`；
- **前缀整体豁免过宽**：`system:`/`ai:`/`workflow:` 任何新拼写错误都会被静默豁免。

**建议动作**
1. 扫描 `ruoyi-modules/**/controller/**` 的每个 `@*Mapping` 方法，**未标 `@SaCheckPermission` 且未标 `@SaIgnore` 即 FAIL**（可直接拦住产能日历那类缺陷）；
2. 扫描 `plus-ui/src/**` 的 `v-hasPermi`，断言码存在于 `sys_menu.perms`；
3. 断言每个新增菜单至少被一个角色持有（或要求显式登记「有意不授权」）；
4. 反向差集：种子码无端点执行 → 报告为「死码」（WARN 级，需人工确认是否预留）；
5. 把前缀豁免收敛为**精确码清单**；
6. 扫描根扩到 `ruoyi-common` / `ruoyi-extend` / `ruoyi-admin`（现只扫 `ruoyi-modules`，签名模块 `es:*` 新增端点会绕过）。

### F2. 把「主脚本全新建库验证」纳入 CI `[已复核]`
**背景**：本轮的 P0-1（227 个导入错误）**只可能**通过全新建库发现；上一批次「把增量脚本跑在存量库上」的验证方式在原理上无法发现种子漂移。
**已就绪**：`script/tools/verify-main-sql-fresh-install.ps1`（stdin + `--force` 一次拿全错误清单 + 核对建表数）。
**建议动作**：CI 增加一个 job（可用 `mysql:8.0` 容器），跑该脚本；**任何改动 `script/sql/ry-*.sql` 的 PR 必须跑**。

### F3. 租户处理器增加 fail-closed 开关 `[已复核]`
**现状**：`PlusTenantLineHandler.ignoreTable()` 在 `TenantHelper.getTenantId()` 为空时对**所有表**返回 `true`（第 55 行）→ 任何未传播上下文的线程**静默变成「跨全租户」**。
本轮两个 P0 都源于此：`IotDataArchiveTask` 归档进 `000000`、报表跨租户聚合。
**建议动作**：加配置开关（如 `tenant.strict: true`）：无租户上下文且**非显式** `TenantHelper.ignore(...)` 时**抛异常**。
> 这是**一处改动消除一整类静默数据错位**的高杠杆项；但会暴露所有存量未传播上下文的位置，建议先在 dev 打开跑一轮再上生产。

### F4. `@DS` / `@Transactional` 全仓守卫测试 `[已复核]`
**现状**：项目已有 `EqSparePartServiceImplTest#erpCrossDbReadMethodsMustNotBeTransactional` 这一反射守卫惯例，但只覆盖 1 个类。
**本轮新增**：`TenantScanTaskDatasourceGuardTest`（断言读 `sys_tenant` 的任务类无类级 `@DS`）。
**建议动作**：把守卫泛化为全仓规则（可用 ArchUnit 或自写扫描）：
1. `@DS("x")` 的类/方法内**不得**出现 `DynamicDataSourceContextHolder.push("y")`（y≠x），除非方法无 `@Transactional`；
2. 读 master 库表的 `@Scheduled`/`@JobExecutor` 类**不得**带类级 `@DS`；
3. `@Transactional` 方法**不得**被同类 `this.` 自调用（注解静默失效，见 `IotDataArchiveTask` 的「反向陷阱」）。

### F5. CI 增加「默认凭证」检查 `[已复核]`
**现状**：`mes.api-key` 已 fail-closed，但同类等价默认值仍在（见 第四批 S1）。
**建议动作**：对 `application*.yml` / `docker-compose*.yml` 检测 `${VAR:<非空默认值>}` 模式，命中 `password|secret|token|privateKey|api-key|jwt` 等键名即 WARN/FAIL。成本极低，可防复发。

## 第二批：生产主链路与合规语义（需产品/合规决策 + DDL）

### B1. 工单完工判定原子化（MES-PRO-01/02 后半） `[子代理报告]`
**位置**：`ruoyi-mes/.../pro/service/impl/ProFlowCardServiceImpl.java:618-650`
**机理**：`aggregated_flag` CAS（619-626）只保证「卡→工单」不重复累加；第 6 步「累计(完工+报废) ≥ 计划 → `completeWo`」用的是 CAS **之前**读到的 `wo`（REPEATABLE READ 下取本事务首个读的时间点），而工单累加是原子 `setSql`（635-638）。同工单两张流转卡并发完工时锁不互斥（卡锁 key 含 `cardId`，per-card）→ 两边都可能判定「未达计划」→ 双双走 `PARTIAL_COMPLETED` → **工单永不 COMPLETED、ERP 永收不到完工消息**（完工入库/倒冲不发生）。
**加重项**：`completeWo` 全仓唯一调用点就是此处，**无人工端点、无定时兜底** = 永久卡死。
**建议动作**：用条件原子 UPDATE 取代读-判-写：
```sql
UPDATE pro_work_order SET wo_status='COMPLETED'
 WHERE mes_wo_id=? AND completed_qty + scrap_qty >= planned_qty
```
影响 1 行才发 MQ 消息；或累加后 `SELECT ... FOR UPDATE` 再判定。
**需**：完整回归（生产主链路）+ 补并发测试。

### B2. DHR 分册截断显式化（合规） `[子代理报告]`
**位置**：`ruoyi-mes/.../dhr/mapper/DhrAggregateMapper.java:247,259,285,297,318`（`LIMIT 200/500`）+ `DhrRecordServiceImpl:490-537`
**机理**：截断只发生在 SQL 层，`content_json` 内既无 `truncated` 标记也无「总数 vs 返回数」，`/verify` 只校验哈希自洽（截断后的内容被正常哈希）→ 超限工单的 RELEASED/ARCHIVED 批记录**永久性「看起来完整」**地缺失过程证据，且 `/verify` 返回 PASS。
**建议动作**：分册内容改为 `{"truncated":bool,"limit":n,"returned":n,"total":n,"items":[...]}`；`submit` 时对 `truncated=true` 的分册**显式拦截或要求复核确认**。
**附带**：报告写 `pro_sn` LIMIT 200，实际代码是 500；SOP 分册签名摘要上限 50 条超限即静默 `signature=null`（`DhrAggregateServiceImpl:176-182`），同类「静默不完整」应一并处理（改批量查询而非静默置 null）。
**需**：合规/业务确认「截断时是拦截还是标注」。

### B3. 备件退库单与原领用流水关联（+ 退库量校验） `[子代理报告]`
**位置**：`EqSpareReturnServiceImpl.java:229-316`、`EqSpareReturnLine.java`（实体只有 `spareId/qty/unitCost/remark`）
**机理**：`TXN_RETURN` 走**无上限守卫**的入库分支（`EqSparePartServiceImpl:278-286`）并生成 ERP 真实入库过账。任何有 `mes:eq:spare:return:add` + `:confirm` 的用户，只要备件已映射 ERP 物料/仓库，就能对**任意数量**「退库」→ MES `current_stock` 无条件增加 + ERP 侧 `addStock` 真实入库。这不是「少一个校验」，而是**单据缺少与原领用单据的关联**，无法事后追责。
**建议动作**：`eq_spare_return_line` 增 `issue_log_id`（指向 `eq_spare_stock_log` 的 OUT/REPAIR_USE 行）；`confirm` 时校验 `Σ同 issue_log 退库量 ≤ 该行 quantity`；`refId` 透传到 ERP 过账。
**需**：DDL（加列 + 索引）+ 存量数据回填策略 + 前端明细选原领用流水。

### B4. 新增菜单的角色授权补齐 `[已复核]`
**位置**：主脚本 `ry-vue.sql` 的 `sys_role_menu`：menu_id **6030/6040/6075/4127/4128/4196/6154/6158/6191 均 0 行**；增量脚本 `2026-09-20-perm-seed-alignment.sql:119-123` 只授权 `menu_id BETWEEN 20800 AND 20838` 且父菜单已被持有的角色。
**后果**：全新环境导入主脚本后，非超管角色对 IoT OTA/告警/分组标签、MES 备件请购/工装校准、排产新页面**仍一律 403**，需管理员逐项手工勾选；存量库增量脚本也只授权了一部分。
**建议动作**：按「角色拥有其任一子菜单即补授该目录/按钮」派生授权（主脚本 + 增量脚本各一份），并在 F1 里加断言防复发。
**需**：产品决策「哪些角色默认获得这些功能」。

## 4. 建议写入团队规范的经验（本轮实证）

1. **验证方式必须覆盖「全新安装」**：只在存量库上跑增量脚本，**原理上无法**发现种子漂移/语句顺序/重复键类缺陷。已固化为 `verify-main-sql-fresh-install.ps1`。
2. **`mysql -e "source <file>"` 遇错即停**（`--force` 也不继续）：要拿全错误清单必须 **stdin 重定向 + `--force`**；且必须**同时核对建表数**，否则「只建了 3 张表」这种灾难会被「只有 1 个错误」掩盖。
3. **Lombok 项目里出现大面积「找不到 getter」**：先找**第一个** `already defined`/语法错误，不要去逐个怀疑 getter 所在的类（本轮一个重复方法级联出 30+ 条假错误）。
4. **用正则扫注解时必须排除注释**：本轮 `{@code @DS("erp")}` 出现在 javadoc 里，导致把正确范式误判为缺陷。
5. **权限门禁必须双向**：只证「代码码 ⊆ 种子码」会漏掉「端点无注解」「种子未授权角色」「种子码无端点」三类（本轮各命中一次）。
6. **`@DS` 与 `@Transactional` 互斥**、**`@DS` 对同类自调用无效**、**线程池新线程丢失 `@DS`/租户上下文**：三者已在 `IotForwardDispatcher`、`IotDataArchiveTask`、`EqSparePartServiceImpl` 各命中一次，建议做成守卫测试（F4）。
7. **`@Scheduled` + `@JobExecutor` 双入口的任务，必须同时有 `sj_job` 种子**：否则 SnailJob 开启时「兜底让位 + 无人调度」= 两边都不跑（本轮命中 `wmBatchExpiryTask`）。
8. **报告与注释都可能说谎**：本轮核实出「MES-DC-02 声称已修实际未落地」「3 个任务注释与事实相反」「交接报告 §5 声称全新环境可直接导入」。**复核必须读源码**。
