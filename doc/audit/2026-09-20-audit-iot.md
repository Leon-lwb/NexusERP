## 1. P0 详述

### IOT-MQTT-01 MQTT 身份伪造：认证用 username、落库用 clientId、授权只看租户

- **证据**: `ruoyi-modules/ruoyi-iot/.../mqtt/IotMqttAuthenticator.java:41`、`.../mqtt/IotMqttAuthorizatorPolicy.java:44`、`.../mqtt/IotMqttInterceptHandler.java:119`、`.../pipeline/IotMessagePipelineService.java:78`、`.../pipeline/IotStreamConsumer.java:297`~`299`、`.../pipeline/IotStreamConsumer.java:310`~`314`
- **现状**: 三处对"设备是谁"的判定口径互不相同：
  - 认证 `IotMqttAuthenticator.java:41`：`String deviceCode = StringUtils.isNotBlank(username) ? username : clientId;` —— 用 **username** 查设备并校验密钥。
  - 授权 `IotMqttAuthorizatorPolicy.java:44`：`String deviceCode = StringUtils.isNotBlank(user) ? user : client;` —— 用 **user** 解析租户。
  - 落库 `IotMqttInterceptHandler.java:119`：`String deviceCode = msg.getClientID();` → `IotMessagePipelineService.java:78` `entries.put("device_code", clientId)` —— 用 **clientId**。
  - 消费端 `IotStreamConsumer.java:297`~`299` 用这个 device_code 反查设备，并以设备记录的 `tenantId`/`deviceId` 作为权威值写入。
- **触发路径**: 攻击者持有自己的合法设备 A 凭据，用 `username=A, password=A_secret, clientId=B` 连接 Broker（B 为任意目标设备编码）。认证走 A 通过；`canWrite` 只要求 topic 租户 == A 的租户，故发布到 `iot/{tenantA}/whatever/property/post` 通过；消息被归属到 `device_code=B` 并写入 B 的 `device_id`/`tenant_id`。
- **后果**: ①同租户内可任意伪造其他设备的采集数据（污染趋势、SPC、设备健康、告警判定）；②若 B 属于**其他租户**，`buildData` 取 B 的 `tenantId` 落库，实现**跨租户数据注入**（在别人租户下凭空造数据）；③`IotStreamConsumer.java:310`~`314` 对 topic 租户与设备租户不一致只 `log.warn`，不拒绝，等于不设防。
- **修复建议**: 统一以 **clientId** 为唯一身份。`IotMqttAuthenticator.checkValid` 改为 `if (StringUtils.isNotBlank(username) && !username.equals(clientId)) return false;`，并强制 `clientId` 必须等于 `deviceCode`；`IotMqttAuthorizatorPolicy` 同样改用 `client` 而非 `user`；`IotMqttTopicParser` 解析出的 topic deviceCode 与 clientId 不一致时，`IotMessagePipelineService.publishToStream` 直接丢弃并计数；`IotStreamConsumer.java:311` 的租户不一致分支改为 `ack + return`（拒绝入库）。无需 DDL。
- **影响面**: `IotMqttAuthenticator`、`IotMqttAuthorizatorPolicy`、`IotMessagePipelineService`、`IotStreamConsumer`；前端无影响；需补单测（username≠clientId 必须拒绝）。
- **测试现状**: `ruoyi-common-iot/src/test` 仅 `EwmaUtilTest`，MQTT 认证/授权**零单测**。

### IOT-MQTT-02 clientId 冲突抢占（可远程踢掉任意设备）

- **证据**: `.../mqtt/IotMqttAuthenticator.java:41`、`.../mqtt/MqttBrokerConfig.java:67`
- **现状**: `MqttBrokerConfig.java:67` 只注册 `authenticator` 与 `authorizatorPolicy`，未对 clientId 与会话做任何一致性约束。MQTT 协议规定同 clientId 后连接者接管会话（Moquette 会断开旧连接），而认证又不要求 clientId 等于被认证设备（见 IOT-MQTT-01）。
- **触发路径**: 攻击者用自己设备 A 的凭据 + `clientId=DEV0006` 连接 → 真实 DEV0006 被 Broker 断开 → `IotMqttInterceptHandler.onConnectionLost` 把 DEV0006 置 OFFLINE（`IotMqttInterceptHandler.java:102`~`108`），同时攻击者会话被标记为 DEV0006 在线。
- **后果**: 任意持有任一有效设备密钥者，可无限次踢掉任意设备（拒绝服务）；并可长期"占据"受害者身份，配合 IOT-MQTT-01 持续注入伪造数据。无需知道受害者密钥。
- **修复建议**: 同 IOT-MQTT-01 强制 `clientId == deviceCode`（这是最小且彻底的修复）；另可在 `onConnect` 中校验 `msg.getClientID()` 与已认证身份一致，不一致则记录并拒绝。无需 DDL。
- **影响面**: 同 IOT-MQTT-01；需补单测（A 凭据 + B clientId 必须认证失败）。
- **测试现状**: 无。

### IOT-TASK-01 生产环境 SnailJob 关闭 → IoT 三个定时任务全部不执行

- **证据**: `ruoyi-admin/src/main/resources/application-prod.yml:26`（`enabled: false`）、`.../task/IotDataCleanupTask.java:23`、`.../task/IotDeviceHeartbeatTask.java:26`、`.../task/IotStreamTrimTask.java:26`
- **现状**: 三个任务均以 `@JobExecutor(name=...)`（SnailJob 客户端注解）声明，**没有任何一个用 `@Scheduled`**：
  - `IotDataCleanupTask.java:23` `@JobExecutor(name = "iotDataCleanupTask")` → 删 90 天前 `iot_device_data`
  - `IotDeviceHeartbeatTask.java:26` `@JobExecutor(name = "iotDeviceHeartbeatTask")` → 超时 15 分钟置 OFFLINE
  - `IotStreamTrimTask.java:26` `@JobExecutor(name = "iotStreamTrimTask")` → `XTRIM MAXLEN 100000`
  而 `application-prod.yml:24`~`26` 明确注释"生产环境禁用客户端"并 `enabled: false`。对比：`IotConfiguration.java:22` 有 `@EnableScheduling`，`IotRealtimeSseManager.java:69` 用 `@Scheduled(... scheduler = "iotTaskScheduler")` —— 说明 IoT 模块**具备** `@Scheduled` 能力，只是三个任务没用。
- **触发路径**: 生产部署后无需任何操作，任务永不触发。
- **后果**: ①`iot_device_data` 只增不减，90 天保留策略形同虚设，磁盘/查询持续恶化（叠加 IOT-DATA-01 会 OOM）；②`iot:data:stream` 永不裁剪，Redis 内存无限增长直至 OOM（Stream 是唯一入口缓冲，打满即全链路中断）；③异常掉线设备在 DB 中永久停留 `ONLINE`（Redis `iot:status` 有 30s/1h TTL 会自然过期，DB 不会），设备在线率看板长期虚高。
- **修复建议**: 三选一并明确写入文档：①生产把 `snail-job.enabled` 改 true 并在 SnailJob 后台核对 executor 注册；②把三个任务的执行体抽成 `IXxxService` 方法，另加 `@Scheduled` 薄壳（`scheduler = "iotTaskScheduler"`）作为无 SnailJob 时的兜底，用 Redis 分布式锁（项目已有 Lock4j）防多实例重复执行；③至少为 `iotStreamTrimTask` 加 `@Scheduled`（Redis OOM 是最不可接受的）。无需 DDL。
- **影响面**: `ruoyi-iot/task/*`、`application-prod.yml`、SnailJob 后台配置；运维需知悉；需补测试（可用 `@SpringBootTest` 直接调 `jobExecute`）。
- **测试现状**: `ruoyi-iot/src/test` 无任何 task 测试。

### IOT-TASK-02 `sj_job` 种子 cron 与设计要求不符

- **证据**: `script/sql/ry-vue.sql:10055`、`script/sql/ry-vue.sql:10056`、`script/sql/ry-vue.sql:10057` vs `.../task/IotDeviceHeartbeatTask.java:20`、`.../task/IotStreamTrimTask.java:20`、`doc/iot/NexusERP_IoT阶段一验收报告.md:126`~`128`
- **现状**: 三条 `sj_job` 种子的 cron 参数**全部是 `'0 0 2 * * ?'`**：
  - `ry-vue.sql:10055` 数据清理任务 —— 与设计一致（每天 2:00）。
  - `ry-vue.sql:10056` 心跳检测 —— 设计是 `0 */5 * * * ?`（每 5 分钟，见 `IotDeviceHeartbeatTask.java:20`），实际每天 2:00。
  - `ry-vue.sql:10057` Stream 修剪 —— 设计是 `0 0 * * * ?`（每小时，见 `IotStreamTrimTask.java:20`），实际每天 2:00。
- **触发路径**: 一旦按 IOT-TASK-01 方案①启用 SnailJob，这三个错配的 cron 立即生效。
- **后果**: ①心跳一天只跑一次 → 设备掉线后 DB 最长 24 小时仍显示 ONLINE，在线率/安灯联动全部失真；②Stream 修剪一天一次 → 按每设备每秒一条估算，单日可积压上千万条，Redis 先 OOM 再谈修剪。
- **修复建议**: 修正种子为 `('iotDeviceHeartbeatTask','0 */5 * * * ?')`、`('iotStreamTrimTask','0 0 * * * ?')`；同时把 `IotDeviceHeartbeatTask.java:35` 的 `TIMEOUT_MINUTES=15` 与 5 分钟调度节奏对齐复核（15 分钟阈值 + 5 分钟扫描是合理的）。存量库需 UPDATE `sj_job`。属于**存量库改造**，需在 `doc/system/数据库增量变更记录.md` 登记。
- **影响面**: `script/sql/ry-vue.sql`、SnailJob 后台、存量库；需 DML（非 DDL）。
- **测试现状**: 无。

### IOT-PIPE-01 无去重键：Stream 重投即重复入库

- **证据**: `script/sql/ry-iot.sql:102`~`105`、`.../pipeline/IotStreamConsumer.java:210`~`233`、`.../pipeline/IotStreamConsumer.java:283`~`289`、`.../device/service/impl/IotDeviceDataServiceImpl.java:36`~`42`
- **现状**: `iot_device_data` 只有 `PRIMARY KEY (data_id)`（雪花 ID，每次插入都不同）和三个普通索引 `idx_device_time`/`idx_property`/`idx_tenant_id`（`ry-iot.sql:102`~`105`），**没有任何唯一约束**。消费端流程是"批量 insert → 逐条 `afterPersist` → 逐条 `XACK`"（`IotStreamConsumer.java:210`~`233`），而 `ack()` 自身吞异常只记日志（`IotStreamConsumer.java:283`~`289`）。
- **触发路径**: ①`batchInsert` 成功、`XACK` 因 Redis 抖动失败 → 消息仍在本消费者 pending，下轮被回收重放（`IotStreamConsumer.java:133`~`143`）→ 同一批数据二次插入；②消费进程在 insert 后、ack 前被 kill（容器滚动发布）→ 重启回收 pending → 重复插入；③任何一次 Redis 主从切换导致 ack 丢失同理。
- **后果**: `iot_device_data` 出现重复行。对原始数据本身影响有限，但下游全部受影响：SPC/趋势统计被重复点污染（`doc` 中 `IotDataArchiveTask` 依赖 `uk_point_collect_time` 去重，说明 MES 侧已意识到该问题）；`IotDeviceLatestCache` 虽为覆盖写不受影响；**但重复数据会让告警阈值判定次数翻倍**（`IotAlertChecker` 对每条重复数据都执行一次，虽有限频但会延长限频窗口）。
- **修复建议**: 在 `iot_device_data` 增加 `UNIQUE KEY uk_dev_prop_collect (device_id, property_code, collect_time)`（`tenant_id` 维度已被 `device_id` 覆盖，因 device_id 全局唯一）。插入改为 `insert ignore` / `ON DUPLICATE KEY UPDATE`，或在 `IotDeviceDataServiceImpl.batchInsert` 捕获 `DuplicateKeyException` 后降级逐条插入并跳过重复项（把重复视为"已处理"，照常 ACK）。**需要 DDL**（存量库需先清理重复行，建议按 `device_id, property_code, collect_time` 保留 `MIN(data_id)`）。
- **影响面**: `script/sql/ry-iot.sql`、`IotDeviceDataServiceImpl`、`IotStreamConsumer`；存量库需数据清洗 + DDL；需补测试（重复 XADD 同内容只落一行）。
- **测试现状**: `ruoyi-iot/src/test` 无 pipeline 测试。

### IOT-MES-01 IoT→MES `dc_data_record` 归档链路实际未打通

- **证据**: `ruoyi-modules/ruoyi-mes/.../dc/task/IotDataArchiveTask.java:41`、`script/sql/ry-vue.sql:16498`（及 16499~16592 连续记录）、`ruoyi-admin/src/main/resources/application-prod.yml:26`、`ruoyi-modules/ruoyi-iot/.../common/IotDeviceDataQueryServiceImpl.java:110`~`113`
- **现状**: 回写路径**代码上存在**：`IotDataArchiveTask`（`@JobExecutor(name = "iotDataArchiveTask")`，`IotDataArchiveTask.java:41`）扫 `dc_collection_point.point_type=AUTO` 且 `iot_device_id` 非空的采集点，调 `IotDeviceDataQueryService.getHistoryData(deviceId, start, end)` 拉 IoT 历史数据，写入 `dc_data_record`（`source=IoT`），靠 `uk_point_collect_time` 去重（`IotDataArchiveTask.java:31`、`:146`、`:212`）。契约映射为：`DcCollectionPoint.iotDeviceId` + `DcCollectionPoint.propertyCode`（`ruoyi-mes/.../dc/domain/DcCollectionPoint.java:39`、`:41`）↔ `iot_device_data.device_id` + `property_code`。
  但：①该任务同为 SnailJob `@JobExecutor`，prod `snail-job.enabled: false`（`application-prod.yml:26`）→ 不执行；②**库内保留的真实运行日志证明它此前就一直失败**：`ry-vue.sql:16498` 起连续多条 `sj_job_log_message` 记录 `"Executor configuration is incorrect. executorInfo:[iotDataArchiveTask]"` + `"Task scheduling failed... No executable client"`（2026-09-09~09-10，job id 7，`sj_job` 第 7 条即该归档任务）。
- **触发路径**: 生产部署后无人工干预；或 SnailJob 后台手动触发。
- **后果**: IoT 采集的原始数据**从未归档进 MES**，MES 的 SPC 控制图（`SpcControlChartServiceImpl` 走 `DcDataRecordService.listByPointId`）、采集点数据页、设备健康趋势全部拿不到 IoT 数据 —— 即"文档声称 IoT↔MES 已打通，实际链路未闭合"。用户以为在跑，实际数据为空。

### IOT-PIPE-05 消费者名硬编码 + 建组用 NEWEST → 丢消息与 pending 滞留

- **证据**: `.../pipeline/IotPipelineProperties.java:29`~`32`、`.../pipeline/IotStreamConsumer.java:117`~`126`、`:133`~`134`、`:142`~`148`
- **现状**: ①消费者名默认 `iot-consumer-1` 且 `application.yml:350` 显式写死，注释自认"单机开发阶段固定；多实例时改 iot-consumer-{instanceId}"（`IotPipelineProperties.java:30`~`31`）—— 即多实例场景未实现；②建组用 `StreamMessageId.NEWEST`（`IotStreamConsumer.java:120`）"仅消费建组后的新消息"（`:115` 注释）；③pending 回收用 `greaterThan(StreamMessageId.ALL)` 只回收**本消费者名**的 pending（`:133`~`143`）。
- **触发路径**: ①首次部署（Stream 中可能已有消息，例如先启动生产端/模拟器再启动消费者，或消费端故障重启期间设备持续上报）→ 建组后这些消息**永久不可达**；②多实例部署（`docker-compose-assist.yml` 场景）或运维改了 `consumer-name` → 旧消费者名下的 pending 永远不会被任何实例回收。
- **后果**: 静默丢数据（无告警、无指标）；且 pending 列表持续膨胀占用 Redis 内存（与 IOT-TASK-01 的 stream 膨胀叠加）。因为落库失败时消息保留 pending（`:272`~`275`），一旦改名，这些"待重试"消息就变成永久垃圾。
- **修复建议**: ①消费者名默认改为 `iot-consumer-${spring.application.name}-${server.port}` 或注入实例 ID，避免多实例冲突；②建组用 `StreamMessageId.ALL`（`0`）而非 `NEWEST`，让历史消息进入消费（配合 IOT-PIPE-01 的唯一键幂等，重放是安全的）；③增加 pending 超时认领（`XCLAIM`/`XPENDING` 扫描空闲 > N 分钟的消息并重新投递给当前消费者），覆盖"消费者名变更/实例永久下线"场景；④对 `iot:data:stream` 增加长度与 pending 数监控。无需 DDL。
- **影响面**: `IotPipelineProperties`、`IotStreamConsumer`、`application.yml`；多实例部署需重新评估；需补测试。
- **测试现状**: 无。

### IOT-DEV-01 设备 `status` 是死状态，且前端可直接改写状态字段

- **证据**: `script/sql/ry-iot.sql:39`、`.../mqtt/IotMqttAuthenticator.java:52`、`.../device/service/impl/IotDeviceServiceImpl.java:86`~`110`、`:120`~`135`、`.../device/controller/IotDeviceController.java:92`、`:102`、`:112`
- **现状**: `iot_device.status` 定义为 `ACTIVE/INACTIVE`（`ry-iot.sql:39`，默认 `ACTIVE`），且 MQTT 认证**真的会校验它**（`IotMqttAuthenticator.java:52` `if (!"ACTIVE".equals(device.getStatus())) return false;`）。但全模块检索 `INACTIVE`：**没有任何写入点**。`insertByBo`（`IotDeviceServiceImpl.java:86`~`110`）不设 status（靠 DDL 默认值），`updateByBo`（`:120`~`:135`）只处理产品/协议回填与密钥置空，`deleteByIds`（`:145`~`:147`）是 `@TableLogic` 逻辑删除（`IotDevice.java:103`）。Controller 也**没有**禁用/激活/注销端点（`:60`~`:194` 全部端点已逐一核对）。
- **触发路径**: 需要临时停用一台设备（如检修、退役、密钥泄露需立即阻断）时，除删除外无手段；删除又会让 `iot_device_data` 的历史数据与设备脱节。
- **后果**: ①"停用设备"这个最基本的运维动作在产品里**做不到**：设备一旦泄露密钥，只能物理删除（丢历史关联）或改库；②`updateByBo` 直接把 BO 映射为实体后 `updateById`（`:121`、`:134`），**前端可通过编辑接口任意改写 `status` 与 `connectionStatus`**（BO 若含这两个字段即生效），绕过"连接状态由 Broker 维护"的约定 —— 用户可手工把离线设备标成 ONLINE，污染在线率看板与 MES 设备状态联动（`EquipmentStatusSyncTask` 依赖该字段）。
- **修复建议**: ①新增 `PUT /iot/device/{ids}/status`（`@SaCheckPermission("iot:device:edit")`，body `{status: ACTIVE|INACTIVE}`）实现启用/停用，停用时同时 `markOffline` 并清理 Redis 状态；②`updateByBo` 显式排除 `status`/`connectionStatus`/`deviceSecret` 三个字段（`entity.setStatus(null); entity.setConnectionStatus(null);`），并新增 `@TableField(updateStrategy = FieldStrategy.NEVER)` 或专用 BO 字段白名单；③`status` 建议在 `sys_dict_data` 增加 `iot_device_status` 字典并让前端用 `dict-tag` 展示（当前 `plus-ui/src/views/iot/device/index.vue` 需核对，见 §6）。无需 DDL。
- **影响面**: `IotDeviceController`、`IotDeviceServiceImpl`、`IotDeviceBo`、前端设备列表页；需补测试（编辑请求带 `status=ONLINE` 不应生效）。
- **测试现状**: 无。

## 5. 已核查确认无问题（证明覆盖范围）

- **设备密钥未回显前端**：`IotDeviceVo.java:80`~`81` 对 `deviceSecret` 标注了 `@JsonIgnore`，且 `@ExcelIgnoreUnannotated`（`:21`）使导出也不含该列 → 列表/详情/导出均不泄露密钥（修复 IOT-MQTT-05 时须保持此屏蔽）。
- **Broker 未允许匿名**：`IotMqttProperties.java:35` 默认 `allowAnonymous=false`，`application.yml:342` 亦显式 `false`，`MqttBrokerConfig.java:56` 正确传入 `ALLOW_ANONYMOUS_PROPERTY_NAME` → 匿名连接被拒。
- **设备编码唯一性**：`iot_device` 有 `UNIQUE INDEX uk_code(device_code, tenant_id)`（`ry-iot.sql:48`），产品同理（`:129`）→ 不会出现同租户重码导致 `selectOne` 抛 `TooManyResultsException`。
- **MQTT 凭据比较为常量时间**：`IotMqttAuthenticator.java:57`~`60` 用 `MessageDigest.isEqual` 而非 `equals` → 无时序侧信道（`:56` 注释一致）。
- **认证校验设备状态**：`IotMqttAuthenticator.java:52` 拒绝非 `ACTIVE` 设备 → 停用设备（一旦有了停用入口）确实无法接入。
- **多租户表未被误排除**：`application.yml:156`~`174` 的 `tenant.excludes` 不含 `iot_device`/`iot_device_data`/`iot_product`，且 `IotDevice extends TenantEntity`（`IotDevice.java:22`）→ HTTP 路径的租户隔离由 MyBatis-Plus 插件强制生效，`IotDeviceController` 的 `selectById` 前置校验（`:122`、`:134`、`:149`、`:177`）配合插件可阻断跨租户读取。
- **实时 SSE 端点鉴权正确**：`IotDeviceController.java:169`~`184` 虽用 `@SaIgnore`（EventSource 无法带请求头，token 走 query，属项目既有模式），但函数内显式 `StpUtil.isLogin()`（`:172`）+ `StpUtil.checkPermission("iot:device:query")`（`:176`）+ 设备存在性校验（`:177`）三重把关 → 未认证/越权订阅被拒。
- **数据清理为分批删除、无长事务**：`IotDeviceDataServiceImpl.java:89`~`100` 每批 `LIMIT 1000` 独立提交（无 `@Transactional` 包裹，`:81`~`83` javadoc 说明），并有 `DELETE_MAX_BATCH_LOOP=1000` 上限（`:77`）→ 不会因单条 DELETE 锁全表。
- **Stream 消费异常不拖垮 Broker**：生产端 `IotMessagePipelineService` 的解析/XADD 异常全部捕获后 return（`:64`~`67`、`:88`~`95`），不向 Moquette 会话线程抛出 → Broker 不会被坏消息击穿。
- **消费端批量失败有降级路径**：`IotStreamConsumer.java:208`~`233` 批量插入失败时回退逐条插入以隔离毒消息，且 `batchInsert` 带 `@Transactional(rollbackFor = Exception.class)`（`IotDeviceDataServiceImpl.java:36`）→ 批量部分成功不会留下半批数据。
- **MQTT 消息写入使用 Redis Stream 解耦**：`IotMqttInterceptHandler.onPublish`（`:117`~`127`）只做解析 + XADD，不在 Broker 线程直接写 MySQL → 设备上报不会因 DB 慢而阻塞连接。
- **无 TLS 之外的配置泄露**：`MqttBrokerConfig.java:69`~`70` 启动日志只打印 host/port/allowAnonymous，不含密钥。
- **`@DS("iot")` 使用正确**：`IotDeviceServiceImpl.java:34`、`IotDeviceDataServiceImpl.java:23` 类级 `@DS("iot")`，`IotDeviceDataQueryServiceImpl.java:56`/`:89` 手动 push/poll 数据源（`try/finally` 配对）→ 跨库访问 ry-iot 无泄漏。
- **告警限频防刷屏**：`IotAlertNotifier.java:61`~`65` 用 `setObjectIfAbsent` 实现每 `(deviceId, alertType)` 每分钟一次 → 高频上报不会刷爆 SSE。
- **阈值告警与 EWMA 异常检测互斥**：`IotStreamConsumer.java:248`~`258` 把 `thresholdFired` 传给 `anomalyDetector.detect(data, thresholdFired)` → 同一尖峰不会双告警（`:239`~`241` 注释一致）。
- **SSE 连接有生命周期清理**：`IotRealtimeSseManager.java:51`（1 小时超时）+ `:57`~`60`（onCompletion/onTimeout/onError 三回调）+ `:91`~`94`（发送失败立即移除）→ 无长期连接泄漏（调度线程阻塞问题见 IOT-SSE-01）。
