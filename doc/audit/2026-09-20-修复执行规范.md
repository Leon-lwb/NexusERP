## 0. 环境硬约束

1. **模型服务限制 1 分钟最多 50 次请求**：每个 step **并行批量发起 4~8 个工具调用**，总 step 数控制在 15 步以内。
   收到 429 不要重试——先落盘（把已完成的改动与报告写完）再收尾。
2. **禁止任何 git 命令**（不 commit / 不 checkout / 不 stash）。主代理统一提交。
3. **只改你负责的文件**（见 §1）。跨文件改动需求写进报告，交主代理协调。
4. 改动前**必须先 read 目标文件**（fs-observation-policy 要求）；用 `edit` 做定点修改，不要整文件重写（除非新建）。

## 1. 文件所有权（并发安全，强制）

多个修复代理并行工作，**共享文件的并发写入会互相覆盖**。因此：

### 1.1 绝对独占（只有你被明确分配时才可改）
- `script/sql/ry-vue.sql`（39MB）、`script/sql/ry-erp.sql`（1MB）、`script/sql/ry-mes.sql`（0.32MB）
- `doc/system/数据库增量变更记录.md`
- `application-prod.yml` / `application-dev.yml` / `application.yml`

> 若你的修复需要在上述文件中增加内容：**不要直接编辑**。改为在你的**增量 SQL 脚本**里写等价语句，
> 并在报告里单列一节 `## 主脚本合并清单`（给出「目标文件 + 锚点（附近已存在的整行文本）+ 要插入的行」），
> 由主代理串行合并。`数据库增量变更记录.md` 同理：在报告里单列 `## DDL 登记` 一节。

### 1.2 各自独占增量脚本
每个修复任务创建**自己的**增量脚本，命名 `script/sql/update/2026-09-20-<topic>.sql`，不得改别人的：
- 幂等优先（`INSERT IGNORE` / 先查 `information_schema` 再 `ALTER`）；一次性语句必须在文件头用注释写明"**不可重复执行**"。
- 文件头必须写：用途、执行前提、影响的库（`ry-vue`/`ry-erp`/`ry-mes`/`ry-iot`）、是否需清 Redis 缓存。
- **加唯一约束/索引前**必须给出前置检查 SQL（注释形式），说明存量重复数据会导致失败。

### 1.3 业务代码目录所有权
按任务分配。同一模块内不同包通常安全，但**同一文件绝不能由两个代理同时改**；
若发现必须改别人正在改的文件，写进报告交主代理。

### 1.4 前端
`plus-ui/src/**` 由前端修复代理独占（同一 vue 文件不要跨代理）。**禁止运行 `npm run build`**（慢且会写产物）；
只允许 `npx eslint --fix <你改的文件>` 与 `npx vue-tsc --noEmit`（若确实需要类型校验，注意很慢）。

## 2. 修复质量要求

1. **修根因，不修表象**：例如"客户端可直传 status"要从 BO 白名单 + 服务端强制赋值两侧堵，
   而不是只在 Controller 加个校验。**同一根因在同类服务里复发时，一并修掉**（审计报告里会写明同型位置）。
2. **状态流转用条件更新（CAS）**，不要读-改-写；影响 0 行时抛 `ServiceException` 或记 warn 后静默返回（按业务语义选）。
3. **数量/金额类**：服务端权威字段必须服务端重算；库存增减必须原子 SQL（`setSql` + `>=` 守卫），
   新建库存行必须 `setVersion(0)`（否则乐观锁失效）。
4. **幂等**：MQ 消费者/定时任务/批量接口必须有业务幂等键（DB 唯一约束优先，Redis 去重为辅）。
5. **异步/MQ 写库**必须传播租户上下文（`TenantHelper.dynamic` 或 `AiRequestContext.set`），否则 `tenant_id` 落 0。
6. **多租户**：任何自定义原生 SQL（`@Select` 注解 / XML / `SqlRunner`）都要手动带 `tenant_id`。
7. **权限**：新增端点必须带 `@SaCheckPermission`，且权限码必须有 `sys_menu` 种子（否则非超管 403）。
8. **不要顺手重构**：不做与本次修复无关的重命名/格式化/架构调整，控制 diff 面积，便于评审与回滚。
9. **注释与文档同步**：修改了行为，就把该处与行为不符的注释一并改正（本项目多处注释谎称已实现）。

## 3. 必须补测试

1. 每个 P0 修复**必须**有单测覆盖"修复前会失败、修复后会通过"的核心断言（增量数值级优先，
   例如断言库存从 10 → 8，而不是只断言"没抛异常"）。
2. 测试类放在对应模块 `src/test/java/...`，命名 `<被改类>Test`；已存在同名测试类则**追加用例**，不要新建重复类。
3. 测试里的静态桩注意本项目既有坑：`mockStatic(LambdaUtils)` 需 stub `extract()`，
   更推荐 `TableInfoHelper.initTableInfo` 真实列缓存（见 `doc/system/2026-09-06-全项目审查报告.md` §8.2）。
4. **跑测试**：`mvn -pl ruoyi-modules/ruoyi-<mod> -am test -DskipTests=false -Dtest=<你的测试类> "-DfailIfNoTests=false"`
   （PowerShell 里带点的 `-D` 参数必须加引号，否则会被当成 lifecycle phase 而失败）。
   若因并发构建导致 `target/` 争用失败，重试一次；仍失败则在报告里注明并给出你本地已通过的证据。
   **不要跑全模块全量测试**（主代理最后统一跑）。

## 4. 交付物（每个修复任务）

1. 代码/脚本改动（按 §1 所有权）。
2. 修复报告 `doc/audit/2026-09-20-fix-<topic>.md`，结构：
   ```markdown
   # <主题> 修复报告（2026-09-20）
   > 对应审计: doc/audit/2026-09-20-audit-<x>.md 的 <编号清单> | 分支: feature/erp-mes-iot-audit-fix
   ## 1. 修复清单
   | 审计编号 | 修复内容 | 涉及文件:行 | 是否需 DDL | 测试用例 |
   ## 2. 未修复 / 部分修复项（含理由与建议）
   ## 3. 主脚本合并清单（目标文件 + 锚点 + 待插入行）
   ## 4. DDL 登记（供主代理写入 doc/system/数据库增量变更记录.md）
   ## 5. 验证记录（命令 + 结果，含新增测试类与用例数）
   ## 6. 风险与回滚说明（改错会怎样、如何回退）
   ```
3. 返回主代理 ≤15 行摘要：报告路径、修复编号清单、改动文件数、新增/修改测试数与结果、未修复项、需要的 DDL/主脚本合并。
