## 6. 风险与回滚说明

| 改动 | 改错会怎样 | 回滚方式 |
|---|---|---|
| **WM-02 过账前校验实盘数** | 若有业务确实需要"以 0 为实盘数过账"，现在会报错——但此时**必须显式录入 0**（区分"未盘点"与"盘到 0"），这正是修复目标。前端"差异过账"按钮在未录入时会收到明确错误提示（列出缺失行）。 | 删除 `postAdjustment`/`executeCountAdjust` 中的 `assertAllLinesCounted(lines)` 调用，并把 `generateLines` 的 `setActualQuantity(null)` 改回 `BigDecimal.ZERO`。 |
| **WM-01 出库成本结转** | 若某物料 `unit_cost` 为 NULL/0（历史脏数据），`issueStockCost` 的 `GREATEST(IFNULL(total_cost,0)-IFNULL(unit_cost,0)*qty, 0)` 只会把 `total_cost` 压到 0，不会报错；`tx.unit_cost` 会是 0 而非 null（与修复前"null"相比更可核对）。 | 删除 `completeSalesIssue` 中的 `valuationService.issueStockCost(...)` 调用与 `tx.setUnitCost/setTxAmount` 两行，并移除 `valuationService` 字段。 |
| **WM-03 超收上限** | 到货通知行的 `quantity_arrival` 若被少录，PDA 将无法收满实物（会被判超收）——需改通知单或走差异流程。无到货通知的手工收货仍不限（见 §2）。 | 把 `confirmLine` 的条件更新换回 `lineMapper.updateById(line)`，并删除 `resolveArrivalLimit` 调用与 `arrivalNoticeLineMapper` 字段。 |
| **WM-07 调拨状态白名单** | 生产环境若有"草稿单直接过账"的历史操作习惯会立即报错；且 PDA 下架后状态须为 `TAKEN_OFF` 才可过账，需确认 `PdaTransferServiceImpl` 确实写该状态（已核对，与审计 §5 一致）。 | 把 `in(APPROVED, TAKEN_OFF)` 换回 `ne(EXECUTED)`。 |
| **WM-08/09/10/16/17 状态守卫与 CAS** | 若前端存在"修改已审批单"的合法场景，会收到"当前状态不允许修改"。所有 CAS 失败均抛 `ServiceException`（不静默），便于定位。 | 逐个删除对应的 `if (!STATUS_X.equals(...)) throw` 与 `baseMapper.update(null, lambdaUpdate()...)`，恢复 `updateById`。 |
| **WM-05/06 原子累加 + 上限守卫** | WM-06 会让"两张草稿单各发 60、需求 100"的第二张在过账时报错回滚（修复目标）；WM-05 的 CAS 让并发第二次 `execute` 直接报错而非静默重复扣减。 | WM-05：删除 `execute` 中的 CAS 块，`updateRequirementDetail` 恢复读-改-写。WM-06：去掉 `.apply(...)` 上限条件与 `rows == 0` 判断。 |
| **WM-12 新增列 + 通知单部分收货** | **未执行 DDL 时** `received_qty` 列不存在 → `executeReceive` 的 `arrivalNoticeLineMapper.update` 会报 SQL 错误并**回滚整次入库**。**必须先执行增量脚本 §1 再上线代码**。另：通知单状态新增 `PARTIAL_RECEIVED`，若有按状态白名单的报表/前端筛选需同步加入。 | 执行增量脚本回滚段删除列，并恢复 `executeReceive` 中"整单置 FINISHED"的 6 行原逻辑。 |
| **WM-13 单号改分布式 + 唯一索引** | 单号格式从 `WSCI-<委外单号>-<序号>` 变为序列码，**打印/对账模板若按前缀解析会失效**（需通知业务方）。唯一索引在存量重复时会 ALTER 失败（失败即回滚，不破坏数据）。 | 代码侧恢复 `"WSCI-"+...selectCount+1`；DB 侧执行脚本回滚段的 `DROP INDEX`。 |
| **WM-14 目标维度强制校验** | 历史上"只填来源仓库、目标库位留空"的调拨单将无法过账（修复目标：这类单会污染库存维度）。`TransferStrategy` 强制 `eq` 后，若存量目标库存行维度为 NULL，将**新建**一行正确维度的库存行（而非累加到 NULL 行）——需业务确认是否要合并历史 NULL 行。 | `TransferStrategy` 把两个 `eq` 改回条件 `eq`，并删除 `WmTransferServiceImpl.execute` 的前置校验块。 |
| **WM-15 SO 预留递减量改为实际释放量** | 若历史数据中库存行 `reserved_quantity` 与 SO 行 `reserved_qty` 本就不一致，SO 行会**少减**（保留差额）——这比修复前"多减导致库存行永久假占用"更安全，但 SO 行 `reserved_qty` 可能出现"未归零"的残留，需一次性数据核对。 | 把 `actualConsumeReserved` 换回 `totalConsumeReserved`。 |

**整体回滚**：所有改动集中在 `ruoyi-erp/.../wm/**`（12 改）+ 1 个新增增量 SQL + 4 个新增测试文件；**唯一强制 DDL 依赖是 WM-12 的 `received_qty` 列**（其余 DDL 为建议项），按文件粒度回退即可，无数据迁移不可逆点。
