## 1. 硬性约束（违反即视为无效产出）

1. **只读审计**：审计阶段**禁止**修改任何业务代码、SQL 主脚本、菜单脚本、配置、文档。
   每个子代理只允许写**自己那一份报告文件**（路径见各自任务）。
2. **证据必须有 file:line**：每条结论都要给出 `相对路径:行号`（相对仓库根 `D:\workspace\nexus-erp`）。
   **禁止猜测行号**——必须真的打开文件读过。行号写不准比不写更糟。
3. **必须核验"当前代码状态"**：不要相信文档/注释/上一轮报告的结论。
   仓库里有历史审计报告（见 §3），它们的结论可能已过时（有些已修、有些是误判）。
   引用历史结论前必须在代码里复核，并标注「复核后仍存在 / 已修复 / 原判定为误判」。
4. **不报风格问题**：命名、格式、注释措辞、日志级别、无影响的重复代码——**一律不报**。
   每条发现必须能回答："它会造成什么具体后果？"（数据错、功能不可达、算错钱、越权、界面不可用、崩、慢到不可用）。
   答不上来的就不要写进报告。
5. **宁少勿滥**：一份报告 15~40 条高质量发现远好于 80 条注水。同一根因在多处复发时，
   写一条主条目 + 一句"同型问题另见 X/Y/Z:行号"，不要复制粘贴成 20 条。
6. **修复建议要具体到可执行**：不要写"建议加强校验"，要写"在 `XxxServiceImpl.confirm()` 改用条件更新
   `UPDATE ... WHERE status = 'DRAFT'`，影响 0 行时抛 ServiceException"。
   并注明**是否需要 DDL**、**影响哪些调用方/前端页面**、**是否需要补测试**。
7. 报告用**中文**，Markdown，UTF-8。表格里的路径用反引号。

## 2. 审计视角清单（按此逐项过，不要只看主流程）

### 2.1 后端业务逻辑

- **状态机**：每个业务单据的枚举值是否都有代码写入点？是否存在"死状态"（枚举有、无人设置）
  或"死流转"（文档写了、代码没做）？是否存在绕过状态直接改库/改状态的入口（insertByBo/updateByBo 传 status）？
  状态流转是否用**条件更新/CAS**（防并发双执行），还是读-改-写？
- **幂等**：MQ 消费者、定时任务、批量接口、重复点击、失败重试——是否会重复入账/重复扣减/重复生成？
  唯一键是否真的存在（去 `script/sql/*.sql` 查 `UNIQUE`）？查重是先查后写（TOCTOU）还是靠 DB 约束？
- **并发**：库存增减是否用原子 SQL（`setSql` + `>=` 守卫）而非 Java 先算后写？乐观锁 `@Version` 是否
  对新建行设了 `setVersion(0)`（否则乐观锁形同失效）？锁粒度是否覆盖整个事务（`@Lock4j` 与 `@Transactional` 顺序）？
- **事务边界**：`@Transactional` 自调用（`this.xxx()`）是否绕过代理？跨库（`@DS`）调用是否在同一事务里？
  异步线程（`@Async`/MQ/线程池）是否传播租户上下文（`TenantHelper`/`AiRequestContext`）？
- **金额与数量口径**：服务端是否重算金额（还是信客户端传入）？税率/折扣率是百分数还是小数（同一仓库里是否混用）？
  精度是否够（decimal 位宽 vs 业务量级，如体积、单耗、汇率）？四舍五入时机与舍入模式？
  单位换算（主单位/辅助单位）是否一致？
- **跨模块链路**：ERP↔MES↔IoT 之间 MQ 通道的生产者/消费者是否成对？消息体字段与消费端契约是否一致（改名/漏字段）？
  消费端写入是否回写业务字段（如 `delivered_qty`/`actual_qty`）？是否有"发了没人消费"或"消费了但状态不变"？
- **NULL / 空集合 / 空字符串**：`null` 明细是否被当作"清空"（数据丢失）？`List.of(null)`、`in ()`、三值逻辑漏算？
  `Objects.equals` vs `==`？拆箱 NPE？
- **权限**：每个 Controller 端点是否有 `@SaCheckPermission`？权限码是否在 `sys_menu`（ry-vue.sql）里有对应菜单/按钮，
  否则除超管外全员 403（这是本项目反复出现的坑）？是否存在"登录即可访问"的越权端点（尤其 PDA/工位/App/回调）？
- **多租户**：自定义原生 SQL（`@Select` 注解、XML、`SqlRunner`）是否手动带 `tenant_id`？表是否在租户排除名单里被误排除？
- **数据校验**：BO 上的校验注解是否真的生效（Controller 是否漏 `@Validated`）？跨字段校验（起止日期、数量正负、
  父子一致性）？枚举/字典值是否校验（非法值能否落库）？
- **审计字段与乐观锁字段**：`createBy/updateBy/tenantId` 在异步/回调路径是否落 0 或 NULL？
- **接口契约**：Controller 端点与前端 API 层是否一一对应？**后端有端点但前端 api 层缺函数 → 功能在 UI 上不可达**（本项目高发）；
  前端调了不存在的端点 → 404/死接口。

### 2.2 数据库与表结构（读 `script/sql/ry-erp.sql` / `ry-mes.sql` / `ry-iot.sql` / `ry-vue.sql`）

- 实体字段与表列是否一致（列不存在 → 运行时 SQL 报错；实体有列没有 → 静默丢数据）？
- 枚举/字典值：代码里用的每个状态值是否在 `sys_dict_data` 里有条目？前端 `dict-tag`/下拉是否绑了存在的字典类型？
- 缺唯一约束（单号、幂等键）、缺索引（高频查询列、按租户过滤列）、唯一键缺 `tenant_id` 维度、
  `tenant_id` 非 `varchar(20)`、缺 `del_flag`（却走物理删除）、注释与语义不符、精度不足。
- 主脚本与 `script/sql/update/` 增量脚本的**存量库改造**是否需要（新增列/约束/菜单/字典都要考虑存量库怎么升）。

### 2.3 前端（`plus-ui/src/views/`、`src/api/`、`src/types/` 或页面内 types）

- **布局**：表格列（缺关键列 / 顺序不合业务 / 无宽度导致折行 / 该有排序没有 / 操作列按钮过多无分组）；
  表单（字段分组混乱、必填标记缺失、只读态错乱、弹窗宽度不足导致控件挤压、栅格断点、长表单无锚点/分组）；
  详情页信息缺失、抽屉/弹窗在多分辨率下的溢出。
- **字段**：前后端字段**双向不一致**清单——①后端 BO/VO 有、前端表单/列表/类型没接（功能不可见）；
  ②前端类型/表单有、后端没有（提交无效或报错）；③字典码硬编码在页面里（后端改字典就不同步）；
  ④状态/类型展示用原始码而非 `dict-tag`；⑤单位/精度/千分位/百分比展示错误；⑥金额合计与后端口径不一致；
  ⑦时间格式与后端时区不一致。
- **交互与健壮性**：提交无 loading/防重复提交、删除无二次确认、列表筛选未防抖、
  前端自己算金额与后端重算不一致、错误提示不可读、空态/加载态缺失、`v-for` 重复 key、
  监听器/图表实例未释放（内存泄漏）、分页参数错。
- **可达性**：页面在 `sys_menu` 里有菜单吗（没有菜单 = 页面不可达）？按钮权限码与后端 `@SaCheckPermission` 一致吗？
  路由与菜单 `component` 路径对得上吗？

## 4.5 上下文预算（强制，2026-09-20 补充）

> 本轮已有多个审计子代理因**单代理读取量过大**导致上下文超限而失败。因此追加以下硬性预算，
> **违反预算比漏报更糟**（代理中途失败 = 零产出）。

1. **先建文件**：开工第一步就用 write 写出报告骨架（标题 + 范围 + `## 0. 概览` 空表 + 各节标题），
   之后每完成一块就用 edit 增量补充。**保证任何时刻被打断都有产物**。
2. **读取预算**：`read` 工具调用 **总计 ≤ 30 次**，且每次必须带 `limit`（≤150 行；文件本身更短则无妨）。
   **禁止**不带 limit 整读大文件。
3. **大文件策略**（>800 行的 `*ServiceImpl.java`、`ry-*.sql`、`*.vue`）：
   先 `grep` 定位方法名/关键词拿到行号 → 再 `read offset=行号-10 limit=120`。
   **绝对禁止** read 整读 `script/sql/ry-vue.sql`（39MB）、`ry-erp.sql`（1MB）、`ry-mes.sql`（0.32MB）。
4. **实体/VO/BO/Mapper 不逐个读**：用 `grep` 一次性核对字段名（例如 `grep "deliveredQty" ruoyi-modules/ruoyi-erp`），
   只在发现疑似不一致时才 read 具体文件。
5. **发现条目上限**：P0+P1 ≤ 20 条（只写高置信度、有具体后果的），P2 用表格 ≤ 15 条。
   宁可 15 条扎实的，也不要为了"看起来全面"而读遍全仓。
6. **自觉收尾**：一旦感觉已读了 20+ 个文件，立即停止深挖、把当前结论落盘并按 §5 返回。
   没查完的部分写进 §5「未覆盖范围」，不要为了查完而冒失败风险。

## 4.6 请求预算：必须批量调用工具（强制，2026-09-20 补充）

> 本会话使用的模型服务有硬性限制：**1 分钟内最多 50 次请求**（实测 429 RATE_LIMIT，见会话记录）。
> 每次"助手 step"（一次工具调用轮次）= 1 次请求。多个子代理并发时极易触发 429 而整体失败。

因此：

1. **每个 step 并行批量发起 4~8 个工具调用**（在同一条消息里同时调用多个 `read`/`grep`/`glob`），
   不要"读一个文件 → 等结果 → 再读下一个"。
2. **把总 step 数控制在 10 步以内**（含最后的 write/edit）。计划好要读哪些文件，一次性批量读完。
3. 优先用 `grep`（一次可跨文件搜索）替代逐个 `read`。
4. 收到 429 错误时：**不要重试同一个调用**，改为把当前已有结论立即 `write`/`edit` 落盘，然后按 §5 收尾返回。
