## 1. 审查方法（以及为什么必须这样做）

### 1.1 五路并行对抗式复核
按域派 5 个子代理（ERP / MES / IoT / 横切安全 / 前端），每路都明确要求：
- **先读上一批次自己的报告，再逐条到源码里核实**（多份报告自认「注释与事实相反」）；
- 必须给出 `文件:行` + 机理 + 条件，并**显式列出已排除的疑似项及理由**（避免误报污染集成）；
- 只读，不改文件。

### 1.2 主代理的独立复核（关键，不能省）
子代理的结论**本身也需要被复核**，本轮至少抓到 3 类子代理自身的偏差：

| 子代理结论 | 复核结果 |
|---|---|
| 「`SoContractExpiryTask` 是正确范式，无 `@DS`」 | ✅ 正确。但**我自己的正则扫描**曾把它误判为「有 `@DS("erp")`」——因为它的 javadoc 里**写着** `{@code @DS("erp")}`。教训：正则扫注解必须排除注释 |
| 「`updateStockCost` 丢失更新」 | ✅ 属实，但子代理主动把严重度从 P0 下调为 P2（四个调用点都紧邻重读、同行并发被 InnoDB 行锁/版本守卫兜住），**这是负责任的判断**，予以采纳 |
| 「`BdBomDetailServiceImpl` 等 30+ 处 Lombok getter 找不到」 | ❌ **不是缺陷**。根因是**我自己编辑时在 `PuPurchaseReportServiceImpl` 留下了一个重复方法**，javac 报错后**中断了整轮注解处理**，导致 Lombok 未生成 getter、级联出 30+ 条假错误。修复重复方法后全部消失 |

> **这条经验值得写进规范**：Lombok 项目里出现大面积「找不到 getter」时，**先找第一个 `already defined` / 语法错误**，不要去逐个怀疑 getter 所在的类。

### 1.3 全新建库演练（本轮的增量价值）
上一批次的验证方式是「把 26 个增量脚本跑在**存量库**上」。这在原理上**不可能**发现种子漂移类缺陷：存量库的种子数据是在加列**之前**插入的，天然不漂移。因此本轮补了：

```
把 ry-vue.sql / ry-erp.sql / ry-mes.sql / ry-iot.sql 分别导入一次性空库，收集全部错误 + 核对建表数
```

两个关键技术点（否则会严重低估问题规模）：
1. `mysql -e "source <file>"` **遇到第一个错误就中断**，`--force` 也不继续 → 只能看到 1 个错误，且看不到「后面几十张表一张没建」；
2. 必须改成 **stdin 重定向 + `--force`** 才能一次拿全错误清单。

已固化为可复用工具：`script/tools/verify-main-sql-fresh-install.ps1`（建议纳入 CI / 每次改主脚本后必跑）。

## 3. P0-2：三个 ERP 定时任务被上一批次改坏（已修 + 防回归）

### 3.1 机理
`StockAlertTask` / `WmBatchExpiryTask` / `VendorEvaluationTask` 三个类**同时**具备：
- 类级 `@DS("erp")`；
- 字段 `SysTenantMapper`，在 `jobExecute` 开头查 `sys_tenant`。

而 `sys_tenant` **只建在 `ry-vue`(master) 库**（`erp` 数据源指向 `ry-erp`）。于是：

```
@DS("erp") 生效 → sysTenantMapper 查询打到 ry-erp
  → Table 'ry-erp.sys_tenant' doesn't exist
  → 被 jobExecute 的 catch (Exception) 吞掉
  → return ExecuteResult.failure(...)   ← 返回形状"正常"，任务静默失效
  → 租户循环永不执行
```

**后果**：安全库存预警永不生成、批次效期永不置 `EXPIRED`、供应商绩效永不刷新。三个类的注释都写着「任务类无 @DS 注解走默认数据源」—— **与事实相反**。

**为什么 `@Scheduled` 路径也会中招**：类级 `@DS` 在 `scheduledExecute()` 入口生效并压栈，其内部 `() -> jobExecute(null)` 是**同类自调用**（不弹栈），整个 `jobExecute` 期间栈顶都是 `erp`。

**为什么上一批次会这么改**：`doc/audit/2026-09-20-增量脚本执行记录.md` §6 记录该批次因「未标注时默认走 master」的报错给这三个类补了 `@DS("erp")`——但 erp 侧访问**本来就由 Service 自身的 `@DS("erp")` 提供**（已核实 `WmStockAlertServiceImpl:42`、`WmBatchServiceImpl:38`、`PuVendorEvaluationServiceImpl:57` 均带 `@DS("erp")`）。

### 3.2 修法
删除三个类的**类级 `@DS("erp")`** 与其 import，并把 javadoc 改为明确的**反向警告**（说明为什么不能加、加了会怎样）。同型正确范式见 `SoContractExpiryTask`（刻意不加 `@DS`，javadoc 说明了原因）。

### 3.3 防回归测试（新增）
`ruoyi-modules/ruoyi-erp/src/test/java/com/nexus/erp/task/TenantScanTaskDatasourceGuardTest.java`
用反射断言这三个类**没有**类级 `@DS`，失败信息直接写明机理。照既有 `EqSparePartServiceImplTest#erpCrossDbReadMethodsMustNotBeTransactional` 的写法（该项目已有「反射守卫」惯例），带 `@Tag("local")`/`@Tag("dev")`（否则会被 `<groups>${profiles.active}</groups>` 静默跳过）。

## 4. P0-3：JdbcTemplate 报表跨租户聚合 + SQL 注入（已修）

### 4.1 机理
`JdbcTemplate` 走原生 JDBC，**完全绕过 MyBatis-Plus 的 `TenantLineInnerInterceptor`**。`wm`/`pu`/`prd` 三个报表服务的 7 个方法都只带 `del_flag`/日期条件：

- `WmInventoryReportServiceImpl`（库存汇总 / 库龄分析 / 周转率）
- `PuPurchaseReportServiceImpl`（采购执行率 / 供应商准时交货率）
- `PrdProductionReportServiceImpl`（工单完工率 / 生产效率）

→ 把**全部租户**的库存金额、库龄、周转率、采购额、产量聚合给任意租户。

同包 `SoSalesReportServiceImpl` 早在 09-06 就修过同型问题（其 `appendTenantFilter` 的 javadoc 明确写着「JdbcTemplate 原生 SQL 绕过租户插件，必须显式加 tenant_id」）——**同一根因在同类服务里复发**，正是《修复执行规范》§2.1 要求「一并修掉」的情形，上一批次只修了 `so`。

**附加（注入）**：`WmInventoryReportServiceImpl` 把 `categoryCode` **字符串拼接**进 SQL（`sql.append("AND mc.category_code = '").append(categoryCode).append("' ")`），而它由 `WmInventoryReportController` 的 `@RequestParam String` 直传 → 持 `wm:stock:list` 者可注入。

### 4.2 修法
三个服务统一照 `SoSalesReportServiceImpl` 的模式改造：
- 全部条件改**参数绑定**（`?` + `params.toArray()`），包括 `warehouseId`、`categoryCode`、`months`；
- 新增 `appendTenantFilter(sql, params[, alias])`，显式加 `AND <alias>.tenant_id = ?`（取不到租户上下文时不加，与租户插件自身行为一致）；
- 顺带把 `months` 收敛到 `[1, 60]`（照 `SoSalesReportServiceImpl` 的 `normalizeMonths`），避免超大范围全表扫描；
- 删除 `WmInventoryReportServiceImpl` 里未使用的 `WmMaterialStockMapper` import。

## 5. P0-4：`IotDataArchiveTask` 仍无租户上下文（已修）

**上一批次的交接报告 §3 把 MES-DC-02 列为「已修」，实际未落地** —— 该类全文件 **0 处** `TenantHelper`。

### 5.1 机理（已逐行核实）
调度线程无 Sa-Token 上下文 → `TenantHelper.getTenantId()` 返回 null →
`PlusTenantLineHandler.ignoreTable()`（`ruoyi-common-tenant/.../handle/PlusTenantLineHandler.java:39-56`）在租户为空时对**所有表**返回 `true` → 租户插件**整体失效**：

- `dc_collection_point` 的 SELECT **跨租户扫描**；
- `dc_data_record` 的 INSERT 不带 `tenant_id` → 落库列默认值 `'000000'`（`ry-mes.sql` 该列 `NOT NULL DEFAULT '000000'`）。

**后果**：所有租户的 IoT 采集数据都归档进系统租户，归属租户在 DHR 的 `DATA_COLLECT` 分册（`DhrAggregateMapper` 显式 `tenant_id = #{tenantId}`）与 SPC/采集点页面**永远查不到** —— IOT-MES-01 想修的症状对非默认租户依旧存在。

### 5.2 修法
照同批任务的既有范式（`MaintenanceDueTask:141-169`）改造：
- 新增 `queryTenantIds()`：`push("master")` 查 `MesSysTenantMapper.selectAllTenantIds()`（`sys_tenant` 在 master 库），`finally poll()`；为空回退 `000000`；
- `jobExecute` 改为**逐租户** `TenantHelper.dynamic(tid, () -> archiveAutoPoints(...))`，单租户失败只 WARN 不中断其它租户；
- 游标 `last_archive_time` 挂在**各租户自己的采集点行**上，因此按租户迭代天然是「每租户独立推进」（子代理担心的「单游标被先跑的租户推掉」问题不成立，已在 javadoc 写明）。

### 5.3 顺带修掉的隐患：`@Transactional` 的「反向陷阱」
原 `archiveAutoPoints` 标了 `@Transactional`，但因 `jobExecute` 同类自调用，**注解从未生效**（AOP 绕过）。它**恰恰因为无事务**才让内部的 `IotDeviceDataQueryService`（`@DS("iot")`）跨库读生效：一旦有人按本仓惯例改成 `SpringUtils.getAopProxy(this).archiveAutoPoints(...)`，事务会在 `doBegin` 时把 mes 连接绑定到线程，`@DS("iot")` 不再重路由 → 查询打到 ry-mes 报 `Table 'ry-mes.iot_device_data' doesn't exist` → 异常被逐点 catch 吞掉 → **归档静默 0 行**。

已**移除该失效注解**并写明「本方法刻意不加 `@Transactional`」及原因，消除这个定时炸弹。

### 6.2 IoT 数据转发 100% 不投递
`IotForwardDispatcher` 是类级 `@DS("iot")`，但 `submit()` 把投递丢到**自己的线程池**：

```java
executor.submit(() -> TenantHelper.dynamic(tenantId, () -> deliver(logId)));  // this.deliver → AOP 绕过
```

dynamic-datasource 的 `DynamicDataSourceContextHolder` 是**普通 `ThreadLocal`**（非 Inheritable），工作线程数据源栈为空 → 回落 `primary: master`（已核实 `application-prod.yml:50` `primary: master`）→ 而 `iot_forward_log`/`iot_forward_rule` **只建在 ry-iot** → `BadSqlGrammarException` 被 `catch` 吞成一条 WARN → 留痕永远停在 `PENDING`（重试只扫 `FAILED`，也捞不到），**转发 100% 不投递**，且每条命中数据留下一条永不清理的 PENDING 行。
已在新线程内显式 `DynamicDataSourceContextHolder.push("iot")` + `finally poll()`，并写明为什么类级 `@DS` 在这里帮不上忙。

### 6.3 OTA / 下行指令回执不校验归属

已分别补归属校验：OTA 不匹配即抛 `ServiceException` 拒绝；指令不匹配即丢弃该回执（返回 `null`，不回落兜底匹配）。

## 12. 风险与回滚

| 风险 | 说明 | 回滚 |
|---|---|---|
| 移除三个任务的类级 `@DS("erp")` | 恢复到「默认 master 数据源」的正确行为；erp 侧读写仍由 Service 的 `@DS("erp")` 提供 | 加回注解即回退到（失效的）旧行为 |

| 权限码修正 | 修好后非超管才能看到原本就该看到的按钮（此前永久消失）；**不会**新增越权 | 改回原字符串 |
