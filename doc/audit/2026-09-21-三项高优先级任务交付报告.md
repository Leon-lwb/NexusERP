- **因此任务①的真实缺口只有 DHR**，方向与审计 §4 第 7 项一致。

### 1.2 DHR 批记录实现
- **表**（`ry-mes`）：`dhr_record`（工单/物料/批次/SN 快照、计划·完工·报废数量、状态、快照哈希、三处签名 ID、`version`；`uk_dhr_no(tenant_id,dhr_no)` + 3 索引）、`dhr_section`（10 个固定分册、append-only、`content_json`/`content_hash`；`uk_dhr_section(tenant_id,dhr_id,section_code)`）。
- **状态机**：`DRAFT→SUBMITTED→(RELEASED|REJECTED)`、`REJECTED→DRAFT`、`RELEASED→ARCHIVED`；仅 DRAFT 可重建/删除；进入 SUBMITTED 后快照与分册不可变。
- **聚合 10 分册**：`WO_INFO`/`PROCESS`/`MATERIAL`/`EQUIPMENT`/`TOOLING`/`SOP`/`QC`/`DATA_COLLECT`/`SN_TRACE`/`NCR`。无数据也落 `item_count=0` 空分册，保证分册集合完整可校验。
- **哈希**：`content_hash = SM3(content_json)`；`snapshot_hash = SM3(按 sort_order 拼接 section_code + content_hash)`；`/verify` 重算比对 + 签名链校验。
- **电子签名**（合规要点）：提交/放行/驳回**强制二级认证**（PASSWORD，显式拒绝 `LOGIN_ONLY`）；用 `signInNewTransaction`（REQUIRES_NEW → master）**先签名后 CAS**、不降级；`@Lock4j` 防并发重复签署；签名 ID 与状态在同一条 UPDATE 内落库。
- **跨库边界**：新增 `DhrSignatureAccessor`（`@DS("master")` + 每方法 `REQUIRES_NEW`），解决「DHR 服务类 `@DS("mes")` 却要读 master 的 `es_signature`」；读端点 `listSignatures`/`verify` **刻意不加 `@Transactional`**（有事务时 `@DS` 不切换会读错库）。
- **端点/权限/菜单/字典**：13 端点、10 权限码 `mes:dhr:record:*`、菜单 `4370-4380`（component `mes/dhr/record/index`）、字典 `mes_dhr_status`(600212/600254-600258)、`mes_dhr_section`(600213/600264-600273)。
- **前端**：`views/mes/dhr/record/index.vue`（列表/筛选/生成/导出/详情抽屉分册折叠/重建/删除/提交复核/放行/驳回/归档/校验/签名链），复用 `SignAuthDialog`（凭证只走请求体、失败保持弹窗重试）。

### 1.3 关联口径的诚实标注（审计可复核）
MES 工单主键是 `pro_work_order.mes_wo_id`（**不是** `work_order_id`）。聚合时对**没有工单外键**的来源表不做伪造关联，而是在每条条目里写 `linkage` 字段：
`BY_WORK_ORDER` / `BY_WO_CONSUMPTION` / `BY_INPUT_LOT` / `BY_LOT_IQC` / `BY_MATERIAL_TIME` / `BY_EQUIPMENT_TIME` / `BY_SN` / `BY_NCR_ID`。
其中 `qc_iqc`（仅 `receive_id`，经 `lt_wo_consumption → lt_lot.iqc_id` 链）、`qc_oqc`（仅 `so_id`，按物料+时间窗）、设备分册（按 `equipment_id`+时间窗）均如实标注。

## 4. 同批次发现并修复的真实缺陷（主代理评审产出）

### 4.1 P0：`@DS` 与事务互斥（含 MES-EQ-04 遗留缺陷）
`EqSparePartServiceImpl` 类级 `@DS("mes")`，跨库 ERP 只读走 `DynamicDataSourceContextHolder.push("erp")`。
**机理**：Spring 的 `DataSourceTransactionManager.doBegin` 在事务开启时就取连接并绑定线程（此刻栈顶是 `mes`），此后 `push("erp")` 只压栈；`DataSourceUtils.getConnection()` 直接复用已绑定连接、绕过路由 → 查询打到 `ry-mes` 报 `Table 'ry-mes.bd_material' doesn't exist`。
**受影响**：`insertByBo`/`updateByBo`（**上一批次 MES-EQ-04 就带进来的遗留缺陷**，只要填了 `materialId`/`warehouseId` 就报错）、本批次新增的 `backfillWarehouse`。
**修复**：三处去掉 `@Transactional`（各仅 1 条写语句，单语句原子；编码唯一性由 `uk_tenant_code` 兜底），类/方法 javadoc 加警示，并补**反射防回归用例**（断言这三个方法上没有 `@Transactional`）。
**为什么单测测不出**：单测 mock 了 `ErpSpareStockQueryMapper`，永远不会真的切库。

### 4.2 `sj_job` 的 `deleted=1` 死区
`sj_job` 中 id **4/5/6**（IoT 数据清理/心跳/Stream 修剪）与 **29**（OTA 超时）的 `deleted=1`。SnailJob 视为已删除不调度，而本地 `@Scheduled` 兜底（`SchedulerFallbackUtils`）在 `snail-job.enabled=true` 时**主动让位** → **两边都不跑**。这三个 IoT 任务恰是前序 scheduler-fallback 批次想救活的对象；id=29 是 OTA 批次建种子时从锚点行（id=5）抄了 `deleted` 值。
**附带发现**：前序批次的 cron 修正语句写的是 `UPDATE ... WHERE deleted = 0`，对 `deleted=1` 的行是**静默空转** → 主脚本 cron 已改而本地库一直是旧值。
**修复**：主脚本 + 本地库 `deleted` 置 0，并同步 cron（id=5 → `0 */5 * * * ?`、id=6 → `0 0 * * * ?`）。

### 4.3 主脚本漏种任务定义
`oeeAggregateTask`(201)/`equipmentHealthTask`(202)/`tgMaintenanceDueTask`(205) 只存在于增量脚本与本地库，**`ry-vue.sql` 缺失** → 全新安装会丢失这三个任务定义。已按本地库实际值补种。

### 4.4 测试盲区：电子签名模块的测试从未执行
- `ruoyi-common-sign` 20 个测试类**全部没有 `@Tag`**，被根 pom 的 `<groups>${profiles.active}</groups>` 过滤 → `Tests run: 0`（BUILD SUCCESS 但一个用例都没跑）。补 `@Tag("local")`+`@Tag("dev")` 后 **224 例全绿**（含 PDF CMS 签章 32 例、哈希链 12 例、印章可用性 20 例、验签 13 例等）。
- `ruoyi-system` 的 `PasswordSignCredentialCheckerTest`（电子签名 **PASSWORD 二级认证**校验器）与 `SysOssContentAccessorTest`（签名读取 OSS 正文）同样从未执行，补齐后 **18 例全绿**。
- 累计使 **242 个电子签名相关用例**从「从未执行」变为「实际执行且通过」。

**定位方法（避免误判）**：不能靠「有没有 `@Tag`」推断 —— `@Tag` 是 `@Inherited`，且部分模块自带 surefire 配置使 `groups` 不生效（实测 `ruoyi-mes`/`ruoyi-im`/`ruoyi-station` 的无标签测试照样执行）。正确做法是**对比 `src/test` 下的测试类与 `target/surefire-reports` 下实际产出的报告文件**，逐一列出「从未产出报告」的类。
