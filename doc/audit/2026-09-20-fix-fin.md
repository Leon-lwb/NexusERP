### 1.1 关键设计说明

- **FIN-ARAP-01 采用「拒绝 + 强制」而非「补发消息」**：`insertByBo` 是界面「新增」入口，业务上不存在"直接建已确认收付款单"的合法场景（支付回调走 `PayReceivedConsumer → save(entity)`，该路径自行发 `GlPostingMessage(RECEIPT)`，不受本次改动影响）。因此拒绝非 DRAFT 入参比在新增路径补发消息更安全：不会出现"建单即确认"绕过人工复核。
- **反核销为何直接操作 `SoInvoiceMapper`/`PuInvoiceMapper`**：`so`/`pu` 包不在本批次文件所有权内（另有代理在改），无法在 `ISoInvoiceService` 上新增逆原语。`FinSettlementServiceImpl` 内直接使用其 Mapper 做等价条件更新，字段口径与 `SoInvoiceServiceImpl.verifyInvoice` 完全对称（同表、同 `version` 乐观锁、同 `>=` 守卫、同状态枚举常量），并在类 javadoc 中注明，便于后续把原语下沉到 so/pu 服务层。
- **FIN-GL-02 选择"拒绝"而非"自动把期间改 OPEN"**：自动重开期间会静默破坏月结"无草稿凭证才可关账"的约束，且已生成的损益结转/期末结转凭证仍在账上。拒绝后由用户显式反结账重开期间，"反过账 → 再过账"闭环成立（OPEN 期间路径已用测试覆盖）。

测试过程中定位并修正的实现/测试细节（供后续复用）：

1. **`IdGeneratorUtil` 需要 Spring 上下文**：其静态字段在类初始化时执行 `SpringUtils.getBean(IdentifierGenerator.class)`（该方法继承自 hutool `SpringUtil`，字节码调用点是 `SpringUtil.getBean`），单测必须 `mockStatic(SpringUtil.class)` 并桩 `IdentifierGenerator`；否则 FA/Closing 用例抛 `ExceptionInInitializerError`。注意 `getAopProxy` 是 `SpringUtils` 自己声明的方法，需单独 `mockStatic(SpringUtils.class)`。
2. **MyBatis-Plus 条件参数惰性物化**：`eq/ge` 的值只有在 `getSqlSegment()` 渲染 WHERE 后才会进入 `paramNameValuePairs`（`set()` 的值由 `getSqlSet()` 物化），断言条件守卫必须先取 SQL 段。
3. **审计报告 §2 中 FIN-GL-01 的"建议一"不可直接采用**：`dc[1] = Σdebit − Σcredit` 会把**本币**金额当作原币金额，随后又乘一次期末汇率，实测断言失败。本批次按任务要求采用"以 `amount_currency` 为原币绝对额、方向由借贷列决定"（等价于审计的"建议二"）。
4. `insert(any())` 在 MyBatis-Plus 下会因 `insert(T)` / `insert(Collection<T>)` 重载而歧义，测试里一律写 `insert(any(具体实体.class))`（本批次 5 个测试类均如此，可作规范）。

> 说明：本批次首次执行时 `ruoyi-erp` 的 testCompile 曾被并行代理的 `pu/PuPurchaseReturnServiceImplTest.java:146`（`insert(any())` 歧义）阻断，主代理修复后已全绿；与 fin 改动无关。

## 6. 风险与回滚说明

- **FIN-ARAP-01**：`insertByBo` 现在拒绝 `status != DRAFT`。若存在本仓库之外的自研客户端在新增收付款单时硬编码 `"status":"CONFIRMED"`，将收到 400/业务异常而非静默落库 —— 这是预期的失败可见化；正确用法是先新增（DRAFT）再调 `PUT /confirm/{id}`。回滚：还原 `FinReceiptServiceImpl.insertByBo/updateByBo` 与 `FinReceiptBo` 注释即可，无数据影响。
- **FIN-FA-01**：代码改动后新计提的资产净值立即正确；**存量数据必须执行增量脚本 §2**，否则老资产卡片仍显示偏小净值（且新旧口径混合）。脚本 §2 排除 `DISPOSED` 资产（其净值被处置逻辑有意置 0），只更新与 `original_value - cumulative_depreciation` 不一致的行，可重复执行。若误执行了不含 `status <> 'DISPOSED'` 的版本，可按 `fa_disposal` 记录把已处置资产净值重置为 0 回退。
- **FIN-GL-01**：修复后重估差额符号正确；**已重估期间的历史重估凭证不会自动纠正**（幂等键复用），需按增量脚本 §3 的清单人工复核/红冲重做，否则历史汇兑损益仍偏。
- **FIN-GL-02**：已关账期间不能再反过账/作废已过账凭证。若生产上确有"关账后调整"的作业习惯，需先走反结账重开期间；回滚方式为还原 `GlVoucherServiceImpl.unpost/cancel` 的期间校验（不涉及数据）。
- **FIN-ARAP-02**：反核销会回退发票/收付款单金额并复位未清项，属高权限操作（新权限码默认不分配给普通角色）；逻辑删除核销记录保留了审计线索（`del_flag=2`）。回滚：撤销端点与 service 方法即可，已执行的核销数据由 DBA 按 `fin_settlement` 备份恢复。
