# 故障排查手册

本章档汇总 NexusERP 系统运行中常见的故障现象、可能根因、排查步骤及解决方案，供运维人员快速定位和处置问题。文档按故障层级分类：应用层、数据层、中间件层、基础设施层。

## 一、应用层故障

### 故障 1：启动报错 - 数据库连接失败

现象：应用启动时抛出 `Cannot get JDBC Connection` 或 `Connection refused` 错误，应用无法启动。

可能根因：
- MySQL 服务未启动
- 数据库连接配置错误（URL/用户名/密码）
- 防火墙拦截了 3306 端口
- 数据库最大连接数已满

排查步骤：
1. 检查 nexus-db01 上 MySQL 是否运行：`systemctl status mysqld`
2. 检查连接配置：`cat /opt/nexus/config/application-prod.yml | grep datasource`
3. 测试网络连通性：`telnet 192.168.1.20 3306`
4. 查看数据库当前连接数：`SHOW STATUS LIKE 'Threads_connected';`
5. 查看数据库错误日志：`tail -100 /var/log/mysqld.log`

解决方案：
- MySQL 未启动：`systemctl start mysqld`
- 配置错误：修正 `application-prod.yml` 中的数据库 URL 和凭证
- 防火墙：`firewall-cmd --add-port=3306/tcp --permanent && firewall-cmd --reload`
- 连接数满：调大 `max_connections` 或清理长时间未释放的连接

### 故障 2：接口超时 - 502 Bad Gateway

现象：用户访问页面或调用接口时返回 502 错误，Nginx 日志报 `upstream timed out`。

可能根因：
- 应用节点负载过高（CPU > 90% 或内存不足）
- Undertow 线程池耗尽
- 数据库查询慢导致请求堆积
- AI 模型调用超时（默认 15 秒）

排查步骤：
1. 检查应用节点负载：`top` 或 `htop`
2. 检查 Undertow 线程数：访问 `/actuator/metrics/undertow.threads.busy`
3. 检查数据库慢查询：`SHOW PROCESSLIST;` 和慢查询日志
4. 检查 AI 服务日志：`grep "timeout" /opt/nexus/logs/ai/*.log`
5. 检查 Nginx 错误日志：`tail -50 /var/log/nginx/error.log`

解决方案：
- 应用负载高：重启应用节点（滚动重启，不中断服务）
- 线程池耗尽：调大 `server.undertow.threads.max`（默认 200，可调至 400）
- 慢查询：优化 SQL 索引，添加必要索引
- AI 超时：增大 `nexus.ai.webSearch.timeoutMs` 或检查 API Key 有效性

### 故障 3：SSE 推送中断

现象：AI 对话或 IoT 实时数据推送断开，前端显示连接超时。

可能根因：
- Redis Pub/Sub 连接断开
- Nginx 代理对 SSE 长连接超时（默认 60 秒）
- 应用节点重启导致 SSE 连接丢失

排查步骤：
1. 检查 Redis 连接：`redis-cli ping`
2. 检查 Nginx 超时配置：`grep -A5 "location /dev-api" /etc/nginx/nginx.conf`
3. 检查应用日志中的 SSE 错误
4. 检查是否有应用节点在近期重启

解决方案：
- Redis 断连：重启 Redis 或检查网络
- Nginx 超时：添加 `proxy_read_timeout 300s;` 到 SSE 路径配置
- 连接丢失：前端实现断线重连机制（已内置，5 秒自动重连）

### 故障 4：多租户数据串扰

现象：租户 A 查询到了租户 B 的数据。

可能根因：
- MyBatis-Plus 多租户插件未正确注入
- 手动编写的 SQL 未包含 tenant_id 过滤条件
- 超级租户查询时未正确设置上下文

排查步骤：
1. 检查相关 SQL 是否使用 MP 自动注入
2. 检查手动 SQL 是否显式添加 `AND tenant_id = ?`
3. 检查 TenantInterceptor 是否被正确注册
4. 检查 `@DS("erp")` 注解的方法是否也受多租户控制

解决方案：
- 手工 SQL 必须包含 tenant_id 过滤
- `@DS` 切换数据源后多租户插件仍生效（设计如此）
- 超级租户操作需显式设置上下文：`TenantHelper.setTenantId("000000")`

## 二、数据层故障

### 故障 5：MySQL 主从延迟

现象：从库数据落后主库，报表查询结果不一致。

可能根因：
- 从库硬件配置低于主库
- 主库大事务（如批量删除、大批量导入）导致从库追不上
- 网络延迟
- 从库正在执行全表扫描查询（锁表）

排查步骤：
1. 检查主从延迟：`SHOW SLAVE STATUS\G` 查看 `Seconds_Behind_Master`
2. 检查主库大事务：`SHOW PROCESSLIST;` 查找长时间运行的语句
3. 检查从库查询：`SHOW PROCESSLIST;` 查找全表扫描
4. 检查网络：`ping` 和 `mtr` 测试主从网络质量

解决方案：
- 临时加速：在从库执行 `STOP SLAVE; START SLAVE;`
- 大事务优化：拆分为小批量操作（每次 1000 条）
- 从库只读：禁止在从库执行写入或长时间查询
- 升级配置：主从使用相同硬件配置

### 故障 6：Redis 缓存雪崩

现象：大量缓存同时失效，导致数据库瞬时压力激增，接口响应变慢。

可能根因：
- 大量缓存设置相同的过期时间
- Redis 实例宕机
- 缓存击穿（热点 key 过期）

排查步骤：
1. 检查 Redis 状态：`redis-cli info stats`
2. 检查缓存命中率：`redis-cli info stats | grep keyspace_hits`
3. 检查是否有大量 key 同时过期：`redis-cli --bigkeys`

解决方案：
- 过期时间增加随机偏移：`TTL = base_TTL + random(0, 300)`
- 热点 key 永不过期或设置逻辑过期
- Redis 宕机：启用本地缓存（Caffeine）降级
- 多级缓存：本地 Caffeine + Redis 二级缓存

## 三、中间件层故障

### 故障 7：RocketMQ 消息堆积

现象：工单下发或数据采集消息大量堆积，消费延迟严重。

可能根因：
- 消费端处理速度低于生产速度
- 消费端宕机或网络中断
- 消息体过大导致消费慢

排查步骤：
1. 检查堆积量：访问 RocketMQ Console（http://192.168.1.50:8080）
2. 检查消费端日志：`grep "exception" /opt/nexus/logs/mes/*.log`
3. 检查消费端线程池状态
4. 检查网络连通性

解决方案：
- 增加消费实例（水平扩容）
- 批量消费：增大 `consumeMessageBatchMaxSize`
- 消费失败的消息：检查重试次数，手动重投
- 大消息优化：拆分消息体，减小单条消息体积

### 故障 8：MQTT 设备断连

现象：IoT 设备频繁断开连接，数据上报失败。

可能根因：
- MQTT Broker 负载过高
- 设备网络不稳定
- Keep Alive 间隔设置不当
- 设备证书过期（若启用 TLS）

排查步骤：
1. 检查 MQTT Broker 连接数：访问 192.168.1.51:8083
2. 检查设备日志：查看设备端的 MQTT 连接错误
3. 检查 Keep Alive 配置
4. 检查证书有效期（如启用 TLS）

解决方案：
- Broker 扩容或负载均衡
- Keep Alive 调为 60 秒（默认 30 秒过于频繁）
- 启用设备离线消息缓存
- 设备端实现断线自动重连（指数退避）

## 四、基础设施故障

### 故障 9：服务器磁盘满

现象：应用日志写入失败，数据库报错 `No space left on device`。

排查步骤：
1. 检查磁盘使用：`df -h`
2. 查找大文件：`du -sh /opt/nexus/* | sort -rh | head -20`
3. 检查日志文件大小：`ls -lh /opt/nexus/logs/`
4. 检查临时文件：`ls -lh /tmp/`

解决方案：
- 清理旧日志：`find /opt/nexus/logs/ -name "*.log.*" -mtime +30 -delete`
- 日志切割：确保 logback 配置了按天滚动和压缩
- 扩容磁盘或挂载新数据盘
- 设置磁盘告警（使用率 > 80% 时触发）

### 故障 10：JVM 内存溢出

现象：应用频繁 Full GC，响应变慢甚至 OOM 崩溃。

排查步骤：
1. 检查堆内存使用：`jmap -heap <pid>`
2. 分析堆转储：`jmap -dump:format=b,file=heap.hprof <pid>`
3. 使用 Eclipse MAT 分析内存泄漏
4. 检查是否有大对象分配（如大批量 Excel 导出）

解决方案：
- 调整 JVM 参数：`-Xms4g -Xmx8g -XX:+UseG1GC`
- 大对象分批处理：Excel 导出分页，每次不超过 1000 条
- 检查内存泄漏：常见原因包括 ThreadLocal 未清理、Session 未过期
- 使用 Arthas 在线排查：`dashboard`、`thread`、`jvm` 命令
