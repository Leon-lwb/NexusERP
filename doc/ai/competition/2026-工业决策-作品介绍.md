## 解决的问题

生产订单的承诺日期可能同时受到物料到货、产线负载与排产变更影响。原先将工单、采购行、库存、排程分别查看，难以形成有来源、有权限、有审核记录的交付决策。NexusAI 把一次具体业务对象（工单等）的事实快照串接为“识别风险 → 缺料/APS 推演 → 带来源的方案 → 人工选择动作 → 执行草稿/通知 → 回看结果”。

## 组成与边界

1. **ERP 事实层**（`ruoyi-erp`）：按租户和可见业务对象读取工单、需求、库存、采购行、路由、产能日历及已保存排程；跨数据源读取与快照 hash 支持过期判定。缺料与 APS 使用共享业务口径。
2. **确定性决策层**（`ruoyi-ai`）：计算风险维度、KPI、方案排名、证据链和动作白名单；历史排程利用率只取已保存任务关联资源的计划/有效工时，要求日历覆盖及业务重读。缺证据则不发表低风险数字。
3. **流程与安全层**（`ruoyi-flow`）：工业分析、人工批准及执行节点；越权、跨租户、过期或未经批准的高风险动作失败关闭。LLM 只生成文字说明，不计算工业数值或写业务表。
4. **双端展示**（`plus-ui` 与独立 Nexus-App）：同一字符串 Snowflake runId 的风险、六类 KPI、方案、证据、人工审批和执行状态；SSE 与移动端轮询用于更新，REST 用于刷新恢复。

数据路径：**ERP 只读快照 → 缺料模拟/历史排程＋APS 候选 → 确定性评分/来源校验 → Flow 审批 → 受限动作执行**。历史 KPI 与假设推演必须标清，不以催货承诺虚构降低 APS 拖期。

## 安全与可验证性

- 跨租户和业务读取权限双重校验；审批使用持久化状态及幂等；ERP 下游草稿保持未发布。
- 数值证据绑定具体 ERP 事实及快照版本；重读比较已保存日历工时、资源与日期范围。模型不可提供可信数值事实。
- 40 条 `DELIVERY-001..040` 黄金用例及 5 项 CONTROL 的**服务级测试**、独立库限定 seed/reset 和模拟 HTTP Runner 已交付；真实 MySQL/RabbitMQ/Redis/Flow 端到端报告仍**未实测**。当前不得填写虚构通过率、P50/P95、安全事故次数。
- 竞赛公开材料须注明基于 RuoYi-Vue-Plus 的二次开发；贡献者真实姓名、素材授权、真实视频及 PDF 的校对由项目负责人最终确认。
