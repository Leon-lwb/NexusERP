## 2. Vision 核验

- Docker 容器 nexus-vision-service 处于 healthy 状态，5001 端口可访问。
- /health 与 /health/ready 均返回 HTTP 200。就绪结果为 ready，数据库、通用检测、OCR、人脸模型加载状态均为 true。
- 容器内可见 general、defect_metal、defect_pcb、material_retail 场景，权重均存在。权重存在不等于所有场景已完成实图推理验证。
- ERP 8081 的 /cv/face/health 返回 available=true、status=ready。
- 经 ERP /cv/detect/product 上传程序生成的测试标签，返回 success=true，识别 5 行文字，料号匹配到现有 ERP 物料。该图片用于连通性和字段解析检查，不作为实际工业缺陷检测结果。

若正式视频展示金属或 PCB 缺陷识别，还需选定场景和最终样图。当前 ERP 检测页面及 Java 代理仅传 OCR 开关、标签解析开关，没有请求级 scenario 选择及透传。可在 Vision 管理端固定默认场景后验图；若需要在 ERP 页面切换场景，则需补齐页面和代理接口，并验证场景权重缺失、识别失败时的反馈。

## 3. 方案对比前置条件

现有 9 份排程方案中，同一组 EDD、CR、PRIORITY 方案均为 22 个工单、104 个任务、429 工时、拖期 0，完工日期为 2026-11-02。当前主要汇总指标不能说明三种策略的差异。不同工单数量、车间或窗口的方案不能直接用来证明算法改善。

最近一次已保存工业分析回查结果：

- 状态 WAITING_APPROVAL，证据 295 条，动作 0 条，无推荐方案。
- 四个方案均不可行，原因包含 MATERIAL_SHORTAGE、INCOMPLETE_SCENARIO_COMPARISON、MISSING_KPI；催交方案另含 NO_EXPEDITABLE_PURCHASE_LINE。
- 催交方案 actionCost 为 null。现有排名规则要求同次比较的候选指标完整，因此未知成本影响整组排名资格。
- 风险原因另有 CAPACITY_BOTTLENECK、SUPPLIER_EVIDENCE_INSUFFICIENT。

准备工作：

1. 选定同一组工单、同一车间、同一时间窗口作为比较输入。录制日期变化时，重新核对需求日期、计划日历和供应交期。
2. 让工单存在可解释的共享资源瓶颈、不同交期或优先级；补齐生效 BOM、工艺步骤、工时和产能日历。
3. 核对物料需求、库存、在途数量、基础计量单位及可换算关系。
4. 若纳入催交方案，提供来源可核验的未完成采购行、承诺交期、调整后交期与成本依据。
5. 用可信业务数据重新分析，确认至少两个方案具有可比指标，且存在可推荐方案。不可直接修改结果、放松证据守卫或把未知成本补为零。
6. 若要录制审批执行，另确认可执行动作、实时权限及目标业务对象回查。分析完成、方案推荐、草稿生成、草稿发布分别核验。

当前无动作时，页面已禁用“批准选中项”并提供无动作驳回入口。准备正向案例应补齐数据与证据，不应把 WAITING_APPROVAL 状态解释为已有可批准动作。

## 5. 应优先处理的代码问题

### 5.1 PDA 待办过滤

本轮实际接口结果：

| 入口 | 待办统计 | 待办列表实际返回 |
| --- | --- | --- |
| 收货 | 0 | 25 条，全部 FINISHED |
| 发料 | 3 | 11 条，其中 8 条 COMPLETED、3 条 CREATED |

PdaTodoServiceImpl 的统计按可作业状态过滤；PdaReceiveServiceImpl.todo 和 PdaIssueServiceImpl.todo 未设置状态过滤，直接分页查询业务表。该差异会让演示者从“待办”入口打开已完成单据。

建议统一统计、列表、详情操作的状态口径，在数据库分页查询前过滤可作业状态，并回归页数、总数、关键词查询及状态改变后的刷新。历史记录可保留独立查询入口，不混入待作业列表。

### 5.2 按镜头需要纳入的修复

- 制造 SN 统一追溯：当前 PDA 综合追溯接口对所选 MES SN 没有 resolved.sn 或 mes 结果。如果镜头要求 PDA 扫描制造 SN 并看到 MES 履历，需补齐接口集成并验证；单独展示 Station 制造追溯则无需把此项列为前置。
- 工业缺陷场景选择：需要在 ERP 内切换金属、PCB 模型时，补齐 scenario 选择、校验与代理透传。只展示标签 OCR 时，现有基础链路已验证。
- AI 长回答解析：上一轮已复现全量工单明细的结构化输出解析错误。本轮未重发该请求，未新增修复。只有脚本需要大批量问答时，才纳入本轮专项前置修复。
- 单位显示：现有 ERP 工单有 2 条 unitName 为空。选定案例需按单位主档核对，不通过模型推断单位或填入默认单位。

## 6. 推荐案例准备顺序

1. 修复 PDA 待办过滤，冻结各端后端地址及操作权限。
2. 确定方案比较所用工单和约束，补齐产能、物料及采购来源证据，先跑通同输入下的方案比较与一个可执行建议。
3. 建立同一业务对象关联的现场作业批次，发布并绑定 SOP，准备对应的物料标签、批次码和制造 SN。
4. 分别预演“分析—比较—审批—目标业务回查”和“领取任务—现场作业—结果回传—PC 查询”。使用 H5 和桌面程序的实际运行画面说明仿真环境验证。
5. 保留预演记录，用新的正式录制批次采集提交镜头。最终标签和缺陷样图单独跑识别测试。

Agent 可完成代码修复、仿真案例清单、标签与二维码样张、操作步骤、数据关联核对和预演脚本。若使用实际工业场景，需要确定产品、工艺和最终图片；仿真案例也需明确所模拟的业务约束，使指标变化可解释。
