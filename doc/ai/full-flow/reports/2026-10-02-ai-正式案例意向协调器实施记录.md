# 2026-10-02 正式案例意向与独立来源协调器实施记录

本说明覆盖本任务Python代码与测试，不授予实际业务写入或验收资格；关联[本批阶段报告](2026-10-02-ai-库存未知来源NCR与正式案例准备阶段报告.md)。实际驱动、授权、可信事实及40例真实运行仍未交付/执行。

## 已实现的边界

- `prepare_batch(spec)` 是纯函数式离线准备：40 份独立的 SO → 生产计划 → MRP → ERP 工单创建意向；同一已核验的新物料/BOM/路线可以共享，但不能复用业务来源元组。
- 客户、物料、BOM、单位、工序和工位来自既有 `formal_manufacturing_fixture.build_fixture` / `resolve_new_references` / `assert_request_ready` 契约。正常业务名称、SO/计划空编号由服务端编号；UUID 仅为客户端意向身份，保存在真实 BO 的 `remark`，不是服务器 ID 或业务编号。
- **批次数量只接受明确 `SOFTWARE_PLANNED` 输入**，要求正整数、明确计量单位和明确软件批次增量。无默认数量、无旧 510 推导、无 5.4292 取整、无报价/包装条款/产能猜测。
- 旧 `decide_lot_quantity` 的 `unitBasisConfirmed`、`quantityUomId` 注记及 600/1000 默认值**不用于给本批次定量或授予采购资格**。规范 MOQ/UOM/有效供应条款仍是后续采购集成的独立门禁。所有输出 `procurementReady=false`，本工具根本没有采购/收货/审批写入口。
- 每份计划显示输入缺失与运行门禁，始终 `BLOCKED`、`readyForExecution=false`。缺少事实不是就绪，也不把计划数组长度当成创建记录数。
- 无默认 HTTP/数据库连接、文件保存、环境凭证读取或服务控制。执行需要注入独立的已授权业务客户端、外部权威与独立只读能力。

## 对接既有真实接口

每次 `BatchCoordinator.step(1..40)` 至多对一个案例调用一次既有客户端对象的 `post(path, payload=...)`：

| 顺序 | 实际业务接口 | 请求/读回要点 |
|---|---|---|
| SO | `POST /erp/so/orderheader` | 实际 `SoSalesOrderHeaderBo` + 一个 `SoSalesOrderLineBo`；编号为空、价格必须是适用的新鲜正数解析报价，零价格缺少独立证据则阻断，不写审批/信用状态 |
| 生产计划 | `POST /erp/prd/plan` | 实际 `PrdProductionPlanBo`；DRAFT，服务端编号；来源行/参考号只能来自新 SO 独立读回 |
| MRP | `POST /erp/prd/plan/generateMaterialRequirementsWithDetails/{planId}` | 无自造 body；按新计划定位唯一根需求及四条组件需求 |
| 工单 | `POST /erp/prd/plan/generateWorkOrders/{planId}` | body 是仅含一个新 `requirementId` 的列表；校验 `MATERIAL_REQUIREMENT`、计划、成品、客户、BOM 和原计划数量 |

CREATE 的 Void / 生成器消息响应不提供可信新 ID。响应后从完整分页列表、详情和独立租户行重建身份、编号、关联、数量与日期，再调用既有 `Manifest.record_verified`。冲突拒绝且不重写历史记录；清单只在内存修改，不自动 `save`。

**实际生成器口径已核对源码：** MRP 明细 `unit` 保存 `String.valueOf(material.getBaseUomId())`，不是显示名称“件”；MRP 主表数量是组件毛需求合计，不能当成工单成品数量；工单生成器把 `planStartDate` 设置为服务端创建日，不代表生产计划开始日，更不是现场开工证据。协调器核对这些真实口径，不通过状态/日期补丁把它们改成期望值。

## 输入与能力契约

离线输入 JSON 顶层白名单：

- `batchId`：显式客户端 UUID。离线缺省可生成意向命名空间，但执行必须提供稳定的原始 `batchId`。
- `tenantId`、`asOfDate`：明确租户字符串与业务日期。
- `fixtureInputs`：原 `build_fixture` 的关键字输入，含真实单位目录、类别、工序、独立工位/车间、编号规则等。
- `masterReadbacks`：`material.finished/bolt/nut/washer/box`、`routing`、`bom` 及 `customer`；必须使用实际 VO 字段，不夹带自造服务器字段。
- `masterBaseline`：创建上述主数据之前的完整 `material/routing/bom` ID 集合，不能把旧物料标成新物料。
- `preflight`：既有 `erp_flow_runner.read_only_preflight` 的 `client_code/bom_id/routing_code/warehouse_code/process_keys` 参数。
- `quantity`：`kind=SOFTWARE_PLANNED`，以及明确 `value/uomId/lotMultiple`；数据是软件计划输入而非实物观察。
- `cases`：恰好 40 个输入对象；各自明确 `orderDate/startDate/endDate/requestedDate`。`priceQuote` 是 `/erp/so/orderheader/resolvePrice` 对对应客户、物料、数量、订单日的确切新鲜读回，含 `path/value/readDate/clientId/materialId/qty/orderDate`。报价/数量用确切十进制字符串，拒绝浮点猜测。`resolvePrice` 在缺少价格表且参考价 NULL/默认零时可能兜底为 0；本工具没有零价证据签发方，离线报价、执行前重读和发送白名单均要求价格严格大于 0，不把两次读到 0 当成明确有效零价。可选正常 `planName`。

传入 `verified/apply/created` 等顶层或案例标志不能授予任何权限；未知字段拒绝。

执行对接需由父任务/运营方实现以下能力，**本补丁没有实际驱动或权威签发方**：

1. `ScopedBusinessReads.inventory()`：实际新获取的 `inventory_local3306` 报告，严格为 `localhost TCP 3306 / dev`、当日且无缺失；执行重用真实只读预检，不以 `human_ack` 授予写权限。
2. `master_baseline(tenant_id=...)`：独立核验的原始主数据创建前全量 ID 审计，与同一目标/租户对应。
3. `rows(table, tenant_id=...)`：独立完整、非删除的租户范围只读行，不是复制 API 的投影；实际 snake_case 列，ID 规范字符串、确切数值和统一数据库时区的 ISO 日期/时间。业务创建前读取四类来源全集，以及 SO 行/MRP 明细全集；采集 `db_timestamp` 作为创建基线。`NOW(6)` 基线与秒精度原生 `create_time` 的一秒存储区间比较：同秒可兼容，前一秒不兼容；此时间检查只能补强完整创建前 ID 排除，不能单独证明新记录。
4. `ExternalWriteAuthority.require_authorized(...)`：检查传入的**实际 business_client/主体绑定**、真实环境、租户、意向和确切原请求 SHA-256；授权成功返回 None，否则抛出门禁异常。不能只返回一个“已验证”布尔值，也不能禁用实际业务客户端已有的鉴权。
5. 已独立明确授权的业务客户端对象：自身 `post` 方法保持原有鉴权和本地目标约束；四种 POST 均不得自动重发，不得取 `ApiClient._request` 绕过只读门禁。

`BusinessWriteCapability` 自身固定允许上述四种请求形状，并在发送边界执行外部权威检查。`erp_flow_runner.ApiClient` 及其子类一律不能被此门面提升为可写；`apply/preflight_approved` 原有拒绝语义未改。

物料独立读取只接受真实原生列白名单；`bd_material` 不含 VO 派生 `baseUomName/categoryName`。单位、类别显示名分别通过 `bd_unit_of_measure` / `bd_material_category` 的独立原生行核对 ID、租户、状态与名称，基本单位关联和换算也保留核验；不得把整份 VO 自动转 snake_case 伪装成数据库证明。测试替身依权威 DDL 限定表列。

每次动作重新核对登录租户、主数据、单位目录、选定工序/工位/车间、路线步骤及 BOM 组件。MRP/工单动作还须完整库存证据：缺行、NULL 库存/预留、安全库存未知、冻结未知、基本单位不一致均 BLOCKED；已独立核验的 0 仍可为 0。本工具不以部分合计构造可用量或缺料 KPI。

## 重试与来源完成

- 原请求在该协调器中冻结，重试不能更换数量、日期、来源或意向身份。
- 响应丢失先独立读回；已找到并核验原请求对应的新记录时，只补清单，不再 POST。
- **SO、计划、MRP、工单四种写请求一律需要独立 `require_retry_safe` 证明才能重发**，同时复用原请求和逐请求授权。实际 MRP/工单生成器是“先查存在，再创建”，不是原子并发幂等：首个请求可能仍在事务中，另一次完整读回查无已提交记录不能证明它不会稍后提交。外部证明必须确认首请求已终结且未提交/不会再提交；无此证明保留 UNCERTAIN/BLOCKED，不用端点名称豁免。
- 新协调器不收养已存在的来源；丢失原始请求/基线不能凭清单或“verified=true”恢复写入。当前实现是内存、单协调器、逐步对接器，没有跨进程日志恢复或分布式事务平台；并发锁/快照一致性由独立权威与读适配器负责，变化或歧义即停止。
- 只有 SO、唯一 SO 行、计划、MRP、工单的整组新来源经重读、跨案例唯一性检查及 Manifest 冲突检查后，才计为 `sourceCompleteCases`。单独已有清单、40 次分析或 40 个逻辑条目均不计数。
- `SOURCE_COMPLETE` 仅说明业务来源创建/读回闭环，不等于 SO 已确认、MRP 已发料、工单下发/完工、生产部署、实物验收或 SLA。`readyCases`/`physicalAcceptance`/`slaAccepted`/`procurementReady` 不会被此工具提升。

## 第二次规格审查：派发状态不得由异常类型重置

- 再审发现完整 `send()` 包含授权和真实 POST，不能把其中的 `PreflightError` / `BatchContractError` 一律解释为尚未派发。首次派发后的本地响应包装错误也可能使用这两类异常；删除 attempted 会让下一次请求绕过重试证明。
- 父线程加入四角色×两异常的 8 个实际派发反例，以及明确的派发前授权拒绝用例，取得 62 个方法中 8 个子场景断言失败、0 错误/跳过的 RED。
- `BusinessWriteCapability.send(..., on_dispatch=...)` 在逐请求授权成功、冻结路径/载荷之后且真实 POST 之前触发派发记录；回调只是状态观察，不授予权限。协调器只在该边界写 attempted，此后不按异常类别撤销标记；派发后响应/读回/契约故障返回 UNCERTAIN，不冒称单据尚未创建。
- 派发前明确授权拒绝仍 BLOCKED、POST 为0且没有未决尝试；授权恢复后无需伪造重试证明。派发后未决请求必须先独立读回或取得外部安全证明，数量/日期/载荷不变化。
- 五个原来在 POST 之后拒绝来源的用例只将状态断言从 BLOCKED 改为 UNCERTAIN；数量、来源不接受、跨租户/旧ID拒绝及 Manifest 原样保留的断言未放松。62 个定向用例 GREEN，最终整套 Python 以之后父线程复验为准。
