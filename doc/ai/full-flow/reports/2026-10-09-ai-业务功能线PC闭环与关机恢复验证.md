### 真机发现的日期查询问题

首次新 JAR 的订单／数量上下文成功，但两个仓储上下文 R500。沿实际异常定位到 `WmCertifiedWarehouseReadMapper.databaseDate`：本机 MySQL **5.7.20-log** 执行带 WHERE 而无 FROM 的原日期常量查询报 **1064**；READ ONLY 对照只增加 `FROM DUAL` 后实际返回 1 行，无业务表写入。

先补真实 Mapper `@Select/@Options` 回归；首次漏 import 的编译失败单独保留，**不记为 RED**。修好测试 import 后正确 RED 为 **11 用例、1 失败、0 errors/skipped**；生产 SQL 最小加入 `FROM DUAL` 和中文 Javadoc 后 GREEN **11／0**。日期格式、租户绑定、禁缓存、非锁定和其他查询合同未改，独立两文件复审无 P1/P2。修复后重新完整测试／打包并重启服务，两个仓储上下文再经真实 API 验证成功。这是本次日期 SQL 根因，**不代表历史 JDBC/AOP UNKNOWN 已定位**。

## 四、单位核验与共享护栏

单位列表接入核验对话框和 `GET /erp/bd/measure/quantity-context`。上下文仅使用真实登录主体，不取得业务连接。人工从原生详情、真实根映射和资料确认 `expectedVersion / primaryId / conversionRate / quantityScale / reference`；单位旧合同的 expectedVersion 是**字符串或合法 NULL**，不可照搬订单整数版本规则。不提交 actor、verified、认证时间或额外 requestKey，不猜根、不自动认证旧单位族／历史库存。Fresh 事实必须匹配用户确认的原快照。

共享 transport 固定内存凭证，dispatch 前及响应后校验完整会话／业务作用域。认证响应只在 HTTP200／R200 且合同完整时成功；明确 4xx 拒绝才可按守卫释放，5xx／网络／畸形 200 保留 UNKNOWN，不换键或自动重发。内存 latch 与可读回的 durable release-fence 防止存储 I/O 异常解锁；同 scope 异 metadata 冲突粘性封闭。认证错误在全局 request 的 toast／重新登录／解码前脱敏，旧账号迟到 401 不能登出新账号，普通 CRUD 保持原处理。

**存储边界**：浏览器存储不是跨进程 CAS；全持久存储丢失＋写全失败＋硬 reload 无法恢复已丢意图。只读 GET、重新打开和换版本都不是 UNKNOWN 清锁证明。本轮不宣称所有浏览器／存储故障完成证明。
