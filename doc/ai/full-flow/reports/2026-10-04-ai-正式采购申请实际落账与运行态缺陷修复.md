## 四、运行过程中实际发现和处理的问题

### 1. 私有执行器的供应关系请求不完整

首次关系请求漏传现有 `bd_material_vendor` 表必需的供应商编码和名称。操作日志明确记录 `vendor_code` 非空约束拒绝，独立 SQL 确认没有关系行。保留原拒绝和意图，随后从本批已回读的供应商复制准确字段，提交新的明确纠正请求并完成双读；不是把未知响应按同名记录补认成功。

### 2. 私有响应适配误将量纲编码当雪花 ID

预览 API 实际成功，但私有执行器把合法 `dimensionId=数量` 当成数字 ID 拒绝。已将量纲语义文本和数字业务 ID 分开验证；重新观察的是无业务写入的预览，记录新观察来源，不重发采购创建。私有离线执行器最终 58 项回归通过；这些不是实际业务用例或独立来源案例。

### 3. 实际审批的供应商状态映射错误

当前 JVM 的异常诊断定位到生命周期 `requireCatalog → lockLifecycleVendor`：MyBatis 将实际 VARCHAR `ACTIVE` 映射为 Long，产生 `NumberFormatException`，随后由 ERP 专属事务入口统一拒绝。只读复验确认申请仍 DRAFT/0、无 APPROVE 事件、占用仍 10。

生命周期以及转单 Mapper 的供应商 status 改为与 `BdVendor` 主档一致的 String；门禁严格要求 `ACTIVE`、正确租户/ID和未删除，不接受数字文本 `1`、大小写/空白变体、未知或停用状态。**未改写供应商数据库状态来绕过接口。**

新增真实内存 VARCHAR → MyBatis Mapper → 业务门禁回归，先复现红测试再修复；它证明类型修复和拒绝边界，不代表运行中后端已修好或真实审批已经通过。

### 4. 四段采购权限不能经正常菜单接口配置

本地目前缺少准确的 `pu:order:terms:add`、`pu:order:terms:confirm` 菜单，原三段正则还会拒绝四段权限。共享后端菜单格式现已支持至少三段的完整层级权限，并同步 PC 表单格式校验，保留空可选值/既有通配符位置及长度限制，拒绝少段、空段、非法字符、空白和换行。

这是语法修复，**不改变权限匹配或独立复核业务规则**。本批没有创建宽泛复核角色、冒充第二操作人或给同一人确认报价；真实菜单保存、最小角色/第二正常用户及独立确认仍待新构建加载后执行。
