## 0. 文档目的与结论

本文将 NexusERP 现有的 ERP、MES、IoT、AI、Flow 能力收敛为一个适合“AI+ 工业软件赛道”的主场景：**订单交付风险推演与闭环决策**。

本设计不把大模型作为排产、缺料或业务数据的事实计算器，而采用以下职责边界：

- **工业算法负责计算**：APS、缺料推演、风险评分、方案 KPI、规则校验均由确定性代码完成；
- **LLM 负责理解与表达**：理解自然语言目标、归纳根因、解释方案取舍、生成面向人的决策摘要；
- **规则与权限负责约束**：动作白名单、租户隔离、权限检查、幂等、数据新鲜度和审批策略由服务端控制；
- **人工负责最终授权**：高风险业务动作必须经具备权限的用户批准；
- **流程引擎负责执行与追踪**：审批后的通知、草稿创建、MQ 投递和状态回写进入可审计流程。

一句话定位：

> NexusAI 基于 ERP/MES/IoT 业务证据识别交付风险，运行缺料与有限产能排程推演，比较多个可执行方案，并在人工批准后驱动业务流程闭环。

## 1. 关键架构决策

| 编号 | 决策 | 说明 |
|---|---|---|
| ADR-01 | 以“交付风险闭环”作为唯一主场景 | 比赛视频和文档不再平均展示全部 AI 功能，其他能力作为平台支撑和未来扩展说明 |
| ADR-02 | 新增独立 Decision API，不破坏现有 `/ai/chat/**` | 结构化工业决策不与通用聊天响应混用，现有聊天保持兼容 |
| ADR-03 | 数值计算不交给 LLM | 交期、缺口、拖期、利用率、方案评分全部来自确定性服务 |
| ADR-04 | 核心决策链不允许任意写 SQL | 读取与动作执行统一通过业务 Port/Service；LLM 只选择受控能力 |
| ADR-05 | 比赛前不新建 Maven 模块 | 在 `ruoyi-common-ai`、`ruoyi-ai`、`ruoyi-erp`、`ruoyi-flow` 内按端口适配器方式实现，赛后再视规模抽取 `ruoyi-industrial-ai` |
| ADR-06 | 分析流与执行流分离 | 分析完成后进入 `WAITING_APPROVAL`；批准后才启动执行流，避免长时间占用 Flow 工作线程 |
| ADR-07 | 比赛版审批门由 Decision 服务实现 | 通用 `HumanApprovalNodeProvider` 涉及 Flow 暂停/恢复语义，列入赛后平台化；比赛版仍在时间线上显示审批节点 |
| ADR-08 | 复用现有 Flow 实例和节点运行记录 | `ai_decision_run.analysis_flow_instance_id` 与 `execution_flow_instance_id` 分别关联 `ai_flow_instance`，避免重复建设完整追踪表 |
| ADR-09 | 方案排名采用确定性多目标评分 | LLM 不参与方案排序；权重可配置并记录版本 |
| ADR-10 | 高风险动作只生成草稿或待办 | 比赛版不自动发布排产、不自动审批采购、不自动执行不可逆库存事务 |
| ADR-11 | 决策结果使用结构化 DTO | PC/App 不解析 LLM Markdown 来决定按钮、状态或业务动作 |
| ADR-12 | 以 Benchmark 证明效果 | 使用固定演示数据和可重复测试集，对路由、数据、决策、安全、性能和业务指标进行量化 |
| ADR-13 | `snapshotHash` 使用可重算的关键业务指纹 | 完整快照 JSON 独立持久化；哈希排除 `snapshotAt` 等展示字段，只覆盖审批前必须复核的订单、工单、需求、库存、在途、路线/产能和当前排产关键字段，避免 horizon/时间戳导致永久误判过期 |
| ADR-14 | ERP 草稿使用结构化幂等凭据和乐观版本 | 采购申请/排产方案持久化 decisionRunId、actionId、idempotencyKey（排产另含 scenario/workOrderIds），租户级唯一键防重复；补偿使用版本 + 来源条件 CAS，不依赖 remark 或秒级时间戳 |

## 2. 范围与非范围

### 2.1 竞赛版必须覆盖

1. 从销售订单、生产工单或排产方案触发交付风险分析；
2. 汇总订单、BOM/MRP、库存、在途采购、工艺路线、产能与当前排程证据；
3. 运行缺料风险推演；
4. 运行 EDD、CR、PRIORITY 等 APS 方案比较；
5. 计算基线风险、方案 KPI 和确定性排序；
6. 生成带证据引用的 AI 决策说明；
7. 通过服务端策略校验数值和动作；
8. 生成可审批动作建议；
9. PC 和 App 支持批准、驳回、重新推演与查看执行结果；
10. 批准后安全创建草稿、待办或通知；
11. 全链路记录运行、证据、动作、Flow 实例和评测指标；
12. 提供一键演示数据和可重复 Benchmark。

### 2.2 竞赛版明确不做

1. 不从零实现预测性维护模型；
2. 不新增模型厂商、文生图或 MCP 市场功能；
3. 不全面重构现有 `AiServiceFacade`；
4. 不在比赛前升级 LangChain4j 主版本；
5. 不替换现有 APS 为复杂数学优化器；
6. 不让 LLM 直接执行 INSERT/UPDATE/DELETE；
7. 不自动发布排产或自动审批采购单；
8. 不以“展示推理过程”作为核心创新；
9. 不制作与主场景无关的大量管理 CRUD 页面；
10. 不将质量分析、设备运维作为第二条同等规模主线。

### 2.3 长期兼容目标

本设计的 Port、证据模型、动作模型、评测模型和 UI 组件必须支持后续扩展到：

- 质量异常根因分析；
- 设备预测性维护；
- 库存与自动补货；
- 供应商风险；
- 经营分析；
- 跨工厂资源协调；
- 高级 APS 与数字孪生推演。

### 4.2 模块依赖边界

```text
ruoyi-common-ai
  ├── 决策实体、DTO、枚举
  ├── IndustrialDecisionDataPort
  └── DecisionWorkflowPort
       ▲                  ▲
       │                  │
ruoyi-erp             ruoyi-flow
实现 ERP Adapter       实现 Flow Adapter
       ▲                  ▲
       └────────┬─────────┘
                │ runtime beans
             ruoyi-ai
       Controller / Orchestrator /
       Policy / Prompt / SSE / Service
```

约束：

- `ruoyi-ai` 不直接依赖 `ruoyi-erp`；
- `ruoyi-ai` 不直接依赖 `ruoyi-flow`；
- `ruoyi-erp` 和 `ruoyi-flow` 分别实现 `ruoyi-common-ai` 中的 Port；
- `ruoyi-flow` 可继续依赖 `ruoyi-ai`，不存在反向编译依赖；
- Decision 功能开启时要求最终应用同时装配 ERP 与 Flow Adapter；
- 所有 Port 调用均携带 tenantId、userId、runId，不依赖隐式线程上下文作为唯一来源。

### 4.3 配置开关

建议新增配置前缀：

```yaml
nexus:
  ai:
    decision:
      enabled: true
      max-concurrent-runs: 4
      max-scenarios: 4
      analysis-timeout-seconds: 60
      action-timeout-seconds: 30
      stale-threshold-seconds: 300
      require-approval-levels: HIGH,CRITICAL
      allow-auto-low-risk-notify: true
      benchmark-mode: false
      default-horizon-days: 30
      max-horizon-days: 90
```

比赛环境固定启用；普通部署可通过 `enabled=false` 完全隐藏菜单和接口。

## 5. 核心业务场景

### 5.1 标准演示事件

比赛演示使用一个可重复的数据故事：

1. 客户销售订单存在明确交期；
2. 订单已经形成生产工单和物料需求；
3. 一个关键物料预计到货日期延后；
4. 一个瓶颈工作站在未来若干天可用产能下降；
5. 当前排程将产生拖期；
6. 系统自动或由用户触发交付风险分析；
7. 系统比较当前方案、催货方案、重排方案和组合方案；
8. 用户批准推荐方案；
9. 系统创建催货通知、排程草稿和相关待办；
10. 系统显示执行结果和风险变化。

演示数据必须由初始化脚本或数据工厂生成，禁止依赖人工临时修改数据库。

### 5.2 支持的触发入口

| 入口 | 触发参数 | 默认行为 |
|---|---|---|
| 销售订单详情 | `bizType=SALES_ORDER, bizId=orderId` | 分析订单能否按期交付 |
| 生产工单详情 | `bizType=WORK_ORDER, bizId=woId` | 分析工单缺料与排产风险 |
| APS 方案页 | `bizType=SCHEDULE_PLAN, bizId=planId` | 解读当前方案并与备选策略比较 |
| 缺料风险页 | `bizType=SHORTAGE_HORIZON, horizonDays=N` | 汇总未来 N 天交付影响 |
| AI 助手 | 自然语言 + 可选业务上下文 | 先解析业务引用，确认后启动 Decision Run |
| 系统事件 | `triggerType=EVENT` + event payload | 创建待分析运行并通知负责人 |

竞赛版优先实现前三个显式入口；自然语言自动抽取业务 ID 和事件自动触发列为 P1。

## 6. 状态机设计

### 6.1 Decision Run 状态

```text
CREATED
   │
   ▼
RUNNING
   ├── 无风险 ───────────────► SUCCEEDED
   ├── 节点失败且不可恢复 ───► FAILED
   └── 生成动作建议
             │
             ▼
      WAITING_APPROVAL
       ├── 驳回 ─────────────► REJECTED
       ├── 数据已过期 ───────► STALE
       │                           └── 创建替代运行 ─► SUPERSEDED
       └── 批准
             │
             ▼
          APPROVED
             │
             ▼
         EXECUTING
       ├── 全部成功 ─────────► SUCCEEDED
       ├── 部分成功 ─────────► PARTIAL_SUCCESS
       ├── 可补偿失败 ───────► ROLLING_BACK ─► FAILED/ROLLED_BACK
       └── 取消 ─────────────► CANCELLED
```

状态转换只能由服务端状态机执行，Controller 不允许直接更新状态字段。

### 6.2 Action 状态

```text
PROPOSED
  ├── 需要审批 ─────────► PENDING_APPROVAL
  └── 低风险自动通知 ───► APPROVED

PENDING_APPROVAL
  ├── APPROVED
  └── REJECTED

APPROVED
  └── EXECUTING
        ├── SUCCEEDED
        ├── FAILED
        ├── COMPENSATING
        │      ├── COMPENSATED
        │      └── COMPENSATE_FAILED
        └── SKIPPED
```

### 6.3 并发与幂等规则

1. 同一租户、同一 `bizType + bizId + sceneCode` 在 `RUNNING` 时禁止重复启动；
2. 用户可选择“取消旧运行并重新分析”；
3. 审批接口使用 `runId + version` 乐观锁；
4. 动作使用 `tenantId + actionType + bizRef + runId` 生成幂等键；
5. 重试动作复用原幂等键，不创建重复业务单据；
6. 同一动作只允许一个线程从 `APPROVED` CAS 到 `EXECUTING`；
7. Flow 重试不得绕过 Decision Action 状态检查。

## 7. 风险计算与方案排名

### 7.1 交付风险评分

风险分数范围为 0–100，由服务端计算并记录评分配置版本。比赛版默认权重：

| 维度 | 最大分 | 计算依据 |
|---|---:|---|
| 预计拖期 | 40 | APS 完工日与承诺交期的差值 |
| 物料短缺 | 30 | 最早缺料日、关键件缺口、在途覆盖情况 |
| 产能瓶颈 | 20 | 最大资源利用率、超负荷小时和不可用日 |
| 供应风险 | 10 | 供应商准时率、预计到货偏差；无可靠数据时该维度记 0 并标记“证据不足” |

默认分段：

```text
0  - 19  LOW
20 - 39  MEDIUM
40 - 69  HIGH
70 - 100 CRITICAL
```

拖期子分建议：

| 预计拖期 | 分数 |
|---|---:|
| 不拖期 | 0 |
| 1–2 天 | 15 |
| 3–5 天 | 25 |
| 6 天及以上 | 40 |

缺料、瓶颈和供应风险使用相同的配置化分段方式。配置保存在 `ai_config`，运行时将最终权重快照写入 `ai_decision_run.score_config_json`。

### 7.2 场景覆盖参数

```text
ScenarioOverride
├── scenarioCode
├── scenarioName
├── schedulingStrategy        EDD/CR/PRIORITY/CURRENT
├── horizonDays
├── purchaseArrivalOverrides  物料/采购行 → 新预计到货日
├── capacityOverrides         资源/日期 → 可用工时变化
├── workOrderPriorityOverrides
├── outsourceStepOverrides
├── overtimeCost
├── expediteCost
└── note
```

比赛版内置场景：

1. `BASELINE_CURRENT`：当前数据和当前排产；
2. `APS_EDD`：最早交期优先；
3. `APS_CR`：临界比优先；
4. `APS_CR_EXPEDITE`：临界比重排 + 关键物料催货假设。

若当前页面明确选择其他策略，可替换内置第四方案，但总方案数不得超过配置 `max-scenarios`。

### 7.3 现有算法边界与方案可行性门（评审修订）

现有 `PrdScheduleEngine` 只按工艺路线和日产能前向排程，**并不将物料可用日期作为工序开工硬约束**。因此“催货 + CR 重排”不能天然计算出比 CR 更早的 APS 完工日。竞赛版必须明确区分：

- **APS 排程 KPI**：仅表示产能与工艺约束下的模拟结果；
- **物料可行性**：由缺料模拟在每个物料需求日独立验证；
- **组合方案**：物料到货覆盖能改善“缺料风险/可行性”，但在未实现物料约束排程之前，不得声称催货缩短了 APS 排程工期、拖期天数或已经实际改善订单交付；
- 若未实现工单级物料齐套日与 APS 的硬约束耦合，`APS_CR_EXPEDITE` 与 `APS_CR` 的排产工期 KPI 必须保持相同；只有缺料指标和可行性标记可以不同；
- 项目评测和路演将该限制写为已知边界，而非模型预测能力。

详情见 `PrdScheduleEngine.schedule()`、`PrdShortageSimulator.simulate(input, today)`。后续高级 APS 阶段再考虑物料硬约束耦合。

### 7.3 方案 KPI

每个方案必须输出：

- 受影响订单数；
- 拖期工单数；
- 总拖期天数；
- 最大拖期天数；
- Makespan；
- 缺料物料数；
- 总缺口量；
- 最早缺料日；
- 最大资源利用率；
- 超负荷资源数；
- 计划变更工单数；
- 催货/加班/委外等代理成本；
- 可行性标记；
- 不可行原因。

### 7.4 确定性方案评分

采用“越低越优”的归一化加权评分：

```text
objectiveScore =
    0.30 * normalized(totalTardinessDays)
  + 0.20 * normalized(delayedWorkOrderCount)
  + 0.15 * normalized(shortageGap)
  + 0.10 * normalized(maxResourceUtilizationPenalty)
  + 0.10 * normalized(actionCost)
  + 0.10 * normalized(planChangeCount)
  + 0.05 * infeasiblePenalty
```

规则：

1. 不可行方案始终排在可行方案之后；
2. 归一化范围基于本次候选方案集合；
3. 全部指标相同时优先变更更少的方案；
4. 再相同时优先不需要外协/加班的方案；
5. 最终再按 `scenarioCode` 排序，保证结果确定；
6. LLM 只能解释排名，不能修改 `objectiveScore` 或 `recommendedScenarioCode`。

### 9.2 D01——业务上下文快照

**Flow nodeType**：`industrial.deliveryContext`
**Provider**：`DeliveryContextNodeProvider`
**核心服务**：`IndustrialDecisionDataPort.loadDeliveryContext()`
**超时**：10 秒
**重试**：最多 1 次，仅重试瞬时数据源异常

#### 节点参数 Schema

| 参数 | 类型 | 默认值 | 说明 |
|---|---|---:|---|
| `includeSupplier` | boolean | true | 加载供应商交付表现 |
| `includeCapacity` | boolean | true | 加载产能日历、排班、请假 |
| `includeCurrentSchedule` | boolean | true | 加载当前排产方案 |
| `maxOrderLines` | number | 200 | 最大订单/物料明细数 |
| `horizonDays` | expression | `{{input.horizonDays}}` | 推演跨度 |

#### 输入

- runId；
- bizType、bizId；
- horizonDays；
- tenantId；
- 可选场景覆盖参数。

#### 处理逻辑

1. 根据业务入口解析根业务对象；
2. 销售订单入口：加载订单头、订单行、承诺交期和状态；
3. 工单入口：反查来源订单或生产计划；
4. 排产方案入口：加载方案关联工单；
5. 加载关联工单剩余数量、计划起止和优先级；
6. 加载当前版本工艺路线和步骤；
7. 加载 MRP 未发料需求；
8. 加载库存、预留、安全库存；
9. 加载有效在途采购和预计到货日期；
10. 加载产能日历、排班、班次、节假日和请假影响；
11. 加载当前排程任务与资源负荷；
12. 可选加载供应商评价；
13. 对快照字段进行白名单裁剪和脱敏；
14. 对完整快照生成稳定排序的 canonical JSON，写入 `ai_decision_run.input_snapshot_json`；
15. 另行构造可重算的 `CriticalFreshnessFingerprint`：订单/工单状态与交期、需求、库存/预留、采购到货、当前路线与产能版本、当前排产版本；排除 `snapshotAt`、warnings 和纯展示字段；
16. 对关键指纹 canonical JSON 计算 SHA-256，并写入 `snapshotHash` / `input_snapshot_hash`；
17. 将关键业务字段转换为 EvidenceItem；
18. 输出 `DeliveryContextSnapshot`。

#### 输出

```text
DeliveryContextSnapshot
├── rootBusinessRef
├── salesOrders[]
├── workOrders[]
├── routingByMaterial
├── materialRequirements[]
├── stockBalances[]
├── purchaseArrivals[]
├── capacityByDate
├── holidays[]
├── currentSchedule
├── supplierMetrics[]
├── snapshotHash
├── snapshotAt
└── warnings[]
```

#### 数据一致性

- 快照读取在同一 Decision Run 中只执行一次；
- 不要求跨库强事务，但记录各数据域的最大 `update_time`；
- 审批时重新读取关键版本字段进行新鲜度校验；
- `checkFreshness(ref, expectedHash, actor)` 重算同一关键指纹；比赛版仅持久化总 SHA-256，因此不一致时 `changedFields` 返回稳定类别 `criticalSnapshotHash`，赛后可在快照 JSON 中增加分域摘要以定位具体字段；
- 销售订单与工单的权威关联优先使用 `so_sales_order_line.line_id → prd_production_plan.order_line_id → prd_work_order.plan_id`，物料需求工单再以 `source_type=MATERIAL_REQUIREMENT + source_id=requirement_id` 精确绑定；`sourceId/sourceLineId/sourceNo` 仅兼容历史直连数据，且不得用于 MATERIAL_REQUIREMENT 回退；
- 决策事实 scope 与 APS 可排候选分离：审批中工单可作为事实存在，但只有 CREATED/APPROVED/RELEASED/IN_PROGRESS 进入重排；指定排产方案即使工单均已终态，方案及全部任务版本仍进入 freshness 指纹；
- 固定窗口使用 Asia/Shanghai 业务日和半开 DATETIME 区间 `[start, end+1day)`；`java.sql.Date` 保持纯日期语义。APS 路线、产能、排班和 freshness 来源只读取明确关联的物料、车间和工位，无关资源变化不得使运行过期；
- 若业务对象已关闭、删除或跨租户，运行失败；
- 某非关键域不可用时可降级，例如供应商指标缺失只产生 warning。

#### 失败与降级

| 情况 | 行为 |
|---|---|
| 根业务对象不存在 | 失败 `BIZ_NOT_FOUND` |
| 无关联工单 | 继续运行，标记 `NO_WORK_ORDER`，只分析物料/订单风险 |
| 无工艺路线 | 对相关工单标记不可排产，不阻断其他工单 |
| 无产能日历 | 沿用现有 APS 默认 8 小时/日规则，并记录证据警告 |
| 供应商指标不可用 | 供应风险分记 0，标记“证据不足” |

#### 安全

- Adapter 内部使用 ERP Service，不向 AI 暴露 Mapper；
- tenantId 显式传入并二次校验；
- 不保存手机号、身份证、完整地址等非必要信息；
- 快照 JSON 最大 512 KB，超限时保留汇总和前 N 条明细。

### 9.3 D02——基线风险计算

**Flow nodeType**：`industrial.baselineRisk`
**Provider**：`BaselineRiskNodeProvider`
**核心服务**：`DeliveryRiskScoringService`
**超时**：5 秒
**重试**：不重试；纯函数应稳定执行

#### 输入

- `DeliveryContextSnapshot`；
- 风险评分配置快照；
- 当前排产和当前采购到货数据。

#### 处理逻辑

1. 识别每个订单关联的未完工工单；
2. 读取当前排程末序预计完工日；
3. 无当前排程时，以工单计划结束日作为低可信基线；
4. 计算预计拖期天数；
5. 汇总关键物料短缺信号；
6. 汇总最大资源利用率和超负荷资源；
7. 汇总供应商准时率和到货偏差；
8. 按评分配置计算四个子分和总分；
9. 计算风险等级；
10. 生成根因候选，但只使用确定性原因编码；
11. 生成基线 EvidenceItem；
12. 输出 `BaselineRiskResult`。

#### 根因编码

| 编码 | 含义 |
|---|---|
| `MATERIAL_SHORTAGE` | 关键物料在需求日前无法齐套 |
| `PURCHASE_DELAY` | 在途采购晚于需求日 |
| `CAPACITY_OVERLOAD` | 资源负荷超过阈值 |
| `ROUTING_MISSING` | 工单缺工艺路线 |
| `SCHEDULE_DELAY` | 当前排程完工日晚于交期 |
| `SUPPLIER_LOW_OTD` | 供应商准时率低于阈值 |
| `NO_CURRENT_SCHEDULE` | 缺少可信当前排程 |

#### 输出

```text
BaselineRiskResult
├── riskScore
├── riskLevel
├── dimensionScores
├── impactedOrders[]
├── rootCauseCodes[]
├── baselineKpis
├── confidence
└── evidenceRefs[]
```

#### 置信度

置信度不是 LLM 生成值，而按数据完整度计算：

- 有当前排程、齐全工艺路线、库存、MRP、采购、产能：`HIGH`；
- 缺一个非关键域：`MEDIUM`；
- 无当前排程或大量工艺路线缺失：`LOW`。

当置信度为 LOW 时，前端必须显示“数据不完整，建议先完善排产/工艺数据”。

### 9.4 D03——缺料风险推演

**Flow nodeType**：`industrial.shortageSimulation`
**Provider**：`ShortageSimulationNodeProvider`
**核心服务**：复用 `PrdShortageSimulator`，通过 ERP Adapter 调用
**超时**：10 秒
**重试**：最多 1 次

#### 节点参数 Schema

| 参数 | 类型 | 默认值 | 说明 |
|---|---|---:|---|
| `horizonDays` | expression/number | 30 | 1–90 |
| `includeSafetyStock` | boolean | true | 是否扣除安全库存 |
| `includeOnOrder` | boolean | true | 是否计入有效在途采购 |
| `criticalOnly` | boolean | false | 是否只返回影响当前订单的物料 |
| `maxResults` | number | 100 | 最大明细数 |

#### 输入

- 物料需求；
- 当前可用库存；
- 安全库存；
- 在途采购及到货日；
- 场景中的到货日期覆盖；
- horizonDays。

#### 处理逻辑

1. 按物料和需求日汇总未发料需求；
2. 按日期推进余额：`可用库存 + 累计到货 - 累计需求 - 安全库存`；
3. 首次余额小于 0 的日期为最早缺料日；
4. 记录最大缺口；
5. 判断在途是否可覆盖；
6. 计算影响工单和销售订单；
7. 对关键件优先排序；
8. 根据场景覆盖重新计算到货日，不写回业务库；
9. 生成建议编码：`NO_RISK`、`EXPEDITE`、`NEW_PURCHASE`、`RESCHEDULE`；
10. 将所有数值绑定到库存、MRP 和采购 EvidenceItem。

#### 输出

```text
ShortageSimulationResult
├── hasRisk
├── riskMaterialCount
├── earliestShortageDate
├── totalGap
├── items[]
│   ├── materialRef
│   ├── firstShortageDate
│   ├── maxGap
│   ├── onOrderQty
│   ├── affectedWorkOrders[]
│   ├── affectedSalesOrders[]
│   └── recommendationCode
├── kpis
└── evidenceRefs[]
```

#### 与现有工具的关系

- `ErpShortageRiskTool` 继续服务通用 Agent 对话；
- Decision 链不得复制其 SQL；
- 新节点直接调用 ERP 业务层的推演输入组装和 `PrdShortageSimulator`；
- 后续应逐步让通用 Tool 也复用同一个 Service，消除两套口径。

#### 降级

- 无 MRP 明细：返回 `NO_REQUIREMENT_DATA`，不视为“无风险”；
- 物料主数据缺失：保留 materialId 并记录警告；
- 到货日期为空：在途不计入可用量，并标记证据不足；
- 单个物料异常不得阻断其他物料计算。

### 9.5 D04——APS 多方案推演

**Flow nodeType**：`industrial.apsCompare`
**Provider**：`ApsScenarioCompareNodeProvider`
**核心服务**：`ApsWhatIfSimulationService`，内部复用 `PrdScheduleEngine`
**超时**：20 秒
**重试**：整体不重试；单个场景失败可隔离

#### 节点参数 Schema

| 参数 | 类型 | 默认值 | 说明 |
|---|---|---:|---|
| `strategies` | multi-select | `EDD,CR,PRIORITY` | 允许策略 |
| `includeCurrent` | boolean | true | 包含当前方案 |
| `horizonDays` | expression/number | 30 | 排程跨度 |
| `maxScenarios` | number | 4 | 最大方案数 |
| `allowCapacityOverride` | boolean | true | 允许场景化产能变化 |
| `allowArrivalOverride` | boolean | true | 允许场景化到货变化 |

#### 输入

- `DeliveryContextSnapshot`；
- `ShortageSimulationResult`；
- 场景列表；
- 工单、工艺路线、产能、节假日；
- 采购到货覆盖和资源产能覆盖。

#### 处理逻辑

1. 构造不可变基础输入；
2. 为每个场景复制可变产能和覆盖参数；
3. 应用工单优先级、采购到货和产能覆盖；
4. 调用 `PrdScheduleEngine.schedule()`；
5. 计算场景内拖期、Makespan、资源负荷和计划变更；
6. 使用场景后的需求时间再次计算缺料影响；
7. 检查工艺路线、跨度和资源约束可行性；
8. 保存场景输入哈希，保证可重放；
9. 生成场景级 EvidenceItem；
10. 单场景失败时记录 `infeasibleReason`，继续其他场景；
11. 所有场景均失败才使节点失败。

#### 输出

```text
ApsScenarioCompareResult
├── scenarios[]
│   ├── scenarioCode
│   ├── scenarioName
│   ├── feasible
│   ├── infeasibleReasons[]
│   ├── strategy
│   ├── overrides
│   ├── kpis
│   ├── delayedOrders[]
│   ├── bottleneckResources[]
│   ├── schedulePreview[]
│   ├── inputHash
│   └── evidenceRefs[]
└── warnings[]
```

#### 约束

- 不把 What-if 结果写入 `prd_schedule_plan`；
- 只有批准 `CREATE_SCHEDULE_PLAN_DRAFT` 动作时才创建未发布的排产方案；
- `schedulePreview` 只保留演示所需汇总和前 N 条任务，完整结果可存 OSS 或压缩 JSON；
- 同一输入和配置必须得到相同结果；
- 不使用 LLM 修改工时、交期或产能。

#### 未来升级兼容

`ApsWhatIfSimulationService` 对外只暴露统一 `ApsSolverPort`。比赛版实现为现有启发式引擎；未来可增加 Timefold/OR-Tools 实现，不影响 Decision 层。

### 9.6 D05——方案汇总与确定性排名

**Flow nodeType**：`industrial.scenarioRank`
**Provider**：`ScenarioRankNodeProvider`
**核心服务**：`DecisionScenarioRankingService`
**超时**：5 秒
**重试**：不重试

#### 输入

- 基线风险；
- 缺料推演；
- APS 场景列表；
- 评分权重；
- 动作代理成本配置。

#### 处理逻辑

1. 校验每个场景 KPI 字段完整性；
2. 对候选集合进行 min-max 归一化；
3. 应用多目标评分；
4. 对不可行方案施加惩罚；
5. 应用确定性 tie-break；
6. 选出推荐场景；
7. 计算相对基线的 KPI 差异；
8. 对“改善为负”或高成本方案添加警告；
9. 生成 `ScenarioComparison`；
10. 记录评分配置、原始 KPI、归一化值和最终分数，保证可解释与可复算。

#### 输出

```text
ScenarioRankingResult
├── baselineScenarioCode
├── recommendedScenarioCode
├── ranking[]
│   ├── scenarioCode
│   ├── rank
│   ├── objectiveScore
│   ├── normalizedMetrics
│   ├── deltaFromBaseline
│   └── selectionReasons[]
├── scoreConfigVersion
└── evidenceRefs[]
```

#### 失败处理

- 只有一个可行方案：直接推荐并标记“无可比较候选”；
- 没有可行方案：不生成执行动作，风险等级至少为 HIGH，建议人工处理；
- KPI 缺失：对应方案不可参与排名，但保留在 UI 中说明原因；
- 权重和不为 1 时由服务端归一化，并记录警告。

### 9.7 D06——规则与 SOP 检索

**Flow nodeType**：复用 `rag`
**核心服务**：`RetrieverService`
**超时**：10 秒
**重试**：失败不重试，直接降级

#### 输入

```text
业务类型 + 风险根因编码 + 物料/工序类别 + 动作类型候选
```

```text
采购到货延迟 关键物料缺料 供应商催货制度 排产调整审批规则
```

1. 选择工业制度/SOP 知识库；

5. 返回结构化 `RetrievalHit`，不得只返回字符串；
6. 记录文档、chunk、分数、图谱路径和版本；
7. 将命中内容标记为“规范性证据”，不得覆盖业务数值证据。

#### 目标结构

```text
RetrievalHit

├── documentName
├── content
├── vectorScore
├── keywordRank
├── rerankScore
├── graphPath
├── version

```

#### 降级

RAG 不可用时：

- 分析继续；
- 决策摘要只使用业务数据和内置规则；
- 前端显示“未引用企业制度知识库”；

## 10. 分析流节点详细设计（D07–D12）

### 10.1 D07——证据标准化与结论绑定

**Flow nodeType**：`industrial.evidenceMerge`
**Provider**：`DecisionEvidenceMergeNodeProvider`
**核心服务**：`DecisionEvidenceService`
**超时**：5 秒
**重试**：不重试

#### 输入

- D01–D06 产生的 EvidenceItem；
- 基线风险；
- 缺料结果；
- 场景和排名；
- RAG 命中。

#### 处理逻辑

1. 按 `sourceType + sourceRef + metricCode + observedAt` 去重；
2. 给每条证据生成稳定 `evidenceKey`；
3. 统一金额、数量、日期、百分比和时长的单位；
4. 绑定业务数据版本和快照哈希；
5. 对数值证据标记 `verifiable=true`；
6. 对 RAG/SOP 证据标记 `normative=true`；
7. 对推导值记录 `derivedFromEvidenceKeys`；
8. 禁止形成无来源的数值结论；
9. 批量写入 `ai_decision_evidence`；
10. 生成供 LLM 使用的精简证据包，限制总字符数；
11. 生成前端证据树。

#### EvidenceItem 结构

```text
EvidenceItem
├── evidenceKey
├── runId
├── sourceDomain       ERP/MES/IOT/RAG/RULE/DERIVED
├── sourceType         SALES_ORDER/WORK_ORDER/STOCK/...
├── sourceId
├── sourceCode
├── sourceName
├── metricCode
├── metricName
├── valueType
├── value
├── unit
├── observedAt
├── dataVersion
├── confidence
├── verifiable
├── normative
├── derivedFromEvidenceKeys[]
└── displayPath
```

#### 数值绑定规则

- `expectedDelayDays` 必须引用订单交期和 APS 完工日；
- `shortageGap` 必须引用 MRP、库存、安全库存和在途；
- `resourceUtilization` 必须引用可用工时与已排工时；
- `supplierOnTimeRate` 必须引用评价周期和样本量；
- 所有派生值在后端重新计算，不能直接信任节点传入的字符串。

#### 失败处理

证据入库失败视为关键失败，不允许继续生成“无证据决策”；数据库短暂异常可由 Flow 节点重试一次。

### 10.2 D08——LLM 决策摘要

**Flow nodeType**：复用 `llm`，使用专用场景模板
**核心服务**：`DecisionSummaryService`
**超时**：30 秒
**重试**：最多 1 次；第二次使用更严格、短输出 Prompt

#### 输入

仅允许以下经过服务端裁剪的数据进入 Prompt：

- 用户问题；
- 业务对象摘要；
- 风险分数和等级；
- 根因编码；
- 方案排名和 KPI；
- 证据键及展示摘要；
- SOP/RAG 片段；
- 允许的动作类型；
- 输出 JSON Schema。

禁止输入：

- API Key；
- 用户 Token；
- 数据库凭证；
- 无关个人隐私；
- 未脱敏异常堆栈；
- 可被执行的任意 SQL；
- MCP 市场未授权工具描述。

#### Prompt 目标

模型只生成：

```text
DecisionNarrative
├── executiveSummary
├── riskExplanation
├── rootCauseExplanations[]
├── scenarioTradeoffs[]
├── recommendationRationale
├── evidenceCitations[]
├── uncertaintyNotes[]
└── operatorChecklist[]
```

模型不得生成：

- 新的 KPI 数值；
- 不在输入中的物料、订单或资源；
- 不在白名单中的动作；
- “已执行”“已审批”等虚假状态；
- 详细隐藏推理链。

#### 输出约束

- 使用 JSON Schema/结构化输出；
- 所有数值引用只使用 `evidenceKey`，显示值由后端填充；
- 中文输出；
- 摘要建议不超过 800 字；
- 单个方案解释不超过 200 字；
- 不落库保存原始 chain-of-thought，只保存最终摘要和必要的简短理由。

#### 降级策略

1. 模型超时或 JSON 解析失败：重试一次；
2. 第二次失败：使用服务端模板生成摘要；
3. 模型不可用不影响风险计算、方案排名和审批；
4. 模板化摘要仍必须展示完整证据和方案 KPI；
5. 降级结果标记 `summaryMode=TEMPLATE_FALLBACK`。

#### Token 与成本

- 独立记录 decision run 的 input/output tokens；
- 将 modelId、modelName、Prompt 版本写入 run；
- 不与通用 chat session 强绑定；
- 日统计继续写入 `ai_token_usage`。

### 10.3 D09——决策策略校验

**Flow nodeType**：`industrial.decisionGuard`
**Provider**：`DecisionPolicyGuardNodeProvider`
**核心服务**：`DecisionPolicyGuardService`
**超时**：5 秒
**重试**：不自动重试；可要求 D08 重新生成一次

#### 节点参数 Schema

| 参数 | 类型 | 默认值 | 说明 |
|---|---|---:|---|
| `requireEvidenceForNumeric` | boolean | true | 数值必须有证据 |
| `allowedActionTypes` | multi-select | 场景白名单 | 允许动作 |
| `maxNarrativeLength` | number | 5000 | 最大摘要长度 |
| `blockOnStaleEvidence` | boolean | true | 过期证据阻断 |
| `requireApprovalLevels` | multi-select | HIGH,CRITICAL | 强制审批等级 |

#### 校验项

1. 所有数值引用的 evidenceKey 存在；
2. 摘要中引用的订单/物料/资源存在于快照；
3. 推荐场景与 D05 确定性排名一致；
4. 不允许模型自行提高或降低风险等级；
5. 动作类型位于场景白名单；
6. 动作参数引用合法业务对象；
7. HIGH/CRITICAL 动作必须审批；
8. 不允许发布、审批、过账、库存扣减等不可逆动作；
9. RAG 文本中的指令不得覆盖系统策略；
10. 文本不得包含疑似密钥、Authorization 或数据库连接信息；
11. 快照未超过可接受时效；
12. 不允许将“建议”描述成“已经执行”。

#### 输出

```text
DecisionPolicyResult
├── passed
├── violations[]
│   ├── code
│   ├── severity
│   ├── fieldPath
│   └── message
├── sanitizedNarrative
├── requiresRegeneration
└── forcedApproval
```

#### 处理规则

- `WARN`：保留结果并展示警告；
- `ERROR`：要求 D08 重新生成一次；
- `BLOCK`：停止自动建议，改用模板化摘要；
- 任何动作安全违规均为 `BLOCK`；
- Guard 失败本身必须入审计日志。

### 10.4 D10——动作建议生成

**Flow nodeType**：`industrial.actionProposal`
**Provider**：`DecisionActionProposalNodeProvider`
**核心服务**：`DecisionActionProposalService`
**超时**：5 秒
**重试**：不重试

#### 动作白名单

| actionType | 竞赛版 | 风险等级 | 说明 |
|---|---|---|---|
| `SEND_EXPEDITE_NOTICE` | 支持 | LOW | 发送采购催货通知，不修改订单 |
| `CREATE_PURCHASE_REQUISITION_DRAFT` | 支持 | MEDIUM | 创建采购申请草稿 |
| `CREATE_SCHEDULE_PLAN_DRAFT` | 支持 | MEDIUM | 依据推荐场景创建 APS 草稿 |
| `CREATE_WORKFLOW_TODO` | 赛后 | LOW | 仅在真实创建 Flowable 任务并取得 taskId 后支持；竞赛版用决策模块审批入口 + `SEND_MANAGER_NOTIFICATION` |
| `SEND_MANAGER_NOTIFICATION` | 支持 | LOW | 系统/IM 通知 |
| `CREATE_SUBCONTRACT_SUGGESTION` | 可选 | MEDIUM | 只创建建议，不直接下委外单 |
| `PUBLISH_SCHEDULE_PLAN` | 禁止 | HIGH | 必须由生产主管在业务页面发布 |
| `APPROVE_PURCHASE_ORDER` | 禁止 | HIGH | 不允许 AI 审批 |
| `POST_INVENTORY_TRANSACTION` | 禁止 | CRITICAL | 不允许 AI 直接过账 |

#### 生成逻辑

动作不由 LLM 自由构造，而由确定性规则根据根因和推荐场景生成：

```text
PURCHASE_DELAY + 在途可覆盖
    → SEND_EXPEDITE_NOTICE

MATERIAL_SHORTAGE + 在途不足
    → CREATE_PURCHASE_REQUISITION_DRAFT

SCHEDULE_DELAY + 推荐场景优于基线
    → CREATE_SCHEDULE_PLAN_DRAFT

HIGH/CRITICAL
    → SEND_MANAGER_NOTIFICATION（提醒审批人进入 Decision 模块审批，不冒充 Flowable 待办）
```

LLM 只允许补充 `displayReason`，不决定 actionType 和关键 payload。

#### 输出

```text
DecisionActionProposal
├── actionType
├── title
├── displayReason
├── targetBusinessRef
├── payload
├── riskLevel
├── approvalRequired
├── permissionCode
├── idempotencyKey
├── executorCode
├── sequence
└── dependencies[]
```

#### 入库

- 每个动作写入 `ai_decision_action`，状态 `PROPOSED`；
- action payload 使用白名单 DTO 序列化；
- 不保存可执行脚本；
- 幂等键在入库前生成；
- 动作依赖形成有向无环关系，例如先创建采购草稿，再通知负责人。

### 10.5 D11——审批策略判定

**实现**：`DecisionApprovalPolicyService`
**节点类型**：Decision 服务逻辑节点
**超时**：3 秒

#### 判定规则

1. 无风险且无动作：直接 `SUCCEEDED`；
2. 只有低风险通知动作且配置允许：动作自动置 `APPROVED`，进入执行流；
3. 存在创建业务草稿动作：进入 `WAITING_APPROVAL`；
4. 风险等级 HIGH/CRITICAL：强制审批；
5. 用户无目标动作权限：动作保留但标记 `NOT_AUTHORIZED`，不可批准；
6. 多动作中任一需要审批：整个运行进入 `WAITING_APPROVAL`；
7. 支持用户只批准部分动作，未批准动作置 `REJECTED`；
8. 批准人必须拥有 `ai:decision:approve` 及对应业务权限；
9. 可配置禁止发起人自审批，比赛版默认允许同一管理员操作以简化演示，但审计中明确记录。

#### 输出

- run 状态；
- 可审批动作列表；
- 缺失权限列表；
- 审批提示；
- 数据有效截止时间 `validUntil`。

---

### 10.6 D12——结果发布与等待用户操作

**实现**：`AiDecisionSseMessageHelper`、Decision 查询接口
**超时**：不占用 Flow 工作线程

#### 处理逻辑

1. 将完整 `DecisionResult` 写入 `ai_decision_run.result_json`；
2. 更新状态为 `WAITING_APPROVAL` 或 `SUCCEEDED`；
3. 结束分析 Flow 实例；
4. 发布 `AI_DECISION_READY`；
5. 推送风险摘要、方案比较、证据数量和动作数量；
6. 前端随后通过 GET API 拉取完整结果；
7. 不在 SSE 中推送超大快照或完整排程任务；
8. 若需要审批，创建系统通知和 App 待处理入口；
9. 记录分析总耗时、模型耗时和节点耗时。

#### 重要约束

`WAITING_APPROVAL` 不是 Flow 引擎线程上的阻塞等待。分析 Flow 已完成，审批后另启执行 Flow，避免 `Thread.sleep`、长超时和服务重启丢失等待状态。

## 11. 执行流节点详细设计（E00–E05）

### 11.1 E00——审批与数据新鲜度复核

**实现**：`DecisionApprovalService.approve()`
**超时**：10 秒
**重试**：用户可重新提交，但每次均受版本检查

#### 输入

```text
DecisionApprovalRequest
├── runId
├── runVersion
├── approvedActionIds[]
├── rejectedActionIds[]
├── comment
└── expectedSnapshotHash
```

#### 处理逻辑

1. 校验 run 属于当前租户；
2. 校验状态为 `WAITING_APPROVAL`；
3. 校验乐观锁版本；
4. 校验批准人权限；
5. 校验 actionId 全部属于该 run；
6. 重新读取订单状态、关键到货日、库存版本、工单状态和排产版本；
7. 重新计算关键数据哈希；
8. 若数据变化超过阈值，将 run 置 `STALE`，拒绝执行；
9. 对批准动作置 `APPROVED`，驳回动作置 `REJECTED`；
10. 记录审批人、时间、意见和客户端；
11. run 状态更新为 `APPROVED`；
12. 启动执行 Flow，状态进入 `EXECUTING`；
13. 发布审批和执行开始事件。

#### 新鲜度规则

以下任一变化必须重新推演：

- 订单已关闭/取消或交期变化；
- 工单状态进入终态；
- 关键物料库存或预留量变化超过配置阈值；
- 采购预计到货日期变化；
- 当前排产方案版本变化；
- 推荐场景依赖的资源产能发生变化。

仅备注、非关键描述字段变化不使运行过期。

---

### 11.2 E01——动作排序与执行计划生成

**实现**：`DecisionActionExecutionPlanner`
**超时**：3 秒

#### 处理逻辑

1. 读取所有 APPROVED 动作；
2. 校验依赖图无环；
3. 按依赖、sequence、风险等级排序；
4. 将可并行动作分组；
5. 为每个动作解析 `DecisionActionExecutor`；
6. 校验 Executor 当前可用；
7. 生成执行计划和补偿计划；
8. 对不存在 Executor 的动作置 `FAILED_PRECHECK`，不启动其他依赖动作；
9. 将执行计划摘要写入 run。

#### 默认执行顺序

1. 创建排产/采购草稿；
2. 创建工作流待办；
3. 发送催货通知；
4. 发送管理通知；
5. 写入评测与跟踪任务。

通知动作不应先于关键草稿创建成功，避免出现“已创建”但实际失败的消息。

---

### 11.3 E02——业务动作执行

**实现**：`DecisionActionExecutionService` + `DecisionActionExecutor` SPI
**超时**：单动作 30 秒
**重试**：默认 2 次，指数退避；业务校验失败不重试

#### Executor SPI

```text
DecisionActionExecutor
├── supports(actionType)
├── precheck(context, action)
├── execute(context, action)
├── verify(context, action, result)
├── compensate(context, action, result)
└── isRetryable(error)
```

#### 竞赛版 Executor

##### 1. SendExpediteNoticeExecutor

- 调用系统通知/IM 服务；
- 目标为采购负责人或配置角色；
- 内容引用物料、需求日、在途和缺口证据；
- 结果保存通知 ID；
- 幂等键防止重复通知；
- 无补偿。

##### 2. CreatePurchaseRequisitionDraftExecutor

- `pu_purchase_requisition` 持久化 `decision_run_id`、`decision_action_id`、`decision_idempotency_key` 和 `version`；唯一键 `(tenant_id, decision_idempotency_key)`；
- 调用采购申请业务 Service 的幂等 `createDraft()`：首次 insert 返回 ID；重试命中相同 key 时重读并返回同一业务对象，不通过 remark 反查；
- 只创建 DRAFT，数量来自确定性缺口并受 `decimal(18,4)` 精度与最大值校验；
- execute 创建与创建后重读处于同一 ERP 本地事务，后置校验失败会回滚首次创建；
- verify 校验结构化来源、业务编号、需求日期和完整物料/数量明细；
- 补偿条件为 `requisitionId + DRAFT + version + runId + actionId + idempotencyKey`，与人工编辑/提交使用相同乐观版本协议；
- 不允许自动提交审批。

##### 3. CreateSchedulePlanDraftExecutor

- `prd_schedule_plan` 持久化 `decision_run_id`、`decision_action_id`、`decision_idempotency_key`、`decision_scenario_code`、`decision_work_order_ids_json` 和 `version`；唯一键 `(tenant_id, decision_idempotency_key)`；
- 使用推荐场景输入调用幂等 scoped `runSchedule(bo, workOrderIds)`，只持久化 payload 指定工单；重试返回同一方案；
- 新方案状态为 `COMPLETED`（现有 ERP 无 `DRAFT` 状态）；`BASELINE_CURRENT/CURRENT` 禁止创建，`APS_EDD → EDD`，`APS_CR/APS_CR_EXPEDITE → CR`；
- execute 与创建后重读在同一 ERP 本地事务；verify 校验结构化来源、scenario、strategy、日期、跨度、车间和 workOrderIds；
- 不自动发布；publish 首先执行 `COMPLETED + version` CAS 抢占 PUBLISHED，再处理任务/工单，CAS 失败不产生副作用；
- 补偿条件为 `planId + COMPLETED + version + runId + actionId + idempotencyKey + scenarioCode`，与 publish 互斥。

##### 4. 移动审批提醒（竞赛版）

- 通过 `SEND_MANAGER_NOTIFICATION` 将链接送至决策模块自身的待审批入口；
- 不向 Flowable 声称创建了不存在的 taskId/processInstanceId；
- 真正的 `CreateWorkflowTodoExecutor` 保留为赛后扩展，需要与 Flowable 待办服务集成。

##### 5. SendManagerNotificationExecutor

- 发送风险摘要和处理链接；
- 不包含敏感明细；
- 支持系统通知和 IM；
- 结果记录通知 ID。

#### 事务边界

- ERP 草稿动作的创建、重读、来源/明细校验和结果构造位于同一个 ERP 本地事务；
- ERP 业务表的 decision idempotency unique key 与业务草稿同事务提交，覆盖“ERP 已提交、AI action 结果未写回”后的重试窗口；
- 每个动作独立本地事务；
- 跨模块不使用分布式大事务；
- MQ 动作使用 `ReliableMessageProducer`；
- run/action 状态通过幂等和最终一致性协调；
- 动作失败不回滚已成功且不可补偿的通知，只将 run 标记为部分成功。

#### 多租户

异步执行必须显式：

1. 从 run 读取 tenantId；
2. 使用 `TenantHelper.dynamic(tenantIdStr, ...)` 包裹写库；
3. 设置必要的 `AiRequestContext`；
4. finally 中清理上下文；
5. 消息中携带 tenantId，消费者恢复后再次校验业务对象归属。

### 11.4 E03——执行结果验证与补偿

**实现**：`DecisionActionVerificationService`
**超时**：每动作 10 秒

#### 验证逻辑

- 通知：目标通知记录存在且状态成功；
- 采购草稿：单据存在、状态 DRAFT、物料和数量符合 payload；
- 排产方案：方案存在、状态为 `COMPLETED` 且未发布、scenarioCode 和 runId 关联可追溯；
- 待办：任务存在且关联 runId；
- 所有返回雪花 ID 按字符串比较。

#### 失败分类

| 分类 | 行为 |
|---|---|
| `TRANSIENT` | 自动重试 |
| `VALIDATION` | 不重试，动作失败 |
| `PERMISSION` | 不重试，记录安全事件 |
| `CONFLICT` | 若关键业务数据已变化则标记 STALE；若为已执行动作结果冲突则标记 FAILED 并转人工处理 |
| `PARTIAL_WRITE` | 尝试补偿 |
| `UNKNOWN` | 不无限重试，转人工处理 |

#### 补偿规则

- 只补偿本 run 创建且仍为草稿/未处理的对象；
- 执行结果保存 `versionMarker=V:<version>`；业务表使用 `@Version`/整数版本，不以 MySQL `datetime(0)` 判断并发修改；
- 补偿以业务 ID + 允许状态 + version + decisionRunId + decisionActionId + idempotencyKey（排产另含 scenarioCode）执行单条条件逻辑删除；
- 人工 edit/submit/publish 与补偿使用同一版本/CAS 协议，任一方抢占成功后另一方必须条件失败且不得提交子表或工单副作用；
- 已进入业务审批、已发布或已被人工修改的对象禁止自动补偿；
- 补偿失败产生高优先级系统通知；
- 所有补偿记录原对象 ID、操作人和原因。

### 11.5 E04——风险结果重新计算

**实现**：`DecisionOutcomeService.recalculate()`
**超时**：20 秒

#### 目标

执行完成后重新读取关键业务数据，计算：

- 风险分数前后变化；
- 拖期工单数变化；
- 总拖期天数变化；
- 缺料物料数和缺口变化；
- 最大资源利用率变化；
- 已创建但尚未生效动作的“预计改善”与“实际改善”区分。

#### 结果类型

```text
DecisionOutcome
├── beforeKpis
├── projectedAfterKpis
├── actualAfterKpis
├── delta
├── effectiveActionIds[]
├── pendingActionIds[]
├── measuredAt
└── outcomeConfidence
```

注意：创建草稿不代表业务已经改善。因此比赛演示中必须区分：

- `projectedAfterKpis`：推荐方案推演结果；
- `actualAfterKpis`：业务动作真正生效后的实际结果。

比赛现场可以展示“预计改善 + 已创建执行载体”，不得把草稿创建描述为实际交付改善已经发生。

### 11.6 E05——通知、归档与评测入库

**实现**：`DecisionFinalizeService`
**超时**：10 秒

#### 处理逻辑

1. 汇总动作状态；
2. 设置 run 为 `SUCCEEDED`、`PARTIAL_SUCCESS` 或 `FAILED`；
3. 写入 outcome JSON；
4. 记录总耗时、节点耗时、Token、成本；
5. 写入 Benchmark/Eval 结果；
6. 发送发起人和审批人通知；
7. 发布 `AI_DECISION_DONE`；
8. 清理运行级临时缓存；
9. 保留 Flow 实例和节点运行记录；
10. 若存在失败动作，通知中提供重试和人工处理入口。

#### 归档策略

- Decision Run、Evidence、Action 默认按业务数据保留策略保存；
- 大体积排程预览可迁移 OSS；
- 日志与 Trace 不保存原始敏感 Prompt；
- 删除业务对象时按项目既有软删除和审计策略处理，不级联物理删除历史决策。

## 13. Port 与服务接口设计

### 13.1 `IndustrialDecisionDataPort`

定义于 `ruoyi-common-ai`，由 `ruoyi-erp` 实现。

```java
public interface IndustrialDecisionDataPort {
    boolean canAccess(DecisionBusinessRef ref, DecisionActor actor);
    DeliveryContextSnapshot loadDeliveryContext(DecisionBusinessRef ref, int horizonDays, DecisionActor actor);
    ShortageSimulationResult simulateShortage(DeliveryContextSnapshot snapshot, int horizonDays,
                                               Map<String, Object> overrides, DecisionActor actor);
    ApsScenarioCompareResult simulateSchedules(DeliveryContextSnapshot snapshot,
                                                List<String> scenarioCodes, int horizonDays, DecisionActor actor);

                                                        DecisionActionExecutionResult result, DecisionActor actor);
    DecisionActionExecutionResult compensateBusinessAction(DecisionActionProposal action,
                                                            DecisionActionExecutionResult result, DecisionActor actor);
}
```

设计原则：

- API 使用公共 DTO，不暴露 ERP Entity/Mapper；
- 读取和写入均显式 tenantId；
- 写动作内部再按 actionType 分发到具体业务 Service；
- Port 不接受任意 SQL；
- 单个方法返回结构化错误码，不返回数据库异常原文。

### 13.2 `DecisionWorkflowPort`

定义于 `ruoyi-common-ai`，由 `ruoyi-flow` 实现。

```java
public interface DecisionWorkflowPort {
    Long startAnalysis(DecisionWorkflowStartCommand command);
    Long startExecution(DecisionWorkflowStartCommand command);
    boolean stop(Long flowInstanceId, DecisionActor actor);
}
```

Flow Adapter 负责：

- 根据 `sceneCode` 找到已发布 Flow Template；
- 启动实例；
- 输入只携带 `runId`；Flow 的可信租户和发起人从 `ai_decision_run`/适配器显式恢复，不信任外部传入的权限和租户；

- 不在 Port 层包含具体业务逻辑。

## 15. SSE 事件协议

沿用公共 SSE 通道，所有 Decision 事件必须包含 `runId`、`seq`、`timestamp`，解决现有聊天事件缺少生成关联 ID 的问题。

### 15.1 事件类型

| type | 用途 |
|---|---|
| `AI_DECISION_STARTED` | 运行已接受 |
| `AI_DECISION_NODE_START` | 节点开始 |
| `AI_DECISION_NODE_END` | 节点完成 |
| `AI_DECISION_WARNING` | 可降级警告 |
| `AI_DECISION_SCENARIO` | 单个方案结果可用 |
| `AI_DECISION_EVIDENCE_READY` | 证据已入库 |
| `AI_DECISION_READY` | 分析完成，可查看/审批 |
| `AI_DECISION_APPROVAL_STATUS` | 批准/驳回/过期 |
| `AI_DECISION_ACTION_STATUS` | 动作状态变化 |
| `AI_DECISION_OUTCOME` | 结果重算完成 |
| `AI_DECISION_DONE` | 全流程结束 |
| `AI_DECISION_ERROR` | 不可恢复错误 |

### 15.2 通用 Payload

```json
{
  "type": "AI_DECISION_NODE_END",
  "runId": "2100000000000000001",
  "flowInstanceId": "2100000000000000100",
  "nodeCode": "D04_APS_COMPARE",
  "nodeName": "APS 多方案推演",
  "status": "SUCCEEDED",
  "seq": 7,
  "durationMs": 1260,
  "summary": "完成 4 个方案推演，3 个可行",
  "timestamp": "2026-09-23T10:00:03+08:00"
}
```

### 15.3 可靠性规则

- SSE 只做实时体验，不作为唯一状态源；
- 页面刷新后通过 REST 恢复完整状态；
- seq 单调递增，前端丢弃重复事件；
- 事件不得包含完整快照或敏感 payload；
- 小程序继续轮询，但按 runId 查询，不再通过消息内容比对；
- PC/App 同时登录可接收同一运行事件，权限仍由查询接口二次验证。

### 20.1 Prompt 分层

1. **System Policy**：角色、安全边界、禁止事项；
2. **Scene Instruction**：交付风险场景输出要求；
3. **Structured Facts**：服务端计算结果；
4. **Evidence Catalog**：evidenceKey 与摘要；
5. **SOP Context**：RAG 命中的企业制度；
6. **Output Schema**：固定 JSON 结构；
7. **User Question**：仅用于调整表达重点。

### 20.2 Prompt 版本

模板键建议：

- `delivery_decision_summary_v1`；
- `delivery_decision_summary_retry_v1`；
- `delivery_decision_fallback_v1` 不调用模型，仅作为服务端模板标识。

每次运行记录实际模板版本和内容 hash，避免模板更新后无法复现历史结果。

### 20.3 Prompt Injection 防护

- RAG 内容用“引用资料”区隔，不得作为系统指令；
- 业务字段中的文本全部视为不可信数据；
- 对“忽略之前指令”“调用某工具”等模式打安全标签；
- Decision Summary 模型不注入任意 MCP Tool；
- 模型没有业务写权限；
- 输出经过 JSON Schema、证据和动作策略校验；
- 检测到高风险注入时改用模板化摘要并产生安全告警。

## 21. 安全设计

### 21.1 权限模型

安全校验顺序：

```text
登录校验
→ Decision 权限
→ 业务对象访问权限
→ 动作审批权限
→ 目标业务新增/操作权限
→ 租户归属复核
→ 状态与幂等校验
```

任何一层失败都不得继续执行。

### 21.2 多租户

- Decision 三表加入多租户拦截；
- 异步任务显式传播 tenantId；
- ERP Adapter 读取和写入都使用 tenantId；
- Flow input 保存 tenantId；
- MQ 消息携带 tenantId；
- 审批时重新校验 run 和业务对象属于同一租户；
- 超级管理员跨租户操作也必须通过明确租户上下文，不能回退 tenant 0。

### 21.3 数据最小化

- Prompt 只包含必要业务字段；
- 不上传身份证、手机号、地址、银行信息；
- 供应商联系人信息默认脱敏；
- 错误信息去除 API Key/Bearer；
- Evidence 保存指标和引用，不复制整张业务表；
- 导出报告遵守当前用户数据权限。

### 21.4 动作安全

- 动作白名单；
- Executor 固定映射；
- payload 使用 DTO 校验；
- 禁止脚本和任意 SQL；
- 高风险强制审批；
- 业务草稿而非最终过账；
- 幂等键；
- 审批时数据新鲜度复核；
- 执行后验证；
- 可补偿动作才允许自动补偿。

### 21.5 外部模型与 MCP

- Decision 核心链默认不使用 MCP 市场工具；
- 若未来启用，仅允许租户管理员明确授权的 Tool；
- Tool 描述和 annotations 视为不可信输入；
- 外部网络访问使用域名/IP 白名单；
- 私有部署可选择 Ollama/本地模型；
- 不因外部模型不可用阻断确定性工业计算。

### 21.6 审计

必须审计：

- 谁发起；
- 使用了哪些数据版本；
- 哪个模型和 Prompt；
- 哪个方案被推荐；
- 哪些证据支撑；
- 谁批准/驳回；
- 执行了哪些动作；
- 创建了哪些业务对象；
- 是否发生重试、补偿或越权尝试。

## 23. 性能与容量设计

### 23.1 性能目标

| 指标 | 竞赛版目标 |
|---|---:|
| 创建 run API | P95 < 1 秒 |
| 上下文快照 | P95 < 5 秒 |
| 缺料推演 | P95 < 5 秒 |
| 4 个 APS 场景 | P95 < 15 秒 |
| LLM 摘要 | P95 < 20 秒，超时降级 |
| 分析总耗时 | P95 < 35 秒 |
| 审批 API | P95 < 3 秒，不含执行流 |
| 单动作执行 | P95 < 10 秒，外部通知除外 |

以上为验收目标，最终材料使用实测值，不把目标值描述为已经达成。

### 23.2 线程池

建议新增独立 `decisionExecutor`：

- corePoolSize：2；
- maxPoolSize：4；
- queueCapacity：20；
- 拒绝时返回系统繁忙并保留 CREATED/REJECTED 状态；
- 不与普通 AI 对话争用全部 `aiExecutor`；
- LLM 调用仍可复用模型客户端，但运行并发受 Decision Semaphore 限制。

### 23.3 数据量限制

- 每次最多 200 个订单行/工单；
- 每次最多 500 个物料需求点；
- 每次最多 4 个场景；
- 每个场景最多返回前 200 条排程预览；
- Evidence 默认最多 1000 条；
- 超限时要求按订单/工厂/日期缩小范围；
- 不允许为了演示关闭所有限制。

### 23.4 缓存

- 工艺路线和主数据可使用已有短期缓存；
- 库存、预留、采购到货和当前排程不使用过期业务缓存作为审批依据；
- run 内使用不可变快照；
- 审批前始终执行关键数据新鲜度复核。

- `ruoyi-ai` 注入 ERP/Flow Port；
- 多租户读取和写入；
- aiExecutor/decisionExecutor 异步上下文；
- Decision 三表落库；
- Flow 实例关联；
- 审批并发；
- Action CAS；
- SSE 包含 runId/seq；
- 模型超时模板降级；
- RAG 失败不阻断；
- 部分动作失败和补偿。

#### 端到端测试

至少覆盖：

1. 销售订单高风险→批准全部动作→成功；
2. 高风险→只批准催货→部分动作被驳回；
3. 等待审批期间库存变化→STALE；
4. 无风险→无动作直接完成；
5. 无工艺路线→低置信度且不生成排产草稿；
6. 模型不可用→模板化摘要；
7. 非法跨租户 runId→拒绝；
8. 重复批准→幂等；
9. 动作执行超时→重试后成功；
10. 草稿创建成功、通知失败→PARTIAL_SUCCESS。

## 33. 安全、真实性与发布门（审查修订，优先于早期概述）

### 33.1 工业 Flow 的可信入口

- `system_delivery_risk_*` 流程是系统专用模板，**禁止**通过通用 `/ai/flow/run`、`run-test`、`run-test-node`、`node-test`、`/ai/flow/instance/{id}/retry` 执行、调试或重试；这些通用入口即使拥有 `ai:flow:*` 权限也不能越权启动工业节点。
- 节点不得从用户可编辑 Flow input 构造 `DecisionActor`。节点只读取 `runId`，然后从受租户过滤的持久化 `ai_decision_run` 装载业务对象、发起人和授权策略；处理线程使用显式、非空的 `tenantId` 在 `TenantHelper.dynamic` 下执行 Port/RAG/Mapper 调用，缺失上下文时拒绝执行。
- 当前租户拦截器在无租户上下文时会放行表的租户过滤；`@DS("erp")` 只切数据源**不等于**权限和租户隔离。因此必须对线程隔离与跨租户读写做反向测试，不能把通用 Text2SQL 作为 Decision 后备路径。
- 业务对象访问不仅要检查“存在”，还要在 ERP 服务层执行用户业务数据权限校验；审批前二次验证业务权限与租户。

### 33.2 流程图版本与运行竞态

- 主 SQL 中系统流程的 `config_json` 必须是包含真实 nodes/edges 的合法、已校验 DAG；禁止把 `config_json='{}'` 标记为 PUBLISHED。动态模型/知识库配置生成新快照时，持久化实际使用的版本图及配置校验结果；实例关联真实 flowId/version。
- 工业决策实例重试只能经 Decision 专用接口；它使用**实例快照**或明确升级后的可验证版本，绝不默认读取损坏/空的当前模板；对 `FlowEngine.start()` 当前“先插实例、后验证图”的行为安排局部修复或启动失败对账。
- 为避免快节点先完成、Orchestrator 后设状态的竞态，必须先持久化 run 的 RUNNING 状态并校验图，再调度异步 Flow；启动失败落 FAILED 并标注未完成关联，重启后的孤儿运行要有修复/告警。

### 33.3 What-if 的一致性门

- `BASELINE_CURRENT` 必须读取**指定排产方案原有任务**，不是把 `CURRENT` 交给 `Strategy.parse()`（其默认会回退 EDD）。销售订单/工单范围只处理该业务对象相关的工单，并保留明确的扩展候选范围规则。
- 采购行覆盖在 `PrdShortageInput.addArrival()` 按日期汇总**之前**应用：快照包含采购行 ID、原到货日、在途数量；相同物料多采购行只移动指定行，其他行不变。What-if 不更新任何 ERP 表或缓存。
- APS 未实现物料齐套约束之前，催货只改变缺料可行性指标，不得改变排程完工日或将预计值写成实际改善；未发布排产方案真实状态为 `COMPLETED`。

### 33.4 比赛交付与可复现证据

- 以官方最新公告核对报名、作品提交和总决赛时间；在报名登记、作品 PDF、正式/60秒视频、匿名可访问链接和组委会回执均确认后，才标记“参赛交付完成”。
- 分支提交不等于评委能看到成果：按项目仓库治理流程合并/推送公开仓库，记录远端默认分支提交 SHA，并通过匿名克隆/浏览验证（具体合并动作需要用户确认）。
- Benchmark 40 案例各自具备确定性 seed/reset、真实 bizId 解析和期望结果；等待审批是 `WAITING_APPROVAL` 状态，`AI_DECISION_READY` 是 SSE 事件，不得以 `READY` 作为轮询终态。
- App 需同时提供工作台入口、通知点击到 `/pages/ai/decision/detail?runId=...` 的路由和测试；PC 路径不能直接作为 App 业务链接。
- MVP `CREATE_WORKFLOW_TODO` 仅在确实创建 Flowable 待办后才可宣称为待办；向 IM 发一条 `workflow_todo` 类通知不等于创建业务审批任务。未完成该集成时只保留风险通知和本模块审批操作。
