## 2. 不可妥协的安全不变量

1. **数值与权限分离**：业务数值/单位/来源只由租户内 ERP 主数据和 MRP/采购服务提供；AI/LLM 只叙述，不能生成采购量、供应商承诺或单位换算。标识经全局雪花 ID 字符串序列化；租户、登录用户、权限和异步上下文沿现有路径校验。
2. **旧动作禁止新版执行**：旧采购载荷没有逐条 MRP 归属、合同版本及单位证明，审批 API 与 ERP 执行器均返回可审计的版本/来源门禁错误，且不产生草稿、需求占用或执行 Flow。旧 run、历史动作和 90 条证据保留原样；GET 仍可读并提示“历史口径，不可批准，重新分析”。人工驳回的既有权限/审计入口不变。P0 门禁在新版写入能力启用**之前**上线；不能依赖前端按钮禁用。
3. **不足即 UNKNOWN，而非零**：单位、精度、来源、有效供应商条款、分母或业务权重缺失时，拒绝生成可执行采购动作/自动唯一推荐；分析允许展示已验证的逐物料事实及明确缺失原因，绝不把未知映射成缺口 0、有效到货或收益。
4. **同源只占一次，申请不是库存**：同一 MRP `detail_id` 的未结人工与 AI 申请共同约束新增申请额度；DRAFT/审批中/已批准申请只算采购意图，不计为可用库存或确定到货。只有满足现有采购订单/到货状态和可信日期的记录才可参与已订购/到货仿真，不通过直接改库存或状态制造通过。
5. **无跨库假原子**：采购草稿、申请行、需求占用必须在 ERP 数据源的同一数据库事务；AI 主库 run/动作/Flow 状态通过既有幂等执行、独立验证、补偿和错误留痕协调，不宣称 master 与 ERP 具备单个本地 ACID 事务。ERP 落库之后、AI 状态回写之前宕机须能重读相同幂等键并恢复。

- 先按“缺失版本即旧版”识别历史数据；新合同准备就绪之前，**没有隐含兼容回退/开关可把旧动作当新版**。详情 API 为不可批准旧动作返回明确只读原因，PC 与独立 App 页面分别显示并禁用批准，服务端始终为最终判定者。
- 审批前预检为只读体验门禁，不能代替执行时的行锁核验；执行中发生确定性归属/单位冲突时只重算新 run，不对相同动作重试三次制造重复草稿。发生审批已提交、执行失败时按既有 `EXECUTING → FAILED/PARTIAL_SUCCESS` 与动作失败审计留痕；不得悄悄回到 WAITING_APPROVAL 或删除历史。部分成功动作不可谎报为全部回滚。

### P1｜可信来源、单位与供应商条款

- **新版运行与载荷**：新增持久化 `decision_contract_version=2`、`purchase_payload_version=2`（存量运行/动作视为 1）；新采购动作以“物料 + 需求日”为边界拆分，不把四种物料放在一个必须同时批准的动作中。每项冻结排序后的 `requirement_detail_ids`、对应缺口分配数量（基本单位）、基本单位 ID、原始必需日期、供应商条款 ID/版本、选定的订购单位及转换版本；载荷 ID 一律十进制字符串。幂等键包含租户、run、动作类型、物料及日期的确定性摘要，不再按仅 run/类型/目标合并不同物料。冻结数量必须由 ERP 净需求服务的同一作用域生成并独立回查；`maxGap`（峰值缺口）不能未经分摊就冒充每行 MRP 应申领数量。
- **主数据证明**：从 MRP 明细的 `unit` 与同租户物料 `base_uom_id`、有效 UOM 主数据验证来源数量口径；订购单位、MOQ 所属单位、订货倍数、是否允许拆零/每包装实物量必须来自**业务确认**的供应商/包装条款并带版本、生效时间。计划 BOM 平均用量允许非整数不等于“按个采购可拆分”；不得凭单位名称“个”、`category`、单独的 `conversion_rate` 或现有 MOQ 数值猜测规则。缺任一关键字段则保留风险分析、阻断采购执行并指明缺失项；转换须校验维度相同、方向、正数、精度和溢出，金额/件数不可混换。
- **数量、超额与交期**：分别记录 `coveredDemandBase`（来源净缺口中实际覆盖的量）、`requestedOrderQty`（采购单位的真实订购量）、`orderedBaseQty`（有证明的单位换算量）和 `excessBase = orderedBaseQty - coveredDemandBase`。即使 MOQ/倍数使 `excessBase > 0`，也不得把超额登记为某个 `detail_id` 的净缺口或库存在途；本版本 AI 采购动作**直接拒绝自动创建**并提示采购员在 ERP 走单独、已授权的超额采购流程；人工路径如果尚无超额审批/独立留痕，也同样拒绝，不能通过前端批准绕过。仅当条款完整、`excessBase = 0` 且额度充足时，新版 AI 才能形成可执行草稿；不足时可保留建议但不可批准。`requiredDate` 是需求日期，不是供应商保证到货日；提前期是否工作日、可用日历及承诺到货日未经证实时标交期风险，不生成保证交付的事实。
- **逐明细确定性净需求及分配**：采购额度使用同租户同物料的**全局竞争需求池**，与本 run 可展示的工单范围分开：纳入截至本窗口结束日所有未结、尚未领用完的有效 MRP `detail_id`（含窗口前逾期未结需求及 run 范围外工单），从有效库存/订单双源统一排序分配；授权 run 只显示自己有权看的明细，外部需求仅作为汇总占用事实参与容量扣减，不回传跨权限业务行。任一开放需求的来源状态/单位不能确定即阻断该物料的自动采购，不把未知的外部竞争需求当 0。以 `detail_id` 升序辨识唯一来源；`D_d = max(0, required_quantity_d - issued_quantity_d)`（基本单位）为未领毛需求，仅作为额度计算输入，不能把历史 `shortage_quantity` 或 `maxGap` 当可申请量。对每种物料，按 `(required_date ASC, detail_id ASC)` 排序，使用**一次**相同快照/ERP 事务中的 `max(0, stock_quantity - reserved_quantity - safety_stock)` 可用结存，及状态有效、仍未收货、预计到货日在 `[snapshotAt业务日, required_date]` 内的订单行供给；对于 `required_date < snapshotAt业务日` 的逾期未结需求，不存在可以追认历史按时到货的订单供给，**仅当前已实收并入账、实际可用的库存可减少今日仍须采购的数量，但不能抹去原始逾期风险**；订单剩余量、库存与供应商订单都按相同基本单位核验，每一供应来源只在租户物料全局竞争需求池分配一次；对相同租户/物料/窗口的不同 run 重算时由全局确定性规则给出相同来源归属，不是每个 run 都从满额库存重新分配。**已转成**相对于快照日尚未逾期且不晚于需求日、状态可信的有效订单**的来源额度只计为该订单的可采信在途供给，不再作为申请意图占用重复扣减；预计到货日已过但未实收的订单剩余量无论其预计日是否早于原需求日，一律进入第三类而非在途供给；申请行转出时由订单承接但仍为 `DRAFT`/待审批或有效但晚到的订单行是第三类 `ORDER_COMMITTED_NOT_TIMELY_SUPPLY`，仍计入阻断新申请的 `C_d`，绝不进入及时供给；订单经 ERP 状态机变为有效、预计到货日仍未过且不晚于需求日才原子地从 `C_d` 转至可采信在途供给，延期但仍生效的同源订单需人工催交/重排而不自动重复申请。对于部分到货，只将已过账的实收量转入库存供给，剩余量依订单状态和到货日分别计为有效在途或阻断额度，任何数量不得同时落两类。**优先以来源资格和到货日按确定性顺序分配，不得以晚到供应覆盖更早需求；不明确订单到货/单位、库存冻结或数量分配关系则该物料的自动采购门禁失败，不把不明供应当 0。`uncovered_d = max(0,D_d - eligibleSupplyForNewPurchase_d)`（只评价**截至快照日仍需采购的数量**，不得写成按时交付率；历史逾期风险单独保留）；再减去经核验的**同一 detail_id** 未转换订单的有效申请意图及 `ORDER_COMMITTED_NOT_TIMELY_SUPPLY` 的阻断额度 `C_d`（含归属可证明的 legacy 未结草稿；已转单申请不再与订单承接重复计算），得到 `requestable_d = max(0,uncovered_d-C_d)`，若 `C_d>uncovered_d` 只标业务冲突并拒绝自动申请，不能吞掉超额。采购动作冻结每条 `detail_id -> coveredDemandBase_d`，须有 `0 < coveredDemandBase_d <= requestable_d`，并满足 `ΣcoveredDemandBase_d = netGapBase`；只有每个分配、库存与订单来源经 ERP 事务重读、日期一致且在窗口内，才可创建草稿。时间序列 `maxGap` 只用于风险观察，不直接决定申请量，也不能把不同日期同一物料的同一供给重复占用；无法证明快照与当前分配一致即拒绝/重算。
- **同源额度与并发**：ERP 新增逐来源的申请占用账（至少包含租户、`detail_id`、采购申请行、占用基本数量、状态、版本/幂等键、创建/释放留痕）。同一物料不同日期可拆分；同一需求可分批申请，但所有有效占用之和不得超过由 ERP 净需求服务当下证明的可申请上限。人工与 AI 的 MRP 关联申请创建/修改/提交/取消都通过**同一个占用服务**；对同租户物料使用受唯一索引保护的可锁定 guard 行序列化**所有** MRP 关联人工/AI/低库存来源写入口，随后按稳定顺序锁竞争池的来源需求行、有效库存/订单及 legacy 申请行，在同一 ERP 事务重读全球分配与 `C_d`、核对余额，再插入草稿/行/账本；未接入 guard 的库存/订单写路径须锁对应资源或在写后进行版本/CAS 新鲜度校验，无法证明供应读取一致就拒绝，不只做 RR 快照或事前 SELECT。唯一键保障行/动作重放；新增覆盖量 `<= requestable_d`，写后有效总占用 `<= uncovered_d`，不得把已扣 `C_d` 的余额当占用总上限。存量 `pu_purchase_requisition_line.source_id` 在 AI 场景是 runId、在低库存自动申请场景是物料 ID、在部分人工 MRP 场景才是 detailId；不得重释旧字段或依据 `source_id` 单独断言占用身份，新账本使用显式来源类型 + detailId + 申请行 ID。低库存申请若无明确 MRP detailId，不得冒充同源账项；自动低库存生成路径在新账本启用期间**默认暂停新增**，除非已接入上述租户—物料 guard 的同一 ERP 事务锁，并能与 MRP 关联申请共同查询、阻断重叠及保留非 MRP 来源身份（不能只做事前 SELECT）。无法归属时只读提示并要求人工关联/拒绝新增占用，不凭空造明细 ID。对于已存在、未登记新占用账的 `CGSQ202609290001`，按同源 legacy 未结行阻断新占用，直到采购负责人处理；禁止自动取消、自动归并或把 510 个直接写入净缺口。`convertToPurchaseOrder` 必须与申请行→订单行的同源账本状态转移在**同一 ERP 本地事务**中，继承已锁定的来源与基本单位数量；事务失败时订单/占用一起回滚，不允许源申请与订单双计。在订单取消、部分到货/退货、申请撤销或 `deleteDraftIfUnchanged` 条件补偿时，先检查现存有效下游订单及库存入库/退货事实，分别迁移、减少或释放对应来源额度，不把部分到货当全部满足；补偿删除草稿必须与释放/标记账本同事务并受版本 CAS 条件保护。**不得因申请单关闭就释放已由订单承接的占用**；最终仅在无有效下游承接或已可信业务结案后释放，并保留完整转移/释放审计与失败重试。ERP 草稿事务已提交而 master AI 动作仍 EXECUTING/回写失败时，重试必须先按 `(tenant_id, decision_idempotency_key)` 查原草稿与来源账本，逐项验证版本、归属和载荷一致后恢复同一个结果，不得生成新编号、再占用或把补偿过的键重新启用。
- **新鲜度**：快照及指纹只包含该 run 租户、物料、上述全局竞争池需求明细范围内会影响判断的 MRP 日期/数量/状态、物料 UOM 与换算版本、供应商条款版本、未结申请/占用以及现有有效采购/到货事实；来源发生变化标旧分析 STALE/拒绝审批，生成新 run。审核前哈希检查和 ERP 事务内来源行锁检查缺一不可；不跨租户扫描或把空查询当数据缺失以外的“已安全”。

### P2｜量纲安全的 KPI 与方案排序

- `ShortageSimulationResult.Item` 保留每个物料的 `maxGap`、基本单位 ID、日期、来源明细和证据键，保证同场景、同物料可比较。新版 `DecisionKpiSet` 应扩展显式 UOM/合同版本字段；`totalShortageGap` 仅在**全部参与项具有经证实的同一物理量纲且可统一换算到明确 UOM**时输出总量并**同时返回单位 ID/换算来源**及证据；混合千克/个/升时值与单位均为 null，旧运行原值仍留作历史审计，既有 KPI 无法作为新版评分输入。新分析报告以逐物料单位和缺口为主。
- **新版量纲无关分值的唯一算法**：固定明细集合 `Q` 为同一 run 根业务作用域、同一窗口 `[snapshotAt在业务时区当日, 当日+horizonDays-1]` 中已核验且 `requiredQty = max(0, required_quantity-issued_quantity)` 为正数的 `RequirementFact`；固定物料集合 `M = {material(d) | d∈Q}`，所有场景共享**完全相同的** `Q`、`M` 和日期。`D_m = Σ_{d∈Q且material(d)=m} requiredQty_d`（基本单位、未扣库存或在途；防止把供给又扣一次）；`G_{s,m} = scenario.shortage.items[m].maxGap`（各物料对应的**同一窗口内峰值、基本单位**，不是所有日期缺口之和）；若模拟器没有该物料 Item，只有带完整来源证据明确写明“经仿真 0 缺口”才按 G=0，否则阻断该场景。对每个 m 有 `D_m>0`、同来源单位经核验且 `0<=G_{s,m}<=D_m`，计算 `r_{s,m}=G_{s,m}/D_m`；固定 `scale=8,RoundingMode.HALF_UP`，`R_s=Σ_{m∈M}r_{s,m}/|M|` 同样 8 位舍入、`M` 等权，独立保存原始 `R_s`、每物料比例和证据键。若 `M` 空且完整快照证明确无正需求、无缺料，则 `R_s=0` 并保留“无需求”的来源证据；若有风险但 D 缺失、跨日期/物料集合不一致或 G 大于 D（例如安全库存因素无法归因），标 `MISSING_SOURCE_OR_UNIT`，所有相关方案**不自动推荐，也不生成采购动作**，而不是算作零。参评集合 `C` 是这次运行请求的**全部已生成方案**且其所有必需 KPI/物料事实完整，缺一个就不推荐任何方案（而不是忽略某个场景）；`minR=min_{s∈C}R_s,maxR=max_{s∈C}R_s`；`N_s = 0` 当 `|C|=1` 或 `maxR=minR`，否则 `(R_s-minR)/(maxR-minR)`，同样 8 位舍入，0 仅表示相对无差距，**不表示原始缺料比例为 0**。新版排名以 `N_s` 替换当前 shortage 项，其他项仍按现有 complete 候选归一化和原始配置权重，目标分最终 6 位舍入，按可行性→目标分→变更数→成本→方案码排序；单候选或同值全相等保留 R 原值、N=0。新算法/舍入及证据政策独立版本号，不从已存运行动态重算。
- `DecisionScenarioRankingService` 的新合同只消费有证据的 `shortageImpactRatio`，使用固定精度/舍入并保留评分中间值与证据键，确定性并列顺序沿用方案编号；旧运行仍按旧合同只读显示，不在读取时重排。若没有可行候选或评分依据不足，推荐码为空并解释原因，不由模型补数；风险分析和可执行采购动作分别满足自己的证据门禁。
